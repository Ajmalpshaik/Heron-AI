## F44 — a kept change could say how its counts compare with the dry run before it, once Heron knows whose dry run that was

### 🟡 F44. One line on a kept change, comparing its counts with the dry run before it - not built, because nothing Heron keeps says the dry run was this chat's

Raised 2026-11-12, while the dry run ([D-155](../decisions/D-155.md)) was repaired after review
([row 5b-1602](../fragment-issues/row-5b-1602.md)). The owner approved the line in principle that day,
*only if it stays small and honest*: when a kept run follows a dry run of the **same** capability on the
same model in the same chat, one line - *"the dry run counted 12 changed, this run kept 14 - the model
changed in between, or the selection did"*. The condition given with it: **if it needs more than the run
records the server already keeps, it is not built, and is written here instead.** It does.

**What Heron keeps today**, read off the code on 2026-11-12:

1. **The run record** - one file for each fragment write, written by the add-in and read by
   [`heron_run_records.py`](../../mcp/server/heron_run_records.py). It holds the fragment, the model's
   title, the time and the whole reply, Revit's counts and the verdict's kind among it. **It holds
   nothing that says which chat asked.** A proof's rollback from the command
   line, another chat's dry run an hour ago and this chat's a minute ago are the same kind of record.
   The line would say *"the dry run counted"* of a run this chat may never have seen.
2. **The batch** (`heron_run_records.Batch`) - what the last reply of a capability printed. It is the
   chat's own, and it ends at a pause of `BATCH_GAP_S` seconds, which is shorter than the time a modeller
   takes to read a dry run's counts and say *keep it*. Since row 5b-1602 a dry run is not remembered in
   it at all.

So the line needs one thing Heron does not keep: **for the life of the chat, the run id of the last dry
run of each capability on the pinned model.** With that id the counts are read from the run record, and
nothing is counted twice. It is a small piece of memory in the server's process - gone when the chat
restarts, and the line is then simply not printed.

Three things to settle before it is built:

1. **Is memory for the life of the chat acceptable here?** Everything else the server remembers about a
   chat is the pin, the binding and the batch. This would be a fourth.
2. **Which counts.** Revit's added, modified and deleted for the fragment's own part, or the total with
   its setup steps. The change report prints them apart
   ([row 5b-407](../fragment-issues/section-5b-rows-401-425.md)).
3. **What it says when the counts are equal.** Nothing, or *"the same as the dry run counted"*. The
   second reads as a confirmation, and [D-126](../decisions/D-126.md) refused two runs as the way a
   change is approved: equal counts do not say the same elements were changed.

**Not built, and not answered yet.**
