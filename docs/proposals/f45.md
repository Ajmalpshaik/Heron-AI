## F45 — an AI that can write files can turn on Changes, Admin and Publish, because each is one line in a text file

### ✅ F45. Changes, Admin and Publish are turned on only by a click in Revit, never by a file, and an office can lock them off - accepted and built 2026-11-16 as D-166, not yet run in Revit

#### The recommendation: a file can never open a switch - only a click in Revit can

Three layers, built in this order. **Layer 2 is the fix**; layer 1 is quick, and layer 3 is for a PC that
wants a lock nobody below an administrator can open. The modeller still turns Changes on in one click in
Heron's Settings. Nothing here changes [Article 7](../../HERON_CONSTITUTION.md): a switch is never the yes it
asks for before a delete, a purge, a workset change or anything touching a link.

**Layer 1 - heron-guard, a tripwire. Python only, small.**

1. A second rule in `heron_guard.py`: refuse a proposed write to a file named `heron.config`, **anywhere
   on disk**, whose new text turns on `write.enabled`, `admin.enabled` or `publish.enabled` - the key and a
   true word, the same four words `HeronConfig.GetBool` reads as true. The same for text naming the
   registry key of layer 3.
2. The matcher in `.claude/settings.json` widens to Bash, PowerShell and the MCP tools that write files
   (Desktop Commander's `write_file` and `edit_block`, for one). For a command, the rule refuses text that
   names `heron.config` and one of the three keys. **Reading the file stays allowed.**
3. Same polarity and traps as today: deny-tier, a crash refuses, `HERON_GUARD=off` is the hatch, and every
   refusal is a diary line - so `python tools/hook-report.py` shows from evidence whether an AI ever tried.
4. Kept after layer 2, as a tripwire that records attempts. [heron-guard's skill](../../.claude/skills/heron-guard/SKILL.md)
   says *"It checks one thing"*; this makes it two, and the skill is corrected in the same change.

*What it does not stop:* a script that writes the file another way (a `.py` or `.ps1` written, then run);
a host that does not load this repository's settings - Claude Desktop, Cowork, or Claude Code opened in
another folder; an AI that edits `.claude/settings.json` or was started with `HERON_GUARD=off`. **It
catches the honest attempt** - the one Heron's own refusal invites today. It is not a lock.

**Layer 2 - the three switches leave `heron.config`. The add-in, C#.**

1. **Changes, Admin and Publish are held inside Revit, in memory.** Pressing ON in Heron's Settings
   window - with the same question on the way on as today ([D-106](../decisions/D-106.md) item 5) - is the
   only way to set one. Nothing about them is written to disk.
2. **The three keys are removed from `HeronConfig`'s defaults and from `heron_config.DEFAULTS`.** `Load`
   already ignores a key it does not declare - *"An unknown key is ignored, not adopted"* - so a line added
   by anybody does nothing, the next `Save` drops the old lines, and a restored backup cannot bring a
   switch back on.
3. **Every switch is OFF when Revit starts.** [D-19](../decisions/D-19.md)'s default, kept every session
   rather than once. Closing Revit turns them off.
4. **Each Revit holds its own.** With Revit 2024 and 2027 both open, Changes on in one is not on in the
   other. The chat's health report asks the Revit it is bound to, over the pipe it already uses, instead
   of reading the file.
5. **No refusal or message names the file any more.** Each says only: turn on Changes in Heron's Settings
   (*Heron > AI Bridge > Settings*).
6. **Ask to Keep and the Companion stay in `heron.config`.** Not part of this proposal.

*The cost to the modeller:* one click and the question after each Revit start, instead of once. That is
the whole cost. *What it does not stop:* a program that drives Revit's screen as the modeller - computer
use, UI Automation, sent keys - presses the button and answers the question exactly as a person would; a
program that writes into Revit's memory on purpose, which Windows allows for the same user; an older
Heron still installed for another Revit year, which reads the file until it is updated - so every year's
add-in is updated together.

**Layer 3 - an administrator's ceiling in the Windows registry. Optional, per PC.**

1. The add-in reads `HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Heron`, three numbers: `AllowChanges`,
   `AllowAdmin`, `AllowPublish`. **0** - that switch cannot be turned on on this PC, and its Settings row
   says *"Turned off on this PC by its administrator"*. **Missing or 1** - the modeller may turn it on, as
   in layer 2. Read fresh on every decision.
2. **Only an administrator can write that key.** A program running as the modeller cannot, and the
   Windows administrator prompt sits on a screen another program cannot press. This is the one layer that
   holds against a program running as the modeller - **but it can only keep a switch off. It cannot tell
   whether a person turned one on.**
3. IT sets it by Group Policy or Intune. The owner can set it on his own PC - `AllowAdmin` and
   `AllowPublish` at 0 while neither is needed - and lift it himself through the administrator prompt.
4. **No key, no ceiling**, so nothing changes on a PC until somebody sets it.

*What it does not stop:* an AI running as administrator - Claude Code started *"as administrator"*, or a
PC whose administrator prompt is set never to ask - can write the key too.

**Taken from, and re-authored** ([31 research](../31-research.md),
[D-25](../decisions/D-25.md)): layer 3's idea that the ceiling sits where the modeller's account cannot
write comes from vibe-bimer/smart-revit (MIT), an admin-owned policy file, and its registry place from
sharafutdinovdi/revit-model-mcp (MIT), a workstation lock with a registry policy above it - both as the
research note describes them; neither repository was read again for this. No code, name or wording is
taken. Layer 2 is Heron's own.

**Not chosen, one line each:**

- **Changes on only through the administrator prompt, every time.** The one gate a program running as the
  modeller cannot pass, but a modeller with no administrator rights - most office modellers - could never
  turn Changes on.
- **The switch kept on disk with a signature** (Windows DPAPI). Any program running as the modeller can
  make the same signature, and Heron's code is public: a longer edit, not a lock.
- **The hook alone.** A tripwire, not a lock - layer 1's own limits.

- **Positive:** Changes ON in Settings, a change from a chat is kept.
- **Negative:** Changes off, `write.enabled = true` appended to `heron.config` from Claude Code's shell -

  and opened again - Changes is off. `AllowChanges` set to 0 - the row cannot be turned on.
- **Layer 1:** the same append, proposed through Edit and through Bash, is refused and leaves a diary line.
