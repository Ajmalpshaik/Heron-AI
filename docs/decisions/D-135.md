### Context

On a PC whose Claude app is the Microsoft Store build, Windows keeps a private copy of `%APPDATA%` and
`%LOCALAPPDATA%` for that app and every process it starts - Claude's shell and every heron MCP server - under
`%LOCALAPPDATA%\Packages\AnthropicPBC.Claude_fnn82j28hfe8t\LocalCache`, and deletes it when the app is reset
or uninstalled. Revit is not such a process. Rows 5b-416 to 5b-419 recorded what followed: the Companion
button reads a folder the chats never write, and the knowledge store, every project's memory and the brain's
audit sat in the copy only. `HeronPaths` says DATA must survive every update, uninstall and reinstall; there,
another program's Reset deletes it.

**Measured on the owner's laptop, 2026-10-17 at 23:53** (Store Claude `2.31226.1.0`), with a throw-away
`%APPDATA%\HeronProbeQ63` made in the copy from Claude's shell and on the real disk from the owner's Terminal
panel, which runs outside the app; each side then read both places by their own paths:

| from inside the app, in a folder that exists... | lands in |
|---|---|
| in BOTH places - a new file | the copy |
| in both - a new folder, and a file in it | the copy |
| in both - an append to a file both hold | the copy's file; the real one unchanged |
| in both - an append to a file only the real disk holds | the real file |
| in both - write a temporary file, then rename it over a file both hold | the copy |
| in both - write a temporary file, then rename it over a file **only the real disk holds** | **the copy** - a new file there, which from then on hides the real one, still holding its old text |
| ONLY on the real disk - a new file, a new folder and a file in it | the real disk ([row 5b-1066](../fragment-issues/section-5b-rows-401-425.md), and new folders now too) |

So whether a write survives depends on which folders exist where - and the copy already held `Heron\knowledge`,
`Heron\audit` and `Heron\config`, while the installer had made a real `%APPDATA%\Heron\knowledge` the same day.
A folder and a file written from inside to `%USERPROFILE%\.heron-probe-q63` and to `%TEMP%\Heron-probe-q63`
were on the real disk when read from outside, and nothing of either was in the copy; the copy has no `Temp`
folder of its own. Every probe folder was removed by its exact path from both sides afterwards.

### Decision

1. **Heron's Python side keeps the DATA it writes in one home**: `HERON_DATA` when set, on any system; on
   Windows `%USERPROFILE%\.heron`; anywhere else none - as before, when Linux had no `%APPDATA%`. The
   knowledge store and every project's memory are `<home>\knowledge`; the brain's audit is `<home>\audit`.
   `HERON_KNOWLEDGE` and `HERON_AUDIT` override as they did. A dot, because `Heron` is a name a person may
   give the folder they unzip the product into, and docs/06 s2 keeps product and data apart.
2. **The add-in's own DATA does not move.** Its settings and its trail stay in `HeronPaths.Data`,
   `%APPDATA%\Heron`. The gaps report reads both trails - the brain's from the home first, then the add-in's
   folder, a brain line found in both once - so moving the brain's file no longer blinds it, which moving
   `HERON_AUDIT` alone would have.
3. **The Companion's notes go to the temporary folder, on both sides.** `HeronPaths.Companion` is
   `<Path.GetTempPath()>\Heron\companion`, under a new `HeronPaths.SharedDerived`, still DERIVED and still safe
   to delete; the chat names the same folder through `heron_bridge_client.temp_folder()`, which reads TMP,
   TEMP and the profile in .NET's order. The temporary folder is machine-local, as D-17 wants.
4. **What the old places hold is carried, never moved.** The first time a process asks for the default home
   and finds no `carried.json` in it, `heron_paths.home()` copies in, from each Store Claude's copy first and
   then `%APPDATA%\Heron` as that process sees it: every knowledge file the home has not got - a store through
   SQLite's own backup, read-only, so one being written is not torn - and every line of the brain's audit
   files that the home's do not hold. A file the home already holds differently is left as the home has it
   and named in the note. The add-in's trail and settings are not carried. Nothing in an old place is changed
   or deleted. `python brain/heron_paths.py --carry` carries again on purpose; `--where` says where things are.
5. **Removing the old copies is the owner's to decide, and never automatic.**

### Alternatives considered

- **Leave Heron as it is, and warn** (Q-63 shape 1). All four rows stay true.
- **A virtual environment on `D:`** (shape 2). Settles where packages live; the server is still a child of
  the app, so everything it writes still lands in the copy.
- **Keep `%APPDATA%\Heron` and lean on the rule measured above** - make every folder on the real disk from
  outside, and empty the copy's `Heron`. Rejected: the rule is Windows' behaviour, not a promise, and it is
  undone the moment a `Heron` folder exists in the copy again - a Revit started from Claude's shell writes its
  settings there, which is how the copy got `Heron\config` (row 5b-1004) - after which every write follows it.
- **Write to the real path spelled in full.** Measured redirected the same way ([Q-70](../open-questions/tier-2.md)).
- **Move `HeronPaths.Data` itself, on both sides.** Would also settle Q-70, since both sides would read one
  `heron.config`; but it moves the add-in's settings and trail on every PC, needs the add-in rebuilt for eight
  releases and a carry on the Revit side. Left to Q-70.
- **`%USERPROFILE%\Heron`** without the dot - see point 1. **`Documents\Heron`** - OneDrive may own Documents.
- **The Companion's notes in the home.** Runtime state in a DATA folder, and the profile roams with a roaming
  profile, which D-17 says runtime state must not.

### Consequences

- **On a Store-Claude PC** the store, every project's memory and the brain's audit survive a Reset or
  uninstall of the app. Packages Claude installed itself are still in its copy; the installer's, since
  2026-10-17, are not (Q-63's install half, row 5b-417).
- **Every PC moves once**, the office PC included: the first chat on this code carries its
  `%APPDATA%\Heron\knowledge` and brain audit into `%USERPROFILE%\.heron`. A chat started before the update
  keeps writing the old place until the Claude app is restarted; `--carry` fetches what it wrote.
- **Both halves of the Companion must be updated together.** A chat on this code and an add-in deployed
  before it look in different folders, and the button says no chat is running; an add-in rebuilt and deployed
  from this change is owed before [BK14](../needs-checking/group-bk.md) can be pressed.
- **A planted `%APPDATA%` no longer names a knowledge folder** off Windows: suites plant `HERON_DATA`, and
  every shared-store helper in `tests/` plants it beside `%APPDATA%`.
- **`tools/heron-backup.py` still backs up `%APPDATA%\Heron` by default**, so the moved data is backed up only
  when `HERON_DATA` names the home - recorded, not changed, as [row 5b-1069](../fragment-issues/section-5b-rows-401-425.md).
- **Not moved, deliberately:** the add-in's run records, logs and bridge files (DERIVED, written by Revit on
  the real disk), the server's checkpoints and the development hooks' log (DERIVED), and `heron.config` -
  [Q-70](../open-questions/tier-2.md)'s, still open.
- **[Row 5b-1065](../fragment-issues/section-5b-rows-401-425.md) is not settled by this.** It is about which
  versions of Heron's packages a Store-Claude PC should end with, and packages are not data; see that row.
