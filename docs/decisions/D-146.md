# D-146 — A fragment may name Revit's appearance-asset namespace, so a material's render appearance can be edited

> One record of [the decision log](../DECISIONS.md). Decisions are append-only: to change one, write a
> new decision that supersedes it.

**Status:** Proposed · **Date:** 2026-10-20 · the owner has not read this back; it is what the 2026-10-20 task asked for ("in the material also ... all the parts should be covered"), written down so it can be accepted or overturned
**Keeps:** [Article 21](../../HERON_CONSTITUTION.md) - every fragment already in the library compiles with the namespace added, on every release it claims, 2020 to 2027 (measured 2026-10-20)
**Affects:** [`check-fragments-compile.py`](../../tools/check-fragments-compile.py) (`USINGS`), [`HeronFragmentImports.cs`](../../revit/Heron.Revit.Addin/HeronFragmentImports.cs), [`set-material-appearance`](../../brain/fragments/set-material-appearance/fragment.yaml), [`create-starter-materials`](../../brain/fragments/create-starter-materials/fragment.yaml), [`list-materials`](../../brain/fragments/list-materials/fragment.yaml) version 3, [row 5b-1264](../fragment-issues/section-5b-rows-401-425.md), [Group IA](../needs-checking/group-ia.md)

### Context

What a Realistic view and a rendering draw a material with is its **appearance asset**. Revit keeps the
asset's types - the asset, its typed properties, the property names of the Generic appearance, and the
edit scope that is the only way to change one - in a namespace of their own. The fragment contract did not
supply it: `tools/check-fragments-compile.py` and the add-in's executor import one shared list, and a
fully-qualified name is no way round it, because the structure gate forbids the vendor prefix in `brain/`
so that a fragment can use only what that list says it has.

`REPORT_MATERIAL_TEXTURES` (2026-10-12) read assets by `var` and reflection to stay inside the list, and
the gap-fill plan recorded the write half - repathing a texture - as **BLOCKED, a decision for the owner**.
On 2026-10-20 a duct heater family whose materials `CREATE_MATERIAL` had made drew in colour in a Shaded
view and **flat dark grey in Realistic** on Revit 2020 ([row 5b-1263](../fragment-issues/section-5b-rows-401-425.md)):
nothing in Heron could give a material an appearance. The owner asked the same day for every part of a
material to be covered.

### Decision

1. **The appearance-asset namespace joins the list a fragment may assume**, in both halves at once -
   the gate's `USINGS` and `HeronFragmentImports.Namespaces` - in the same place in each.
   `tests/test_fragment_imports.py` holds the two equal.
2. **It is added because nothing else reaches the edit scope.** The rule both lists carry stands: a
   namespace whose types a fragment could reach another way does not belong. Reading an asset could be
   done without it; writing one cannot.
3. **The add-in must be rebuilt and redeployed** before a fragment that names it runs at the PC - until
   then such a fragment fails to compile there, and says so, while the gate here is green. That is the
   first row of Group IA.

### Consequences

- `SET_MATERIAL_APPEARANCE` and `CREATE_STARTER_MATERIALS` edit appearance assets, and `LIST_MATERIALS`
  version 3 reads them by their types. All are DRAFT until [Group IA](../needs-checking/group-ia.md) is
  run on Revit and signed.
- **Measured:** every fragment in the library compiles on every release it claims with the namespace in
  the list (`tools/check-fragments-compile.py`, 2026-10-20) - no existing name became ambiguous.
- **Not established:** that the add-in built with the longer list loads and runs an existing fragment
  exactly as before on the owner's PC - Group IA's first row asks it, with a read every release has.
