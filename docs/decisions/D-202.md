### Context

MCP lets a server mark each tool read-only, destructive, idempotent and open-world, and give it a title a host shows
in place of its name. Anthropic's directory asks for a title and a read-only or destructive mark on every tool, and
for descriptions that do not tell the model to call other tools. Heron already derived three marks from each tool's
risk in `heron_tools.TOOLS` and typed none at a tool. What that left wrong, read off the code on 2026-11-26:

- **Risk is about the model, and some tools keep things outside it.** `heron_commands` and `heron_checklist` save,
  replace and delete the modeller's own files; `heron_hvac`, `heron_fire` and the loads and sprinkler tools keep a
  project's standards and answers; `heron_earlier_answers` copies answers into a model's record; `heron_helped` adds
  to a count. All were READ or ANALYZE, so all were labelled read-only - a host could run any of them unasked.
- **`openWorldHint` was unset**, which a host reads as *this tool reaches the open world*. None does.
- **No tool had a title**, so a host showed `revit_isolate_temporary`.
- **Several descriptions ordered a call**: *"call heron_check"*, *"use revit_read"*, *"Call this BEFORE answering a
  standards question from your own knowledge"*, *"ASK THIS BEFORE ANY CHANGE"*.

### Decision

1. **A title for every tool**, in `heron_tools.TITLES`, short and in Revit words, served on the tool and in its
   labels. A tool the server registers without one fails `tests/test_tool_registry.py`.
2. **What a tool keeps outside the model is declared once**, in `heron_tools.KEEPS`: what it keeps, whether it can
   replace or delete a thing the modeller kept, and whether every call adds another. A tool there is **not
   read-only**; **destructive** when it can replace or delete; **not idempotent** when every call adds one. A record
   Heron keeps of its own working - the audit trail, a gap note, the dashboard's last numbers, a picture written and
   deleted, a table put on the Companion page - is not the modeller's and does not count.
3. **`openWorldHint` is false for every tool**, because `heron_tools.OPEN_WORLD` is empty: Heron talks to a Revit on
   this PC through its pipe, to its own files and to the Companion page on `127.0.0.1`, and the host has the network
   (D-01). The registry test holds that no file of the server imports a network client. The library encoder's
   weights are fetched once on a machine that has never held them; that is a part being installed, not where a tool
   reaches.
4. **`EXECUTE` stays neither read-only nor destructive** - judged, not assumed. Selecting, zooming and Temporary
   Hide/Isolate change nothing in the model but replace what the modeller has selected or isolated on screen; nothing
   they change is kept.
5. **A description says when its tool is used and never orders a call** - another tool's, or its own as *"Call
   this"*. Naming another tool stays: *"a question is `revit_read`'s"*. Every piece of guidance is kept, re-worded
   as *"Use it when ..."*. `heron_method`'s *once, before the first step* is kept with its meaning. The server's
   instructions (`host.chat`) are not touched.

The labels stay advice to the host. **The gate is the add-in's**, and nothing here moves it.

### Consequences

- **Nine READ or ANALYZE tools are no longer labelled read-only**, so a host that runs read-only tools unasked asks
  before them. That is the point: each keeps something the modeller would miss.
- **A new tool needs a title, and a row in `KEEPS` if it keeps anything**, in the same change, or the registry test
  is red.
- **The labels and titles were read back through a real SDK** - `tests/test_mcp_serves.py` on the pinned 2.2.0 and on
  2.3.0 - and the server started over stdio and listed them. **Nothing here was run in Revit or seen in a host's
  permission prompt.**
