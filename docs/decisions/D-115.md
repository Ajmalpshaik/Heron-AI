# D-115 — A fragment that must run with no transaction open declares D-112's switch too, and the first is OPEN_VIEW

> One record of [the decision log](../DECISIONS.md). It was given its own file on 2026-10-13 so that it
> can be read alone; **its words are unchanged, only its links were re-pointed.** Decisions are
> append-only: to change one, write a new decision that supersedes it.

**Status:** Proposed · **Date:** 2026-10-13 · **Source:** [FRAGMENT-ISSUES 5b-455](../fragment-issues/section-5b-rows-401-425.md) - OPEN_VIEW refused by Revit for every view through revit_change, a sheet included, and the cause measured on Project1, Revit 2020, the same day
**Widens:** [D-112](../DECISIONS.md#d-112--a-fragment-that-must-work-in-one-of-revits-edit-modes-opens-its-own-transactions-inside-herons-group) item 1 - the switch it made for Revit's edit modes is declared for one more reason, and nothing else in D-112 changes
**Keeps:** Golden Rule 16 - one TransactionGroup, one undo, rolled back on a preview · the read path's guarantee that nothing there can open a transaction · [D-28](../DECISIONS.md#d-28--generated-code-is-c-compiled-at-run-time-in-process) - nothing new in the add-in
**Affects:** `open-view` only. Nothing in [`RevitFragment.cs`](../../revit/Heron.Revit.Addin/RevitFragment.cs) or [`heron_fragment.py`](../../brain/heron_fragment.py) changes

### Context

Every fragment `revit_change` runs goes to the add-in as `run_fragment_write`, which opens a
`TransactionGroup` and, inside it, a `Transaction` around the fragment. `revit_read` refuses anything
declared above ANALYZE, so a fragment declared EXECUTE - one that changes the session, not the building -
has no other door. **Revit changes no view inside a transaction.** Measured 2026-10-13 on Project1, Revit
2020, session 18392, with a scratch fragment outside the repository: inside Heron's transaction
`UIDocument.RequestViewChange` threw `InvalidOperationException`, *"Cannot change the active view of a
modifiable document (with a transaction curently open)"* (Revit's spelling); with no transaction open it
returned and the view on screen changed, read back afterwards - and the same with a `TransactionGroup`
open and no transaction in it. So OPEN_VIEW, PROVEN on the strength of a proof whose positive case was
the view already on screen, was refused for every other view a chat asked for: a sheet in Project2 and a
3D view in Project1 that same day.

D-112's switch - the ambient need `editScopeFailures` - is exactly "run me inside the group with no
transaction open". D-112 item 1 says a fragment declares it *"when it has to work in one of Revit's edit
modes"*, and changing the active view is not an edit mode.

### Decision

1. **A fragment that Revit refuses inside a transaction declares `editScopeFailures` too, whatever the
   reason** - an edit mode (D-112) or a call Revit will not make while the document is modifiable, such as
   changing the active view. The declaration is still the only switch.
2. **A fragment that opens no transaction of its own declares the need and never touches it.** D-112's
   item 5 still holds: if the document is modifiable when it returns, the run is refused.
3. **The first is OPEN_VIEW, version 2.** Each further one is named on its card with the Revit refusal
   that made it need the switch, so the reason can be checked against the release it was measured on.

### Alternatives considered

- **A second ambient need with an honest name** - "run with no transaction". An add-in change: a new
  constant beside `EditScopeNeed`, the same name in `AMBIENT`, a rebuild and redeploy for eight releases
  and a Revit restart, all for a switch that does what an existing one does in the same place. Not taken
  now; if the owner wants the name, both are renamed in one change and every card that declares either
  follows.
- **Let `revit_change` send EXECUTE fragments down `run_fragment_read`.** Breaks the read door's one
  guarantee, that nothing on it can open a transaction (`heron_tools.door_refusal` says why EXECUTE is
  kept off it), and takes the Changes switch off every EXECUTE fragment at once.
- **Correct OPEN_VIEW's card to say it cannot open a view through `revit_change`.** Leaves a PROVEN
  capability whose only door refuses it, and every chat asked to open a sheet tells the modeller to do it.

### Consequences

- **The need's name now says less than it does.** A reader of `editScopeFailures` on OPEN_VIEW's card
  finds no edit scope in its code; the card's comment on the need and this decision are what say why.
- **A preview opens the view too.** Measured: a view change asked for inside a group survives the group
  being rolled back. It was already true of the "already on screen" answer, and a view change is a
  session change, not one in the model or in Revit's undo list - EXECUTE, not MODIFY.
- **Such a fragment cannot run on the read path at all** - the add-in refuses any fragment declaring the
  need there, so a proof runs it with `--write`. For an EXECUTE fragment that loses nothing:
  `revit_read` refused it already.
- **Measured on Revit 2020 only.** Whether 2021 to 2027 refuse a view change inside a transaction in the
  same words is not measured; the switch makes the answer the same either way.
