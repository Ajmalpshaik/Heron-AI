### Context

After D-199, seventeen modules were left that the strict count found nothing calling. Each was checked again, in
four ways, before anything was removed:

1. Does anything outside its own tests import it, load it by name (a built name included), or run it - CI, `tools/`,
   the helper agents and skills in `.claude/` and `.codex/`, the guides, the READMEs, the installer, the add-in?
2. Does a maintainer's helper prompt rely on it as the source of a rule?
3. Does a person-facing guide or a modeller's skill tell someone to run it?
4. Would removing it break a module that stays?

Eleven passed all four. Six did not.

### Decision

1. **Retired, and their code removed:**

| Module | Agent | Why it is not needed |
|---|---|---|
| `brain/heron_architect.py` | `HERON-AHR-ARC-003` | Nothing called it; a new agent is scaffolded with `tools/new-agent.py` |
| `brain/heron_authoring.py` | `HERON-SKL-CRE-002` | Nothing called it; skills are written as cards in `brain/skills/` |
| `brain/heron_compatibility.py` | `HERON-IMP-CMP-008` | It judged what an *import* supports, and [D-25](D-25.md) rules imports out (the rest of that pipeline went in D-199). The `heron_compatibility` tool a chat calls is `heron_brain.compatibility()` over `heron_matrix.py`, not this file |
| `mcp/server/heron_discovery.py` | `HERON-MCP-DIS-012` | Nothing imported it; the server never read it |
| `brain/heron_observability.py` | `HERON-OPS-OBS-011` | Nothing called it; the latency the row asks for is measured by `tools/measure-brain.py` and `heron_gaps.py`, as the row already says |
| `brain/heron_performance.py` | `HERON-SKL-PRF-006` | Nothing called it |
| `brain/heron_regression.py` | `HERON-FRG-REG-006` | Nothing called it; a fragment is built on every release by `tools/check-fragments-compile.py` and proved by `tools/batch-prove.py` |
| `brain/heron_devperf.py` | none | It timed the suites against `check-gaps`' bound, and no tool, workflow, skill or guide ran it |
| `brain/heron_dependencies.py` | `HERON-INS-DEP-005` - **stays built** | Nothing called it. The installer's `platform/Heron.Installer/PythonSetup.cs` claims the same agent and is what sets up Python |
| `brain/heron_brain_init.py` | `HERON-INS-BRN-007` - **stays built** | The same: `PythonSetup.cs` claims it, and `tools/heron-ready.py` builds the knowledge store |
| `mcp/server/heron_install_health.py` | `HERON-INS-HLT-009` - **stays built** | The same: `PythonSetup.cs` claims it |

   Their own tests go with them, and the nine contracts in `brain/agents/` that described these modules. The three
   installer agents keep their rows as built; they now have no contract, which [`heron_agents.py`](../../brain/heron_agents.py)
   reports as backlog, not as a fault.

4. **Two kept suites changed only where they used removed code as an example:** `tests/test_new_agent.py`

### What is not known

Nothing here ran in Revit, and nothing a modeller uses changed: no removed file was reachable from the MCP server,
the add-in or the installer. A module loaded by a name built out of text no search would match would have been
missed; the full suites, run after the removal, are the check on that.
