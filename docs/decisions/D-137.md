### Context

D-135 point 3 put the Companion's notes in `<Path.GetTempPath()>\Heron\companion` on the add-in's side and in
the same folder, as `heron_bridge_client.temp_folder()` names it from TMP, TEMP and the profile, on the chat's.
It measured the temporary folder from Claude's shell and from the owner's terminal - never from inside Revit.

**Measured on the owner's laptop on 2026-10-18** ([row 5b-1100](../fragment-issues/section-5b-rows-401-425.md),
[HF4](../needs-checking/group-hf.md)): Revit 2024.3, started by the owner, runs with
`C:\Users\ajmal\AppData\Local\Temp\63835622-bdd8-4d57-a4a9-19a6afb83cd6` as its temporary folder - made one
second after it started, holding its own `revittemp_*` and `Rev*.tmp`. The button read an empty
`63835622-...\Heron\companion` and said no chat was running, while four chats' notes, 1 to 2 s old, were in
`C:\Users\ajmal\AppData\Local\Temp\Heron\companion`.

**The same fact twice before:** [row 5b-430](../fragment-issues/section-5b-rows-401-425.md) met it on 2026-10-11
(`6eeca6d4-9c31-4c58-8a52-334ff361b308`), and `create-family-forms` reads `%TEMP%\heron-work` beside Revit's
folder when that folder's name is a GUID; [DA8](../needs-checking/group-da.md) passed with that rule in Revit 2024.3
on the laptop on 2026-10-17, Revit's folder then `6d4c294e-0255-4e75-b39b-c9e7bd4a7520`. Three starts, three
names, each a hyphenated GUID directly under the user's own folder.

### Decision

1. **Both halves name `<the user's own temporary folder>\Heron\companion`**, and find the user's own folder
   by one rule, from the folder their process was given - `Path.GetTempPath()` in the add-in, `temp_folder()`
   in the chat: **that folder less its last part when that part is a GUID spelled as Revit spells it**, 8-4-4-4-12
   hex digits with hyphens, taken off once; any other folder as it is. `HeronPaths.UserTemp` and
   `heron_bridge_client.user_temp_folder()`.
2. **One pattern, in two files.** `HeronPaths.GuidName` and `heron_bridge_client.GUID_NAME` hold the same
   text, and `tests/test_data_home.py` reads it off both.
3. **`HeronPaths.SharedDerived` moves with it**, and `HeronPaths.Companion` is built on `SharedDerived`.
   Still DERIVED and safe to delete; `IsSafeToDelete` still refuses the temporary folder itself and Revit's
   own folder.
4. **Nothing else moves.** `temp_folder()` stays the mirror of `Path.GetTempPath()`; `HeronPaths.Derived`, the
   installers' download folders and the fragments' own `heron-work` rule are unchanged.

### Alternatives considered

- **The user's TEMP from the registry**, `Environment.GetEnvironmentVariable("TEMP",
  EnvironmentVariableTarget.User)` expanded, in the add-in. Rejected: it reads a different source from the
  chat's own TMP, so the two can part again - on a terminal server with a temporary folder per session every
  process is given `Temp\2` while the registry names `Temp` (reasoned, not measured); reading it on the chat's
  side as well means the registry from inside a Store Claude, which nobody has measured; and the value is a
  `REG_EXPAND_SZ` that can be absent, whose fallback would be `GetTempPath()` - the folder that failed. None of
  it could be measured from this session, which had no Windows.
- **`Guid.TryParse`, as `create-family-forms` does.** It takes any spelling of a GUID - braces, parentheses,
  32 bare digits, the hex-struct form - and the chat's side would need a reader that agrees with .NET on every
  one. Revit's folder has been seen three times, always hyphenated. The fragments keep their own rule: DA8
  passed on it, and changing their code would make it stale.
- **The add-in reading both folders**, its own and the parent. Rejected: the note is written to one folder by
  one side, and naming one folder is what makes the two halves agree; reading two hides a disagreement rather
  than removing it.
- **Taking off every GUID part, or spelling the user's folder from the profile.** Nothing measured nests
  deeper, and a typed `AppData\Local\Temp` is a guess about somebody's PC.
- **Back to `%LOCALAPPDATA%\Heron\companion`.** Row 5b-416 again on every Store Claude.

### Consequences

- **On the laptop**, an add-in built from this change looks in `C:\Users\ajmal\AppData\Local\Temp\Heron\companion`,
  where the chats' notes were on 2026-10-18. Reasoned from row 5b-1100's paths; **NOT RUN IN REVIT**.
- **Only the add-in has to move this time.** A chat on D-135's code already writes the user's own folder when
  it is given that folder, as every chat on the laptop was. The add-in must be rebuilt and deployed for every
  installed Revit - 2020, 2024, 2026 and 2027 on the laptop - before [HF4](../needs-checking/group-hf.md) and
  [BK14](../needs-checking/group-bk.md) are pressed again, in a Revit the owner starts; an add-in deployed before
  this fails as row 5b-1100 says.
- **A chat given a GUID-named folder of its own** writes in that folder's parent, as the add-in reads it.
  The same rule on both sides; no chat has been seen with one, so this is never measured.
- **A user whose own TEMP is a GUID-named folder** has its last part taken off on both sides, so the two still
  agree; the Companion's folder is then in its parent.
- **Not checked:** whether Revit 2020, 2026 and 2027 run with such a folder, and whether Revit does it on every
  PC. Where it does not, the rule leaves the folder as it is.
