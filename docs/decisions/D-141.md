### Context

Every request a chat sends Revit carries a `client` id, and the add-in's D-22 lease is held by it. That id
names a **person**, on purpose: `.mcp.json` sets `HERON_CLIENT_ID = "ajmal-pc"` for every server process,
because a chat that also ran Heron's command line was refused by its own lease (the comment above
`CLIENT_ID` in `heron_bridge_client.py` tells it). So the lease never told the owner's chats apart - and
everything the add-in kept for **one** chat was keyed on that same id:

- **The carried chain.** `RevitFragment` read `client` as the chat. A call without `expect_from` sends
  `"chain": "reset"`, and `Forget(client)` wiped **another chat's** carried elements.
- **The D-138 Keep grant.** `HeronKeepGrant.Decide`'s *"another chat"* branch could never fire, so a
  grant one chat was given kept another chat's changes - and the reply said *"from the same chat"*.
- **Nothing stopped two chats working one model at once.** The owner runs several chats against up to
  two Revits, each with several models.

He designed the answer himself, quoted above.

### Decision

1. **Every chat has its own name.** The request envelope gains `conversation`: a uuid the bridge
   client makes once per process - one per MCP server, so one per chat; one per command-line run. It
   is a reserved key, like `client`, so no operation argument can set it. `client` and the lease are
   unchanged. `HERON_CONVERSATION_ID` makes several processes one conversation: `tools/batch-prove.py`
   sets it for its jobs, and a person may set it for a series of commands. It is never set in
   `.mcp.json` or `.codex/config.toml`.
2. **A model is held by one chat at a time.** When a chat's request runs against a model - a read or a
   change - that model is held for that chat, and every request it sends there renews the hold. A
   request from **another** chat for a held model is refused **before anything runs**, with
   `model_in_use`: *"Model 'X' is in use by another chat. It is free when that chat says it is done,
   after 3 quiet minutes, or with Free this model on the Heron ribbon - at the latest in about N minutes
   from now. Nothing was sent to the model."* One chat may hold several models. The model is named by
   its key - `RevitOperations.DocumentKey`, its CreationGUID, path and title, the key the rollback
   witness and the grant already use - never by its title. The model held is the one the request runs
   against: the one it names, chosen as `RevitFragment.Run` chooses it, else the model in front. The
   claim is made in `RevitOperations.Run`, after the gate and before anything is routed; a request the
   switches refuse claims nothing. **Looking is not claiming**, the lease's own rule for `info`:
   `revit_health`'s count is sent `"claim": "no"`, refused like any request on another chat's model and
   holding nothing on a free one - so no value of it gets past a hold.
3. **What frees a model:** (a) `bridge.modelHoldMinutes` quiet minutes from the holding chat, **3** by
   default in `heron.config` on both sides - counted from the end of its last request, and it is what
   frees a chat closed or archived; (b) the chat saying it is done - `revit_release`, which sends
   `release_models` and frees **this chat's** hold on one model or on all of them, never another's;
   (c) the model closing; (d) Revit closing - holds live in memory only; (e) **Free this model** on
   the ribbon; and the bridge being disconnected from the ribbon, which clears them all, as it clears
   the lease. A command line hands back what it held when it ends, and `batch-prove` at the end of its
   batch.
4. **Free this model**, on the Heron tab beside Ask to Keep, frees the **active** model's hold at once,
   whoever holds it. It changes no element, so it opens no transaction and asks nothing; it announces
   nothing either - the add-in log says what it freed. Revit greys it on the start screen.
5. **The carried chain and the Keep grant are per chat.** `RevitFragment` keys both on the request's
   conversation. A request with **no** conversation - an older client - is a chat of **one request**
   (`HeronConversation.ChatOf`): what it carries ends with it, and it is never offered *"Keep, and keep
   the rest of this job without asking"*. On a model another chat holds it is refused, since it cannot
   be shown to be the holder; on a free model it runs as before and holds nothing.
6. **A refusal for a held model never ran.** `heron_failure` classes `model_in_use` as `NEVER_RAN`,
   `FIX_FIRST`, beside `session_in_use` and `revit_busy`: nothing changed, and it is safe to ask again
   once that chat is done.

### How it relates to D-22 and D-138

- **D-22 stays exactly as it is.** The lease is per Revit and per person, held by `client`; the owner's
  own chats share it, by the trade its comment records. The hold is per **model** and per
  **conversation**, and sits beside the lease, not in place of it: a second person on the same Revit is
  still refused by the lease first.
- **D-138's grant becomes per chat**, which is what its item 2 and Article 9 always said - *"that chat's
  next changes to that model"* - and what the code could not do while the chat's id was the person's.

### What this does NOT change

- **Revit's main thread still runs one step at a time** (D-09, docs/25 §6). The hold decides who may
  ask; it does not make two jobs run together.
- **The pin and the session binding** - Golden Rule 20, Article 12a - are the chat's own, in its
  server, as before. A chat bound to a Revit whose model in front another chat holds is still bound;
  only that model is refused until it is free.
- **Write permission.** `write.enabled` still defaults to `false`; the hold refuses, it never allows.

### What it accepts

- **A chat that used the Heron tools, then ran Heron's command line on the same model, is two
  conversations,** and the command line is refused for up to three minutes. `revit_release` or Free
  this model frees it at once; the [`fragment-proving`](../../.claude/skills/fragment-proving/SKILL.md)
  skill and the [`heron-fragment-author`](../../.claude/agents/heron-fragment-author.md) agent say so.
  NEEDS-CHECKING HG7, which used `HERON_CLIENT_ID` to make a command line *"the same chat"*, cannot
  do that any more - Group HK notes it.
- **A chain carried between two hand-run commands** needs `HERON_CONVERSATION_ID` set for both, as the
  lease once needed `HERON_CLIENT_ID`.
- **A Save As, or a model's first save, changes its key**, so its hold ends there and the next request
  claims it afresh - the same edge D-138 accepted for the grant.
- **An older client keeps working** on a free model and is refused on a held one; it is never given a
  grant. A running chat keeps the Python it started with (mcp/README rule 5), so a chat opened before
  this change is such a client until it is reopened.
- **The quiet time is the PC's clock.** One put back restarts a hold's three minutes rather than
  stretching them.

### Alternatives considered

- **Make the lease per chat** - give each chat its own `HERON_CLIENT_ID`. Two chats on one Revit would
  then refuse each other outright, even on different models, which is the opposite of the owner's
  design; and it undoes the trade D-22's comment records.
- **A queue for a held model.** docs/25 §3 rejected a queue for the lease and the reason holds: an
  invisible queue runs a command minutes later against a model that has since changed.
- **Free a model when the chat closes.** A closed chat sends nothing to say so; three quiet minutes is
  the honest signal, and the owner's design names it.
- **Key the hold on the model's title.** Two open models can share one; the key the add-in already
  uses for the grant cannot.

### Consequences

- Nothing here has run in Revit. It compiles for 2020 to 2027; the rule is run without Revit by

  wiring as text. [NEEDS-CHECKING Group HK](../needs-checking/group-hk.md) holds the runs that would prove
  it, and the owner says when they are run.
- [docs/25 §3](../25-multi-session-and-binding.md) carried *"one chat, one Revit"* and *"per process, not
  per document"* as the whole rule; it now says where the model hold sits beside them.
