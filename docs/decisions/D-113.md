### Context

Everything Heron keeps for a project - its governing standards (D-111), its load runs, its sprinkler runs,
its project index - was filed under the UniqueId of the model's **Project Information** element, which the
add-in sends as `projectKey`. The review of 2026-09-11 chose it believing that element is created with the
document. **It is created with the TEMPLATE**, and a new project inherits it, UniqueId and all:

- 2026-09-15 ([NEEDS-CHECKING E12](../needs-checking/group-e.md)): two blank projects and an unrelated
  `PIPE.rvt` in Revit 2020 all reported `8764c510-57b7-44c3-bddf-266d86c26380-0000c160`. That finding moved
  the WRITE path off the key ([D-74](D-74.md)); the knowledge stores kept it.
- 2026-10-06 (row 5b-324): `Heron loads test`, a new project from Revit 2024's default template, reported
  the same id. `revit_building_loads` asked no question at all and used the design weather, set points,
  `Office` profile and door absorptance Project2 had been given on 2026-10-05 - and a `beyond:352541`
  answer naming an element that exists only in Project2. The owner saw a `Reception` row in a model with no
  Reception.

### What was measured, and how

**In Revit 2024, session 51820, read only** (a no-transaction run, nothing written): on `Heron loads test`,
`Document.CreationGUID` is `c95db604-0abd-4bc5-9ebd-3ece37b3ce52` while its Project Information UniqueId
is the shared one. It was the only model open; the owner was not asked to open more.

**From the saved files on disk, read only, no Revit:** the same GUID heads the `Global/History` stream of
`Heron loads test.rvt` (byte 22, little-endian), so it can be read from a file. Across the owner's own
projects:

| What | Files | Result |
|---|---|---|
| His saved projects made from that template - each holds the template's Project Information episode `8764c510-...` in its history | 18 | **18 different** creation ids |
| Copies of ONE model: Revit 2024's *Snowdon Towers Sample HVAC*, three copies of it under other names, a workshared central made from it (`Snowdon-scratch`), that central's local copy and the local copy's backup | 7 | **one** id, `76d8f96a-...` |
| Two more files and their `_ajmal.al` local copies (`Project1`, `Project1 work`) | 2 pairs | each local copy carries its own file's id, and the two pairs differ |

`Document.CreationGUID` arrived at **Revit 2024** (the [revit-version-support](../../.claude/skills/revit-version-support/SKILL.md)
skill's table, from the shipped `RevitAPI.dll`; on this PC 2020's has no such member, 2024's and 2027's do).
Nothing read-only identifies a model on 2020 to 2023: the Project Information UniqueId is the template's,
the path changes on Save As, and `Document.GetDocumentVersion` changes on every save.

### Decision

1. **A project's kept answers are filed under the model's own id, `Document.CreationGUID`.** The add-in reads
   it by reflection (`RevitOperations.CreationGuid`) so one build still serves 2020 to 2027, and sends it as
   `creationGuid` on every reply that carries `projectKey`. `DocumentPin.project_key` is that id.
2. **On Revit 2020 to 2023, and with an add-in older than this, nothing is kept for the model.** It reports
   only its template's id, and keeping answers there is the defect. Each answer says so in words, and what
   the modeller gives serves that answer only.
3. **The pin compares the model's own id where it compared the template's.** A chat pinned to one
   template-born model refuses a reply from another, instead of taking its name. The template's id is kept
   as a refusal only: the same one proves nothing, but two DIFFERENT ones cannot be one model.
4. **The template's id stays on the wire and on the pin, by its own name** (`project_information_id`): the
   add-in's `expectProject` guard compares it, and answers kept before this decision are found by it.
5. **Answers kept under the template's id are a QUESTION, never a match.** While any are kept and the open
   model has not answered, every answer that would have used them - building loads, sprinkler hydraulics,
   HVAC, fire - begins with what is kept, grouped by the model name each was given for, and that none of it
   was used - and so does a standards or research answer asked of the project scope. The modeller names a
   model, or says none, through `heron_earlier_answers`. On a name, what was given under that name is COPIED
   to this model's own files; nothing under the template's id is moved, rewritten or deleted, a file the
   model already has is never overwritten, and a copy that fails part way is taken back whole. A kept file
   not in the shape Heron writes is passed over, never a crash. Each model answers once.

### What it accepts

- **A copy of a model keeps its id**, by measurement: copies under other names, a central made from it and a
  local copy all carry the original's. That is what was wanted - answers follow the model. It also means a
  model copied to START A DIFFERENT JOB carries the first job's answers. Revit itself cannot tell that copy
  from a Save As, and neither can Heron; the modeller changes an answer by saying it again (D-111 item 5).
- **Two copies of one model open at once are one model to the pin**, as they were before. A write is aimed
  at the pinned path (D-74), so it still lands in the file the chat was pointed at.
- **Revit 2020 to 2023 keep nothing between answers.** The smallest way to give them a key is a Heron stamp
  written once into the model - a change to the owner's model, so it is his to decide and is not built.
- **The add-in's `expectProject` guard and `RevitWrite`'s preview key still compare the template's id.** D-74
  made neither load-bearing; both stay as they were and row 5b-324 says so.

### Consequences

- **Easy:** two models made from one template no longer share standards, load answers or sprinkler answers,
  and the answers already given are not lost - they are offered.
- **Owed:** the add-in rebuilt, deployed and Revit restarted, then [NEEDS-CHECKING Group CG](../needs-checking/group-cg.md)
  on the owner's PC: the same model read again, the question seen, an answer given, and a second model made
  from the same template kept apart. Until then this is built and tested without Revit, not proven.
