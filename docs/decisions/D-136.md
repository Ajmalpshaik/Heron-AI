### Context

D-135 point 3 put the Companion's notes in the temporary folder and named that folder, on both sides, the way
.NET's `Path.GetTempPath()` does - TMP, then TEMP. It measured the folder from Claude's shell and from the
owner's terminal, never from inside Revit. On 2026-10-18 [HF4](../needs-checking/group-hf.md) pressed the
Companion button in Revit 2024.3 on the owner's laptop, and it said no chat was running while four were:
Revit runs with a temporary folder of its own, `C:\Users\ajmal\AppData\Local\Temp\63835622-bdd8-4d57-a4a9-19a6afb83cd6`,
made one second after it started, and the add-in read `<that>\Heron\companion`, empty, while the chats' notes
sat in `C:\Users\ajmal\AppData\Local\Temp\Heron\companion`. [Row 430](../fragment-issues/section-5b-rows-401-425.md)
had met the same kind of folder on the same laptop on 2026-10-11, and `create-family-forms` reads beside it for
that reason.

Row 5b-1100 named two ways to find one folder from inside Revit: the user's own TEMP as Windows stores it,
`Environment.GetEnvironmentVariable("TEMP", EnvironmentVariableTarget.User)`, or `GetTempPath()`'s parent when its
last part is a GUID.

### Decision

1. **Both halves name the folder by one rule:** the temporary folder as `GetTempPath()` names it, stepped out of
   for as long as its last part is named like a GUID - 8-4-4-4-12 hex digits with their hyphens, in either case,
   the form Revit's has. A folder not named so is used as it is, exactly as under D-135.
2. **The add-in** applies it in `HeronPaths.SharedTemp`, private, which `SharedDerived` and `Companion` are built
   on. `Companion` is `<SharedTemp>\Heron\companion`, still DERIVED and still safe to delete.
3. **The chat** applies it in `heron_bridge_client.shared_temp_folder()`, the same rule on `temp_folder()`, and
   `heron_companion.companion_dir()` uses it. `temp_folder()` keeps its meaning: `GetTempPath()`'s, mirrored.
4. **Every GUID-named level, not one,** so the two still agree on a PC whose own temporary folder is named like a
   GUID, and when a chat's own TMP is Revit-style.

### Alternatives considered

- **The user's own TEMP, read from where Windows stores it** (`EnvironmentVariableTarget.User`). Not chosen:
  - On a Remote Desktop server Windows gives each session a numbered temporary folder, `Temp\2`, in every
    process's environment, the chat's included, while the stored value still names `Temp` - so the add-in would
    read `Temp\Heron\companion` and the chat write `Temp\2\Heron\companion`. Reasoned, not measured: no such
    server was at hand.
  - The chat would have to read the same stored value to agree, and what a Store Claude's child reads there was
    never measured - its `%LOCALAPPDATA%` was found redirected ([row 5b-416](../fragment-issues/section-5b-rows-401-425.md)).
  - It is empty where TEMP is set only for the machine or by policy, so it needs a fallback anyway; and it can be
    run only on Windows, while the rule chosen runs in both suites anywhere.
- **The parent, one level only.** Splits the two again on a PC whose own temporary folder is named like a GUID.
- **Any GUID spelling .NET's `Guid.TryParse` reads,** as `create-family-forms` does for its own check. Python's
  `uuid` reads a different set, so the two halves could disagree on a folder in braces or without hyphens; the one
  written form is the one Revit makes.
- **The add-in reading both folders.** Mends the button, not the rule: each half would still name a folder of its
  own, and the next reader of `HeronPaths.Companion` would meet row 5b-1100 again.

### Consequences

- **It is a rule about a folder's NAME, not a promise from Autodesk.** Seen on Revit 2024.3 on one laptop; not
  checked on 2020, 2026 or 2027, or on another PC. A release that names its folder otherwise, or nests it under a
  name that is not a GUID, makes the button fail as row 5b-1100 did, and the re-press is what says so.
- **Both halves must be updated together again.** An add-in built before this reads Revit's own folder and finds
  nothing. The add-in rebuilt and deployed for each release, then [HF4](../needs-checking/group-hf.md) and
  [BK14](../needs-checking/group-bk.md) pressed in a Revit the owner starts, are owed.
- **Where D-135's rule already gave one folder** - a temporary folder with no GUID at its end, on both sides -
  nothing moves: both rules name the same folder.
- **`IsSafeToDelete`** still refuses the temporary folder itself and Revit's own; it answers yes only under
  `<SharedTemp>\Heron`.
- **Checked without Revit.** `tests/Heron.Kernel.TestHost` section 2 and `tests/test_data_home.py` section 6
  plant a Revit-style TMP, TEMP and TMPDIR; each FAILED on the code before and passes on this. Compiled for 2020
  to 2027; never run in Revit.
