### Context

Constitution Article 7 asks for explicit confirmation before deleting elements. Nothing in code asked
([row 5b-161](../fragment-issues/section-5b-rows-151-175.md)): the add-in's gate reads one risk per operation,
`run_fragment_write` is `MODIFY`, and `DELETE_ELEMENTS` is a `MODIFY` card. So *"delete these"* - a phrasing
the PROVEN card declares - ran on the live selection through the words-only path in the same call, and with
Ask to Keep off, its default since D-138, or under D-138's *keep the rest of this job*, it was kept with no box
at all. What stood for Article 7 was a sentence in every chat's instructions, which a model can be argued out
of. D-126 had said so in as many words: its box *"is not the yes Article 7 asks for before deleting"*.

The owner decided it on 2026-10-18. Typing *delete* is the instruction, and that is fine; but nothing leaves
the model without the box, Ask to Keep on or off - how many elements, and Delete or not.

### Decision

1. **The gate is in the add-in, and it measures.** On the write path, after the fragment ran inside its
   `TransactionGroup` and the change is described, and before D-138's grant or D-126's box is looked at
   (`RevitFragment.DeleteGate`), a run that would KEEP - `apply`, or a DRAFT's one run (`ask`) - in which
   Revit's own `DocumentChanged` counted ANY element deleted is asked. Whatever `write.askBeforeKeeping`
   says; never covered by the grant; through every door - `revit_change`, the words alone, the command
   line's `--write --apply`, `try-once`. **What Revit deletes along with what it was told to counts the
   same** - a wall's doors, a duct's fittings - because the count is Revit's (`RevitChangedSet.DeletedIds`),
   never a card's. No card field decides it. An element the same run added and deleted again is no deletion.
2. **Measured, rolled back, shown, asked, run again.** A deleted element cannot be seen inside an open group,
   so the first run is rolled back (`RollBackAndCheck`) and every deleted element is found in the model
   again. Each one's category is read, and what it goes with - an element Revit lists as dependent on another
   that goes (`Element.GetDependentElements`, up to 500 elements). The ones that can be shown are **selected
   and zoomed to** in the model in front - no transaction, so nothing reaches the undo list. On **Delete** the
   same run is made again, setup steps and all, from a new group of its own - one copy of the run, reached by
   a `goto` in `Run` - and **kept only if it deletes exactly the set shown**
   (`HeronDeleteQuestion.Differs`); otherwise it is rolled back too and refused, `delete_set_changed`.
3. **The box.** Its title is *"Delete N elements?"*, its large line *"Delete N elements from <model>?"*. It
   quotes the chat's own words (`chatWords`, sent by `revit_change`, shown and obeyed by nothing - absent,
   it names the capability), gives the total N with what goes along, grouped by category with counts and
   *"(goes with the ...)"* where Revit removes one only because another goes, counts what the same change
   adds and changes, says what is on screen, and lists the element ids in its *more* half. Two links,
   **Delete** and **Don't delete**; Don't delete is the default; **there is no third link**. It is shown
   inside `HeronDialogWatch.HeronAsks()`, so the job's dialog watch never answers it.
4. **No answer in time deletes nothing.** Esc, the close button and Don't delete are no. The dispatcher
   sets the last moment a Delete is kept when it creates the job - `revit.askTimeoutSeconds` from then
   (`RevitJob.AnswerBy`) - and it waits at least a whole operation timeout beyond that once a box is up,
   so the second run's answer still reaches the chat. A Delete pressed after it, or after the caller has
   stopped waiting, deletes nothing (`delete_too_late`), and the box says by when, *"Answer by HH:MM"*. A
   caller that stops waiting on the box is told *nothing is deleted now* (`awaiting_delete_answer`). The
   second run's run clock starts again (`HeronRunClock.Again`).
5. **One question for one change.** A delete the modeller confirmed is not asked Keep or Discard as well,
   and is never reported *kept without asking*, grant or not; the grant's own bookkeeping is unchanged. A
   DRAFT's one run is still asked Keep or Discard after it - its Keep is its proof's positive case (D-119).
6. **Refused rather than asked, three times.** An export, save or sync that also deletes (`delete_in_publish`):
   showing it first would send it out twice. A first run whose rollback cannot be confirmed, or whose deleted
   elements do not all come back (`delete_not_shown` - the model may still be without them, so the chat is
   told to look). And a run whose change report never reached Heron while the model now holds fewer elements
   than before (`delete_not_measured`) - the one delete Revit's count cannot answer.
7. **The chat is told.** A kept change that was asked carries `deleteAsked`, `deleteShown`, `deleteSelected`,
   `deleteAnswer` and `deleteAsking` - *"The modeller was asked in Revit whether to delete N elements - listed
   by category, M of them selected on screen - and pressed DELETE."* - and `revit_change` prints that
   sentence first, beside D-126's `asking` (row 5b-1093's rule). A no is a refusal whose message says who
   chose and that NOTHING WAS DELETED; `delete_declined` is never retried (Article 25).
8. **The server waits long enough.** `fragment_timeout(keeping=True)` adds `revit.askTimeoutSeconds` on
   every keep, whatever the server's own copy of `heron.config` says about Ask to Keep. It added it only
   while that copy said on, and a forced box with Ask to Keep off would have outlived the wait.

### What this does NOT change

- **Article 7's other cases** - purging, bulk parameter writes, family reloads, workset changes, anything
  touching a link - are still the chat's to ask about first, as before.
- **The chat's own instructions are not changed here.** `host.chat` and `revit_change`'s description still
  say Article 7's yes comes before the call for destructive work. With the box in Revit that is a second
  question for a delete, and the owner's *"when I type delete, it means delete"* reads as asking for one; it
  is left for the owner to accept as its own change, not done on a reading.
- **A preview is never asked.** A run that rolls back - every proof, `tools/batch-prove.py` never sends
  `apply` - deletes nothing whatever anybody answers.
- **`revit_apply_move` keeps its own preview** - it deletes nothing. Nothing outside a fragment deletes an
  element: `grep -n "\.Delete(" revit/` finds only files.
- **`HeronKeepGrant.cs` is unchanged.** The rule that a grant never covers a delete is at the call site.
- **Nothing is widened.** `write.enabled` defaults to `false`; every switch decides what it decided.

### What it accepts

- **A change that deletes runs twice.** Revit does the work twice, setup steps included, and a run whose
  outcome depends on something outside the model can delete a different set the second time - then nothing
  is deleted, and the chat is told why. Never the wrong set.
- **Every PROVEN capability that deletes as part of its work now shows the box.** Read from their code on
  2026-10-18 (`.Delete(` in each `fragment.cs`): `DELETE_ELEMENTS`, `REMOVE_TAGS`, `REMOVE_VIEW_FILTER`
  (the filter, when nothing else uses it), `UPDATE_SAVED_SET` (the set it replaces), `SET_MEP_INSULATION`
  (insulation it replaces), `SET_SHEET_TITLE_BLOCK` (the title block it replaces), `FILLET_LINES` (the two
  lines it joins) and `COMBINE_FAMILY_FORMS` (the forms combined into one). `CREATE_FAMILY_BLEND` and
  `TAG_ROOMS` delete only what the same run made, which is no deletion, so they should not. And any change
  in which Revit deletes elements by itself - a dependant of something changed - shows it too.
- **With Ask to Keep on, a change that deletes is asked once, by the delete box.** What the same change adds
  is counted in the box, never shown before it is kept; Ctrl+Z still takes the whole change back as one step.
- **The gate is as good as Revit's report of the change.** It arrived on Revit 2024 and 2027
  ([EV1](../needs-checking/group-ev.md)); 2020 has not been measured. If it never arrives, the model's element
  count catches a delete - but not one that adds as many elements as it removes.
- **Asking Revit what goes with what, with no transaction open, is not measured.** An element it will not
  answer for is listed as going in its own right; the count is Revit's either way.
- **A DRAFT that deletes is asked twice** - Delete, then Keep or Discard - and the second box has less than
  an operation timeout before Heron stops waiting, when the first took most of the ask time.
- **The box cannot close itself.** A TaskDialog has no timeout; after the deadline it stays up until it is
  answered, and every answer then is no.
- **The answer window is up to the busy wait shorter than the Keep or Discard box's**, counted from when the
  request reached Revit rather than when Revit took it - the safe side.

### Alternatives considered

- **Ask with the change still in the open group.** One run, nothing to run twice - and nothing to see: the
  deleted elements are gone inside the group, and their categories cannot be read. Kept as the fallback the
  task named, not needed once the second run fitted in one change.
- **A `destructive:` field on the card, read by the server.** Row 5b-161's first idea. It misses what Revit
  deletes along with what it was told to, and every card that forgets the field. A measurement cannot forget.
- **Isolate them, as D-126's box does.** After the rollback no group is open, so an isolate would be an undo
  entry of its own, or need a group just for showing. Selecting and zooming change no model.
- **Ask in the chat.** The chat cannot show the elements and does not know what goes along with them.
- **Let a job's grant cover a delete.** The owner: *"in any situation"*.
