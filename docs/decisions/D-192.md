### Context

Every write opened Heron's `TransactionGroup` in the model it was aimed at, whatever the job did there.
Two jobs change nothing in that model, and were hurt by the group all the same:

- **A new family** ([row 5b-1912](https://github.com/Ajmalpshaik/Heron-AI/issues/1121)). On 2026-11-19, Revit
  2020, `CREATE_FAMILY_DOCUMENT` opened Heron's group in the real project the chat was pinned to while the
  modeller worked in a scratch model. Revit counted no change there, but a write was opened in a model nobody
  chose for the job - and with the model in front modifiable, Revit would not open the new family's window,
  so the card saved it and named `ACTIVATE_DOCUMENT` as a second step.
- **An export of families** (rows [21](../fragment-issues/section-5-rows-001-025.md),
  [5b-1407 and 5b-1411](../fragment-issues/section-5b-rows-1401-1425.md)). `EXPORT_FAMILIES` opens each family
  with `EditFamily`, which Revit refuses while a transaction is open in the project. Inside Heron's group every
  family came back *"Revit refused to open it for editing"*, on Revit 2020 and 2024.

### Decision

1. **`noGroupOpen` (bool, ambient) says "I work only outside the model I am aimed at, and change nothing in
   it".** The add-in binds it `true`; the fragment never reads it.
2. **Only an Admin or a Publish job may declare it.** A change to the model is one named group, whatever else
   it does (Article 8): a card sent as a change, or one that also declares `editScopeFailures`, is refused
   `bad_contract` before anything runs. On the read and show paths it changes nothing - no group is open there.
3. **Such a job runs with no `TransactionGroup` in that model, MEASURED as a read is** (row 5b-350): the model
   counted before and after, every transaction Revit commits in it heard, and the job refused
   `changed_outside_group` - OUTCOME UNKNOWN, look at the model - if it moved, or if a transaction was left
   open. It opens no transaction of its own: the source scan holds it to that, as it holds
   `noTransactionOpen`. A stop, the run guard and a Revit dialog refuse it as on the read path.
4. **None of the group's machinery runs**, because there is nothing in the model to keep, discard or roll back:
   no Keep or Discard box, no delete box, no grant, no rollback check, and no undo entry made or watched.
5. **Its verdict says what is true.** With `apply`: `verdictKind` *kept*, no undo entry, and what it did
   outside done. Without `apply` - only a proving tool sends that, D-155 keeps it from a chat - row 5b-1594's
   shape: `rolledBack` true means the model is as it was **by count**, `rollbackReported` false, and
   `outsideStands` true. `ranOutsideTheModel` true on both, and the proving client writes *"run with NO
   transaction group open"*, never *"run inside a transaction"*.
6. **The first two cards are `CREATE_FAMILY_DOCUMENT` (version 4) and `EXPORT_FAMILIES` (version 2).** Neither's
   C# moved. `CREATE_FAMILY_DOCUMENT`'s proof stands, as `OPEN_VIEW`'s did under D-125: its positive case was
   the branch that opens the family in a window in the same call, and that is the branch every run takes now.
   `EXPORT_FAMILIES` stays DRAFT until proved.

### Alternatives considered

- **Drop the group for every `noTransactionOpen` card.** The three that declare it are EXECUTE and run
  through the show door, where no group is open anyway; on the write path the group is D-125's own rule.
  Widening it would change an accepted decision for cards that gain nothing.
- **A posted Revit command, read back by a separate read.** D-185 chose the modeller's own click for Reload
  Latest and Sync; nothing here needs Revit's UI.
- **Leave it to the owner first.** The issue said *a decision first*; the owner was asleep and asked for the
  work to go on. The route is opt-in per card, so taking the need off a card undoes it without touching C#.

### Consequences

- A family started from a chat opens no write in the pinned project, and opens in a window in one call.
- `EXPORT_FAMILIES` can reach `EditFamily`, so its proof can be tried again.
- **An add-in built before this refuses both cards** (`needs_unbound` - a need it cannot bind) until
  `python tools/heron-ready.py` rebuilds it and Revit is restarted. Nothing is changed by that refusal.
- **Not run in Revit.** NEEDS-CHECKING [Group OX](../needs-checking/group-ox.md) owes it.
