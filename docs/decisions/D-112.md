# D-112 — A fragment that must work in one of Revit's edit modes opens its own transactions inside Heron's group

> One record of [the decision log](../DECISIONS.md). Decisions are append-only: to change one, write a
> new decision that supersedes it.

**Status:** Proposed · **Date:** 2026-10-03 · **Source:** the school in Project2, 2026-10-03: *"make the stair also"*, and Revit refusing a stair inside Heron's transaction, measured the same day
**Keeps:** Golden Rule 16 - one TransactionGroup, one undo, rolled back on a preview · the read path's guarantee that nothing there can open a transaction
**Affects:** [`RevitFragment.cs`](../../revit/Heron.Revit.Addin/RevitFragment.cs), [`heron_fragment.py`](../../brain/heron_fragment.py) (`AMBIENT`), [`check-revit-gate.py`](../../tools/check-revit-gate.py), `create-stairs`

### Context

A Revit stair is made only inside a `StairsEditScope`, and Revit's own remark on `StairsEditScope.Start`
says it *"can only be started when there is no transaction active"*. Every write fragment runs inside the
one `Transaction` the add-in opens for it. **Measured 2026-10-03 on Project2, Revit 2024, session 41260**,
rolled back: inside that transaction `IsPermitted` read `False` and `Start` threw *"not permitted to start
at this moment ... the document is currently modifiable"*. So no fragment, written any way at all, could
make a stair. The same wall stands in front of `SketchEditScope` (row 5b-264).

### Decision

1. **A fragment declares the ambient need `editScopeFailures` (`IFailuresPreprocessor`)** when it has to
   work in one of Revit's edit modes. The declaration is the switch; nothing else turns it on.
2. **On the write path such a fragment runs inside Heron's TransactionGroup with no transaction of
   Heron's open.** It opens its own edit scope and its own transactions, and gives every one of them the
   `editScopeFailures` object - the same failure discipline Heron's own transaction carries - so what
   Revit says still reaches the verdict.
3. **The group is unchanged.** A preview rolls the whole job back and `apply` assimilates it into one undo
   entry, so Golden Rule 16 holds: the edit scope is a group inside Heron's group.
4. **Never on the read path.** A fragment declaring the need is refused there before anything runs,
   because that path's guarantee is that Revit refuses every change for want of a transaction.
5. **A transaction left open is named, not kept.** If the fragment returns with the document still
   modifiable, the run is refused and the modeller is told to Undo and look.

### What it accepts

A fragment of this kind writes the transactions the rest of the library is forbidden to write, so
`check-revit-gate.py` answers it BY DESIGN only when the need is declared. Whether a `StairsEditScope`
starts inside a TransactionGroup is Revit's to answer and has **not been measured** - the add-in that
carries this has not been in a Revit yet.
