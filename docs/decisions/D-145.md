# D-145 — A card may let its caller answer one named Revit dialog, for one job, and every other dialog is still declined

> new decision that supersedes it.

**Status:** Proposed · **Date:** 2026-10-19 · the owner has not read this back; it is what the 2026-10-19 task asked for, written down so it can be accepted or overturned
**Keeps:** Article 7 of the [Constitution](../../HERON_CONSTITUTION.md) - Heron still answers no dialog for the owner; the caller does, in words they typed
**Affects:** [`HeronDialogNote.cs`](../../revit/Heron.Revit.Addin/HeronDialogNote.cs) (`HeronDialogRule.CallerAnswer`), [`HeronDialogWatch.cs`](../../revit/Heron.Revit.Addin/HeronDialogWatch.cs) (`AnswerForJob`), [`RevitFragment.cs`](../../revit/Heron.Revit.Addin/RevitFragment.cs) (a need's `dialog:`), [`set-parameter-values-by-id`](../../brain/fragments/set-parameter-values-by-id/fragment.yaml) version 5, [`test_dialog_note.py`](../../tests/test_dialog_note.py), [row 5b-1221](../fragment-issues/section-5b-rows-401-425.md), [Group HP](../needs-checking/group-hp.md)

### Context

Every Revit dialog that opens inside a Heron job is declined - Cancel, then Close - and the job is rolled
back, unless a row of `HeronDialogRule` with a recorded run says otherwise ([row 5b-300](../fragment-issues/section-5b-rows-276-300.md)).
That is right for a question whose answer is the owner's, and nobody is there to give it.

On 2026-10-19, on Revit 2020 and the model *Kerala house design*, renaming `Level 1` to `Ground Floor`
through `SET_PARAMETER_VALUES_BY_ID` met Revit's `TaskDialog_Confirm_Level_Rename` - *"Would you like to
rename corresponding views?"* - and was rolled back every time ([row 5b-1221](../fragment-issues/section-5b-rows-401-425.md)).
So Heron could not rename a level at all. The question has two right answers, and which is wanted is
known to the person asking - it is not a choice Heron should make, and not one a fixed table row can make
for every job either.

### Decision

1. **A card may declare, on one request-sourced need, `dialog: <DialogId>`.** The value the caller sends
   for that need is their answer to that one dialog.
2. **Which dialogs a caller may answer, and with which words, is a closed list in the add-in** -
   `HeronDialogRule.CallerAnswer`. Each entry names the run in which Revit reported its id. A card naming
   an id not on the list, or a caller's word the entry does not take, is refused before the job runs, so
   no card can declare its way past the decline. The list holds one entry: `TaskDialog_Confirm_Level_Rename`,
   with `yes` and `no`.
3. **The answer lives for one job.** `HeronDialogWatch.AnswerForJob` keeps it only while a job is armed,
   and `Arm`, `Disarm` and `Detach` clear it. It is given to that DialogId alone.
4. **Left out - the card's `absent: none` - the default stands**: the dialog is declined and the job
   stops. Every other dialog, in every job, is still declined.
5. **Revit refusing the caller's answer stops the job** as for any dialog Heron could not answer.
6. **A table row of `HeronDialogRule` stays the owner's decision with a recorded run** - this does not
   loosen `Problem()`. A caller's answer is a different thing: the caller made it.

### Consequences

- `SET_PARAMETER_VALUES_BY_ID` version 5 takes `renameViews=yes|no`. Left out, a level's name is refused
  by the fragment before anything is written, naming the input - clearer than a rollback that quotes
  Revit's question.
- The card is DRAFT until [Group HP](../needs-checking/group-hp.md) is run on Revit and signed.
- **Not established:** that Revit takes Yes or No through `OverrideResult` for this dialog inside a
  transaction, and what each does to the views. Group HP asks both.
