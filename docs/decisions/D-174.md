### Context

A proof records which Heron add-in and which Revit build it was taken on - `built_on:`, beside the
fingerprint: Revit's release and exact build, and the add-in's version and a hash of its file. When either
moves, the proof is stale for that build. Q-92 asked whether a change from such a fragment should still be
kept from a chat, or refused until it is proved again on the new build. Every add-in rebuild changes the
file's hash, even when nothing a fragment uses moved, so a refusal would stop every proven change that
recorded a build after each update.

### Decision

1. **A proof taken on another add-in build or another Revit build of the same release is SAID, never
   refused.** `revit_read`, `revit_show` and `revit_change` add one line under the answer naming what it was
   proved on and what changed; `heron_validate.py draft` says it on its `build:` line.
2. **D-117 is unchanged.** A change is refused only when the card is not PROVEN or PRODUCTION, or its proof no
   longer describes its code - D-30's fingerprint, read from the card alone. `proof_is_stale` does not read
   `built_on`.
3. **A proof that records no build is NOT RECORDED** - every proof signed before `built_on` - and adds no
   line: never stale, never current, never re-stamped.
4. **Re-proving on the new build is how the line goes away:** a run there, drafted and signed with `accept`.

### Alternatives considered

- **Refuse a kept change until it is proved again on the new build** (Q-92 shape 2). Every add-in update would
  stop every proven change that recorded a build, though most rebuilds move nothing a fragment uses.
- **Refuse only when Revit's build moved** (shape 3). Two rules to explain, and an add-in change that matters
  is still only flagged.

### Consequences

- After an add-in update or a Revit update, a proven change still runs from a chat, and the line under its
  answer says it has not been checked on this build. The modeller judges it, as with any answer.
- Nothing of it has run in Revit: [NEEDS-CHECKING Group OF](../needs-checking/group-of.md) is the check on the
  owner's PC.
