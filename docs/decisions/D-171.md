### Context

Twice in two days a whole build was lost because the model had never been saved and Revit was closed - a
house with 9 sheets and a 32-floor tower, on 2026-10-13 and 2026-10-14
([row 5b-513](../fragment-issues/section-5b-rows-401-425.md)). Heron could not have saved either:
`SAVE_DOCUMENT` version 2 saves only another open document that already has a file, and refuses the one
Heron works in by name. Revit saves nothing while any transaction, sub-transaction or transaction group the
API opened is still open, and every fragment `revit_change` runs is inside the one `TransactionGroup` the
add-in opens for the request - Article 8's one undo entry - so a fragment can never save the document it runs
in, however it is written. After that group has closed, nothing of Heron's is open and Revit's remarks allow
a save: read from the code, **not run** ([Q-69](../open-questions/tier-2.md)).

### Decision

1. **The add-in saves on the fragment's behalf, after Heron's group has closed.** `SAVE_DOCUMENT` version 3
   asks for it - the document it works in, by its own file for a Save, or by a full `.rvt` or `.rfa` path for
   a Save As of a model that has none - and the add-in does it once the group has been assimilated or rolled
   back, before the reply is built, and puts what happened at the end of the reply.
2. **Only when the modeller asks.** Never on Heron's own initiative, and never a step a method adds unasked
   (Article 10).
3. **Heron never picks a name.** A Save As takes the full path the modeller typed.
   `SaveAsOptions.OverwriteExistingFile` stays at Revit's own default, false, unless the modeller said to
   replace that file.
4. **Behind the Publish switch**, as version 2's save is.
5. **The group does not change.** One request, one `TransactionGroup`, one undo entry; the save is not in it,
   because a save is not a model change and cannot be undone. Where Revit asks Keep or Discard
   ([D-126](../decisions/D-126.md)), the box is answered inside the group, before the save, so a save there
   follows only a Keep.
6. **The two choices Q-69's shape 2 carries:**
   - **A preview saves too**, as version 2's save of another document already does. It is the only way the
     route can be proved while D-117 refuses a DRAFT kept for real, so D-55's *"the preview is the run itself,
     rolled back"* gains one sentence: a save asked for with the run is not rolled back.
   - **The pin follows a rename only when the reply says this run did the Save As of the pinned document.**
     On Revit 2020 to 2023, and for a family on any release, a model's own id is null and a never-saved model
     has no path, so without this the next call would be refused as aimed at another model.
7. **Read back by the shape's name.** The suggestion the owner answered named the save after the group, the
   modeller's ask and no name chosen; the two choices in point 6 are shape 2's own words in Q-69, accepted with
   it, and are his to overturn like the rest.

### Alternatives considered

- **Leave Heron as it is** (Q-69 shape 1): the methods ask the modeller to save before a big build, and
  `REPORT_OPEN_DOCUMENTS` says which model was never saved. Rejected: it still rests on the modeller pressing
  Ctrl+S, which is how both builds were lost.
- **A save operation of its own** (shape 3), beside `move_elements`, declared Publish and run with no group
  at all. Rejected: a new tool for the chat, a new entry in the registry and the gate, and the same pin
  change as shape 2.
- **A preview that does not save.** It keeps a preview free of anything irreversible, and then the route
  could never be proved while D-117 refuses a DRAFT kept for real (Q-69's reason 2).

### Consequences

- **Until it is built and proved, nothing at runtime changes.** `SAVE_DOCUMENT` version 2 still refuses the
  model it works in, and the methods still ask the modeller to save first. It is being built in another
  session from 2026-11-16; version 3 starts DRAFT and is proved on a scratch model (Article 20, D-30).
- **A preview that saves writes the file.** The reply says the save was made, so a preview is never read as
  having changed nothing on disk.
- **Not measured** - [Group EN](../needs-checking/group-en.md) EN4 and EN5: whether Revit lets an ExternalEvent
  callback save at all, what Revit's own dialogs do on a workshared model or a network folder, what the
  dialog watch does with one met after the group, and how long a big model's save runs past the add-in's
  60-second *still_running*.
