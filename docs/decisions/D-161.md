### Context

When `revit_change`'s answer is lost after its request left - the chat's wait ends, the pipe drops - the
chat is told the outcome is unknown and to look at the model before trying again. Revit finishes the job
anyway, and since row 5b-407 the add-in writes a run record for it. But nothing tied that record to the
request the chat sent, so the chat could not find the answer it lost.

### Decision

1. **`revit_change` names every request it sends** - a `requestId`, random, sixteen characters.
2. **The add-in writes that name into the run record** it keeps when the job ends, whether or not anybody
   is still waiting.
3. **A failure whose outcome is UNKNOWN (the answer was lost) or RUNNING (Revit is still at it) ends its
   reply with where the answer can be read:** *"heron_run_record request=<id> reads it. Ask that before
   trying the change again."* A refusal - nothing ran - says nothing of it.
4. **`heron_run_record` takes `request`** and finds the record by it among the newest 200. None found says
   Revit may still be working, and to look at the model first.

### Cancelling a long job - not built, because it is already there

The plan's item 9 also asked to cancel a long job. Heron has two ways, both older than this: **D-129's run
clock** stops a fragment that runs too long and rolls it back, inside the dispatcher's wait; and the bridge
**`stop`** (`heron_bridge_client.py stop`) stops Heron until Revit restarts. A third - a chat tool - could
not help: a chat waits for its own tool call to return, so it cannot ask for a stop while one runs. And the
ribbon's Stop button was removed by the owner (D-46). Nothing was added.

### What is not known

Nothing of it has run in Revit. It compiles for 2020 to 2027; `tests/test_late_answer.py` runs the lookup
and the words and reads the wiring, failing on the code before the change.
