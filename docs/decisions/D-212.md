### Context

[D-210](../decisions/D-210.md) said yes to building Heron's chat side as a Claude Code plugin and left two of the design's
three questions open. The second is where the built plugin is published, so that a modeller's Claude Code can fetch it
and update it. Claude Code's documentation, read on 2026-11-28 (the plugin marketplace pages, the marketplace
reference, discovering plugins and hosting a marketplace), says:

- a marketplace is `.claude-plugin/marketplace.json` in a repository, read from its default branch by
  `claude plugin marketplace add <owner>/<repo>`;
- a plugin's source can be a GitHub repository at a `ref` - a branch or a tag - and an optional `sha`, which pins one
  commit;
- with `version` set in `plugin.json`, a modeller stays on the copy they have until that string changes, and a version
  typed in the marketplace's entry as well loses to `plugin.json`'s;
- `heron` is not one of the reserved marketplace names;
- auto-update is off by default for a marketplace that is not Anthropic's.

**It does not say whether a plugin's source may be the marketplace's own repository at another ref.** That was
measured instead, on Claude Code 2.1.332 in a cloud container, with a throwaway repository holding a `main` with the
marketplace and a `plugin-release` branch written by `tools/publish-plugin.py`, its source given as a git address at
`ref` `plugin-release`: `claude plugin marketplace add` and `claude plugin install heron@heron` installed 0.3.0, and
after a second release `claude plugin update heron@heron` moved it to 0.3.1. The real source is GitHub's, which only
the first real release can try.

### Decision

1. **The marketplace is `.claude-plugin/marketplace.json` on `main`**, named `heron`, listing one plugin, `heron`,
   whose source is `{"source": "github", "repo": "Ajmalpshaik/Heron-AI", "ref": "plugin-release"}` - no `sha`, which
   would never move, and no `version`, which is `plugin.json`'s alone.
2. **`plugin-release` is an orphan branch holding only the built plugin folder at its root.** It shares no history
   with `main`, and only [`plugin-release.yml`](../../.github/workflows/plugin-release.yml) writes it: when a person
   publishes a release that is not a pre-release, it builds the plugin from that release's commit and adds **one
   commit**, named *"Heron plugin X.Y.Z - release vX.Y.Z"*, whose one parent is the last release's. **Never a
   force-push**: a branch that moved after it was read is refused.
3. **The rules are in [`tools/publish-plugin.py`](../../tools/publish-plugin.py), not in the workflow.** The tag must be
   `v` and the plugin's version; the version must be new to the branch - the same number with other files would reach
   nobody, and a lower one would move modellers back; and the branch's newest commit must be one of its own. Any of
   these refuses, and nothing is sent.
4. **A pull request that touches what goes into the plugin, or a run by hand, rehearses**: it builds the plugin, runs
   `claude plugin validate --strict` on the marketplace, on a marketplace pointing at the branch's layout and on that
   layout, with Claude Code 2.1.332 installed from npm, and makes the release's commit without sending it.
5. **Nothing is released by this.** No tag and no GitHub release is made; the first is the owner's.
6. **The install line works only after the first release that carries this workflow is published:**
   `claude plugin marketplace add Ajmalpshaik/Heron-AI`, then `claude plugin install heron@heron`. Until Setup's tick
   installs the plugin itself (section 6 of the design), it is not for a PC where Setup already added Heron to Claude
   Code: both would start.

### Alternatives considered

- **A second repository** - offered, and not chosen: two places to keep, and two sets of permissions for one release.
- **Writing the branch on the tag** - when `release.yml` makes its draft. Not chosen: Setup fetches only from the
  newest published release, so the plugin would move to a version Setup could not yet install.
- **A `sha` in the marketplace's source, or a version in its entry** - the first pins one commit and never moves; the
  second is a copy of `plugin.json`'s number that loses to it and goes stale.

### Consequences

- `plugin-release` gains one commit per release. Most of its files are `main`'s own, byte for byte, so GitHub stores
  them once; how much a modeller's Claude Code downloads at install and at each update is a PC check.
- A release published by a workflow's own token would not start the publish job; one published by a person does.
- A workflow file is added. A push or merge with a token that has no `workflow` scope cannot carry it, so the pull
  request that adds it may need the owner's own merge on GitHub.
- Whether the repository's rules let the workflow's token create and push `plugin-release` is first known at the first
  release.
- **That first release needs a new number.** `v0.3.0` was published on 2026-11-22, before this workflow existed, and
  `manifestVersion` is still `0.3.0`; the tag must be `v` and the version, and the version new to the branch, so the
  release that first fills `plugin-release` raises `manifestVersion` in `platform/heron-products.json` first.
- `claude plugin validate` advises an install line in the plugin's README. It waits for the part that changes Setup's
  tick, so that no modeller is told to install a second Heron beside Setup's.
- Nothing here is proven on a modeller's PC: section 8 of the design lists the checks owed.
