### Context

Two EXECUTE fragments could not go through the show door, for opposite reasons. `OPEN_VIEW` must run
with NO transaction open - Revit refuses a view change inside one (D-115) - and declared D-112's
`editScopeFailures` to get that on the write path. But that need also says *"I open my own
transactions"*, so the add-in refuses it on the read and show paths, where no transaction is open
anyway: "open the Level 2 plan" still needed Changes ON. `ISOLATE_ELEMENTS` is the other way round: Revit
takes a temporary isolate only INSIDE a transaction, and Heron opens one for fragment code only on the
write path - so through the show door Revit refused it. The add-in cannot tell these apart by risk: it
never sees a fragment's risk (FRAGMENT-ISSUES row 9, Golden Rule 19).

### Decision

1. **`noTransactionOpen` (bool, ambient) says "run me with no transaction open, and I open none".** On
   the write path the add-in runs it as it runs an edit-mode fragment - inside the job's group, with no
   transaction of its own - and refuses the job if a transaction is left open. On the read and show
   paths it is allowed: nothing is open there to begin with, and the need grants nothing those paths
   did not already allow. The add-in binds it `true`; the fragment never reads it.
2. **`editScopeFailures` keeps its meaning and its refusal** - a fragment that opens its own
   transactions - and `OPEN_VIEW` stops declaring it. Version 3 declares `noTransactionOpen`; its code
   did not move, so its proof stands.
3. **A fragment whose code needs Heron's transaction is declared MODIFY**, whatever it changes. Heron
   gives fragment code a transaction only on the write path, behind the Changes switch, so that is the
   level its card says. `ISOLATE_ELEMENTS` is the first: MODIFY from 2026-10-17, its code and proof
   unchanged. With Changes off, `revit_isolate_temporary` does the same job as fixed code in the add-in.

### Alternatives considered

- **Let the show door run `editScopeFailures` fragments.** A caller that skips Heron's client could
  then send a MODIFY edit-mode fragment through `run_fragment_show` and have it open its own
  transactions with Changes off - a write with no switch in front of it.
- **Send a fragment's risk to the add-in so it can tell an EXECUTE view change from a MODIFY stair.**
  Golden Rule 19: a caller may ask for an operation and may not say how dangerous it is.
- **Retire `ISOLATE_ELEMENTS` for the fixed operation.** It still serves a job that isolates as one
  step of a write, and a retirement is a larger act than correcting a level.

### Consequences

- "Open the Level 2 plan" runs with Changes off, through `revit_show`, once the add-in is rebuilt.
- `ISOLATE_ELEMENTS` sent to the show door is refused before anything is sent, and the refusal names
  `revit_isolate_temporary`; through `revit_change` it runs as before, with Changes on.
- **Not run in Revit.** The write path's handling is D-112's, unchanged, and measured for OPEN_VIEW on
  2026-10-13; the show door's is what NEEDS-CHECKING Group ES rows ES9 and ES11 owe.
