# D-114 — A fragment that reloads a family is handed Revit's load options by the add-in

> One record of [the decision log](../DECISIONS.md). Decisions are append-only: to change one, write a
> new decision that supersedes it.

**Status:** Proposed · **Date:** 2026-10-06 · **Source:** [FRAGMENT-ISSUES 5b-347](../fragment-issues/section-5b-rows-176-200.md) - a nested nut edited and saved on 2026-10-06 could not be reloaded into the two support families that hold it, and had to go through Insert > Load Family > Overwrite by hand
**Keeps:** [D-28](D-28.md) - a fragment is a body of statements compiled in process; nothing here lets a fragment declare a type · [D-112](D-112.md)'s pattern - an object a fragment cannot build is supplied as a declared ambient need · Constitution Article 7 - a family reload needs explicit confirmation for that operation
**Affects:** [`RevitFragment.cs`](../../revit/Heron.Revit.Addin/RevitFragment.cs) (`FamilyReload`, `FamilyLoadNeed`), [`heron_fragment.py`](../../brain/heron_fragment.py) (`AMBIENT`), `load-family`

### Context

Revit overwrites a family already loaded in a document only when `Document.LoadFamily` is handed an
`IFamilyLoadOptions` - the object that answers its *Family Already Exists* dialog. Implementing an interface
needs a class, and a fragment is a body of statements: C# has no local classes, and the compile gate wraps
each fragment in a method. So `LOAD_FAMILY` version 1 refused every family already loaded, and its own
comment said where the answer belonged: *"in the executor (D-28) as a supplied helper, not in a fragment -
the same way `doc` and `uidoc` are supplied. Do not solve it by making fragments able to declare types."*

### Decision

1. **The add-in supplies the ambient need `familyLoadOptions`**, typed `Func<bool, IFamilyLoadOptions>`.
   The bool is Revit's `overwriteParameterValues`. A fragment that declares the need gets it bound on both
   paths, like `doc`; it is only an object, and on the read path Revit refuses the load for want of a
   transaction anyway.
2. **The object always answers "overwrite the existing version"**, and a shared nested family takes the
   file's version (`FamilySource.Family`). Choosing NOT to overwrite is choosing not to reload, and that
   choice stays in the fragment, which never calls `LoadFamily` with this object unless the caller asked.
3. **Its `ToString()` says whether Revit asked** (`not asked`, `asked: family`, `asked: family in use`,
   `asked: shared family`). `LoadFamily`'s bare `false` cannot tell "the same version is already loaded"
   from a refusal; whether Revit reached its question can, and `object.ToString` needs no new type in
   the fragment's scope.
4. **Reloading is never the default.** `LOAD_FAMILY` reloads only on `reload=true`, typed by the caller,
   and refuses a loaded family by name without it - Article 7's confirmation.

### What it accepts

A second ambient need name, kept in step by hand between `FamilyLoadNeed` in `RevitFragment.cs` and
`AMBIENT` in `heron_fragment.py` - the same two-place arrangement D-112 made for `editScopeFailures`, and
[`tests/test_fragment_ambient.py`](../../tests/test_fragment_ambient.py) compares them. An add-in change,
so it reaches a modeller only after the add-in is redeployed for every Revit release and Revit restarted.
Whether `OnSharedFamilyFound` is reached for a nested family loaded into a host family is Revit's to
answer and **has not been measured** - [NEEDS-CHECKING CN](../needs-checking/group-cn.md).
