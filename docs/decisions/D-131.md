### Context

Heron claims every Revit release from 2020 to 2027, and the evidence is one proof per fragment, on one
release. Three things stopped a second release being recorded, each on purpose: `batch-prove` refuses a
PROVEN fragment as `ALREADY`, with no flag; `accept` refuses a PROVEN fragment whose proof still matches its
code; and `proof:` holds one record, its release written as prose inside `model:`. So a run of
`create-floor` on 2025 that held both halves had nowhere to go, and the only way to record it would have
overwritten the 2024 proof. A second route had the same problem from the other side: `second_route` is a
field of that one record, and `accept` would not reopen it. Q-66 put the choice to the owner.

### Decision

1. **`proof:` stays the record that made the fragment PROVEN.** Nothing here rewrites it.
2. **Each further release is one entry of `proof.releases`**, with `release`, `date`, `by`, `model`,
   `positive_case`, `negative_case` and the `fingerprint` of the code it ran against
   (`heron_fragment.RELEASE_REQUIRED`). `proof_problems` holds an entry to those fields, to a release the
   fragment claims, and to one entry per release. A stale entry is not a validation problem: it is
   recorded, and not counted.
3. **`batch-prove --release <year>` runs only fragments at PROVEN or PRODUCTION whose proof still stands,
   and only on a release neither the proof nor a fresh entry names.** Anything else is `ALREADY` or
   `NOT PROVEN`. Its run record and draft are named `<slug>@<year>`, never the proof's own. A record that
   names another Revit than `--release` is `WRONG RELEASE` and the batch exits 1. It writes drafts only,
   and its before/after `heron-status` check still holds.
4. **`heron_validate.py accept <slug> --release <year> --by "Name"` writes one signed entry** and nothing
   else, and refuses: a fragment not PROVEN, a proof gone stale, a release not claimed, a release already
   recorded by evidence that still stands, a draft against other code, a record naming another release, and
   every evidence refusal `accept` already makes. An entry gone stale is replaced, the rule `accept` keeps
   for a stale proof.
5. **`accept <slug> --second-route --by "Name"` writes `proof.second_route` on a PROVEN fragment from a
   recorded run** (`validate --cross`, drafted with `draft --second-route`), signed, and only where the
   line says NOT ESTABLISHED. A route already written is never replaced, and the line is never typed by
   hand.
6. **The matrix marks a cell PROVEN from the proof's release or from a fresh entry, and never from
   `revit:`.** An entry names its release in a field, so no prose is parsed for it.
7. **Each write is checked rather than promised:** the file is read back, and if the status, another field
   of the proof or any other key moved, it is put back and nothing is saved. A proof taken again after the
   code moved keeps the entries already recorded.

### Alternatives considered

- **Leave it as it is** - the 2020-to-2027 claim stays unbacked. Not chosen.
- **Prove again into `proof:`** - loses the earlier release's record. Not chosen.
- **A separate register outside the fragment** - nothing that reads fragments today would read it. Not
  chosen.

### Consequences

- [Group EQ](../needs-checking/group-eq.md) row EQ7 no longer waits: it has a command per release. The runs
  themselves are still NEEDS REAL REVIT, and no fragment is proven on a new release by this decision.
- A second route that is a person's - a schedule count, the Project Browser - has no recorded run, so it
  cannot be written by `accept --second-route`; only a route the bridge runs (`validate --cross`) can.
  EQ8 says so.
- `brain/heron_runs.py` still reads the proof's release alone through `heron_matrix.proof_release`, so a
  run that contradicts an entry is not yet reported there.
