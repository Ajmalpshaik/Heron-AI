### Context

Article 11 says *"untested code never touches a live model"*, and Golden Rule 18 says the same of
generated code on its first run. `revit_change` keeps every change it makes (D-99). Until this
decision it sent a DRAFT fragment, or a PROVEN one whose code had moved since its proof, exactly like
a proven one - and only then added a line under the result: *"'X' is DRAFT, not PROVEN ... Look at
what it did before trusting it."* That warning arrived after the change was already in the model.

The Enforcement table put Article 11 in the add-in's permission gate, and nothing there could enforce
it: the add-in is handed a fragment's source and contract, never its card (`RevitFragment.Run`), so it
cannot know whether what it is running was ever proved. The client reads the card and the proof, and
the client never asked.

**Measured 2026-10-17 on this checkout:** 359 fragments are declared above ANALYZE; 205 of them carry
a proof that still describes their code, and the other 154 are DRAFT - 30 of those with a proof their
code has moved past. No PROVEN fragment was stale that day. Derive it again rather than reading it
here: `python tests/test_admin_publish.py` prints the first two numbers in its section 7.

### Decision

1. **A change is kept only from a fragment whose own files say PROVEN or PRODUCTION, and whose proof
   still describes its code** (D-30's fingerprint). Anything else - DRAFT, no status, a status that
   cannot be read, a stale proof - is refused by the client **before its code is read or a session is
   bound**. The refusal names the capability and its status and says nothing was sent.
2. **One rule, in the client, asked by both paths that keep a change**: `revit_change` - and so every
   Companion Apply, which runs through it - and `fragment --write --apply`. It sits beside
   `risk_refusal` and is called, never copied. The status comes from `heron_brain.proof_status`, read
   from the fragment's files, never from the retrieval index.
3. **A run that keeps nothing is not asked**: `fragment --write` without `--apply`, and `validate
   --write` with the batches `tools/batch-prove.py` runs through it, are rolled back (D-55); `prove`
   only reads. None of them leaves anything in the model, and the rolled-back run is how a DRAFT
   becomes PROVEN at all. **This reads the rolled-back run as Article 11's sandbox** - the owner
   confirms or corrects that reading.
4. **A read is not asked.** `revit_read` opens no transaction, so Revit itself refuses any change, and
   its answer still says DRAFT.
5. **The way through for a DRAFT, once Heron has an in-Revit Keep/Discard prompt**: the client sends
   `unproven: "true"` with the request. The field can only **add** caution - when the add-in sees it,
   its prompt becomes mandatory and says the code was never proved - and a request without it lowers
   nothing. Two conditions come with it. The client sends a DRAFT that way only to an add-in that says
   it honours the field, because an older one would ignore it and keep the change with no prompt. And
   the confirmation is the prompt in Revit, never a "yes" typed in the chat (Golden Rule 19).
6. **Until that prompt exists, a DRAFT is refused.** The add-in half of item 5 is left for that work.

### Alternatives considered

- **Keep the warning after the run.** Breaks Article 11 by construction: the model has already changed
  when it is read.
- **Let a "yes" typed in the chat keep a DRAFT.** The host model can type it; Golden Rule 19.
- **Send the status to the add-in and let it decide.** The caller would be vouching for its own
  request - the reason `risk_refusal` sends no risk either (Golden Rule 19, FRAGMENT-ISSUES row 9).
- **A setting that lets DRAFTs be kept.** A client reading a switch that lowers its own caution is the
  pattern `revit_change` refuses for Changes itself: *"a client deciding its own permission is not a
  permission."* Not taken.

### Consequences

- **A DRAFT that writes cannot be kept from a chat until it is proved.** That includes the Companion:
  the loads page's air-terminal flow step runs `SET_AIR_TERMINAL_FLOW`, DRAFT on 2026-10-17, and is now
  refused.
- **The owner's test-and-undo loop ends for DRAFTs through the chat.** What remains is the rolled-back
  run from the command line and `batch-prove`, on a test copy, then a signed proof.
- **An arrangement KEPT from a DRAFT on a scratch model is refused too.** The client cannot tell a test
  copy from a live model, so it does not try. Three open NEEDS-CHECKING groups build their arrangement
  that way, in a scratch family - [CT](../needs-checking/group-ct.md), [AN](../needs-checking/group-an.md)
  and [CR](../needs-checking/group-cr.md), with `create-family-extrusion`, `group-elements`,
  `combine-family-forms` and `add-family-connector`, each DRAFT on 2026-10-17. Their arrangement steps
  now stop at the refusal, with nothing sent, until the prompt lands, those fragments are proved, or
  the owner decides otherwise below. The groups are left as written: their instructions are his to
  change once he has.
- **It is a guard on this side, like `risk_refusal`.** A caller that skips this client is not stopped
  by it; the Changes switch in Revit still is.
- **The words path is unchanged** - it already ran only a PROVEN match whose proof was current
  (`_runs_as_matched`).
- **The Enforcement table names where Article 11 is now enforced**, and `heron-fragment-author` no
  longer says nothing at runtime stops a DRAFT.

### What is left, and who resolves it

- **The add-in half of item 5** waits for the Keep/Discard prompt. When it lands, a NEEDS-CHECKING row
  is owed for the prompt's "never proved" wording in a real Revit, and for an older add-in refusing a
  DRAFT rather than ignoring the field.
- **Ajmal PS decides**, in the pull request: whether the refusal stands against the D-99 loop; whether
