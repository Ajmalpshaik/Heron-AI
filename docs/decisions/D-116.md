### Context

A chat that has just placed sprinklers, built a family or filled a sheet can count what it made and
cannot see it. Twelve sprinklers is a count; all twelve in one corner of the room is a picture. Every
Heron tool answered in text (`-> str`), and the one thing in Heron that makes a picture of a view,
`export-view-image` (FRG-VIEW-073, PROVEN 2026-09-13), is `risk: PUBLISH`: it writes PNGs into a folder
the caller names, for other people to find, and hands back the folder rather than the picture.

So the owner asked for a tool that returns the picture **into the chat**, changing nothing. Two rules
already in this log bear on it, and neither was written with a picture in mind. D-107 made every export
PUBLISH, and Article 10 says no export *"to a shared location"* is ever made on Heron's own initiative.
D-82 drew the cloud line by content type: documents may go, *"Revit models, families, model data -
never leave the PC"*. D-26 had already put element data - counts, sizes, parameters - in the
conversation.

### Decision

1. **A fixed operation, `capture_view`, declared ANALYZE** in `HeronOperationRegistry.cs`, served as the
   MCP tool `revit_view_image` at ANALYZE. Given a **view name** (empty: the view in front) it exports
   that view as it stands. Given **element ids** it makes a temporary isometric 3D view, puts a section box
   round the elements with a margin, hides every category that is not a model category and every datum,
   and exports that. The width is clamped to 320-2400 px, 1280 when none is given.
2. **It is not a D-107 export.** The PNG is written into `HeronPaths.Captures`, a folder of Heron's own
   under Derived - machine-local, never roaming, safe to delete - read back, and deleted with its folder
   before the add-in answers. No caller can name a folder or a path. Nothing is put where another person
   reads, which is what Article 10 and D-107 are about. `export-view-image` keeps its PUBLISH level and
   its job: pictures somebody else is meant to receive.
3. **It is the first ANALYZE operation that opens a transaction, and that is said, not slipped in.**
   Every other ANALYZE operation opens none, and `run_fragment_read`'s guarantee is structural - Revit
   refuses a change made outside a transaction. Picturing elements needs a new view, which Revit makes only
   inside one. This operation's guarantee is a different one: **its TransactionGroup is always rolled
   back.** There is no `apply` to send; the rollback sits in a `finally` in reviewed C#, not in a fragment
   whose executor also knows how to keep; and `tests/test_tool_registry.py` fails if `RevitCapture.cs` ever
   assimilates or commits a group, or reads `apply` from a request. It runs with Changes off. While Heron
   is stopped the elements way is refused, because stopped means no transaction is opened.
4. **The picture travels inside the reply**, base64, and reaches the host as an MCP image block. Never as
   a path: under the Microsoft Store Claude app, Python and Revit see different AppData folders
   ([FRAGMENT-ISSUES 5b-416 to 5b-419](../fragment-issues/section-5b-rows-401-425.md)), so a file one writes
   is not where the other looks. A picture over 3.75 MB - 5 MB once encoded, the per-image limit the
   Claude API documents - is refused with the width to ask for instead.

### The question only the owner can answer

**Is a view's picture "model data" under D-82?** Both readings hold up, which is why it is asked:

- **Not model data.** It is not the model: it cannot be opened, edited or rebuilt into one, and nothing
  of the file travels. It is the same kind of thing as a count or a size - what the model *shows*, which
  D-26 already lets into the conversation - only drawn. On this reading the tool ships as written.
- **Model data.** A picture shows geometry and layout - where everything is, at a glance - which is more
  of the building than any count, and once in the conversation it has gone to the cloud the same way the
  answers have. On this reading **`revit_view_image` must not ship**: the pull request is closed, or the
  tool and `capture_view` are taken out of it before merge, and nothing else in Heron sends a picture.

D-82 was written about what may be ingested into the knowledge store and embedded; D-26 is the decision
about the conversation. Which of the two governs a picture is the same question asked from the other
side, and the owner's answer settles both.

**Answered 2026-10-17: not model data.** Ajmal PS: *"A picture is not model data, ship it"* - the first
reading, so the tool ships as written, and "ship it" accepts the decision above with it, item 3
included.

### Alternatives considered

- **Use `export-view-image` and read the file back.** It is PUBLISH, so a look at the model would need
  the Publish switch on; it writes where the caller says; and its answer is a folder, which Python under
  the Store app may not see (decision 4).
- **A fragment through `revit_read`.** The read door opens no transaction, so the elements way cannot be
  built there at all - and a fragment's answer is text.
- **The elements way at MODIFY.** Honest about the transaction, but it would need Changes on, and a host
  would ask permission before every look. What is risky about a transaction is what it keeps, and this
  one keeps nothing.

### Consequences

- **A host may call it without asking.** ANALYZE is labelled read-only (`heron_tools.annotations`), so
  Claude Code can take a picture unprompted, as it can count.
- **The banner shows the reading colour** and says *"Taking a picture of a view for the chat"* (D-50).
- **A picture costs the chat far more context than a sentence.** How much at 1280 px is not measured.
- **It has never run in Revit.** It compiles on 2020 to 2027 and its MCP side is tested against a
  stand-in reply on both SDKs ([D-45](../DECISIONS.md#d-45--heron-tracks-the-mcp-sdk-across-major-versions-the-way-it-tracks-revit-releases));
  [NEEDS-CHECKING group EJ](../needs-checking/group-ej.md) holds the run that would prove it, with its
  negative case. It is not PROVEN and nothing here may say so ([D-30](../DECISIONS.md#d-30--a-fragment-is-promoted-by-one-recorded-proof-not-by-a-count-of-runs)).
