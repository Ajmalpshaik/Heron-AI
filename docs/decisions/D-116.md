# D-116 — A tool description over its budget stops a pull request

> One record of [the decision log](../DECISIONS.md). Decisions are append-only: to change one, write a
> new decision that supersedes it.

**Status:** Accepted · **Date:** 2026-10-17 · **Source:** Ajmal PS, 2026-10-17, in conversation, answering the question put in the pull request that added the budget: *"keep it a gate"*
**Keeps:** [D-03](../DECISIONS.md#d-03--mcp-tool-granularity-thick-and-specific) - the tool list's cost is accepted and kept down by a small core set · [D-100](../DECISIONS.md#d-100--a-drop-in-the-score-of-the-owners-own-questions-is-reported-never-a-gate) - the routing score stays a report; this decides a different number
**Affects:** [`tests/test_tool_sizes.py`](../../tests/test_tool_sizes.py), [`mcp/server/heron_tools.py`](../../mcp/server/heron_tools.py) (`--sizes`), [`.github/workflows/gates.yml`](../../.github/workflows/gates.yml), which runs every suite

### Context

D-03 accepted that *"MCP tool schemas cost context on every request"* and kept the cost down with a small
core set - since [04 §8.6](../04-heron-mcp.md) the six tools in `heron_tools.ALWAYS_LOADED`, given to
every chat before the modeller types. Nothing measured it until 2026-10-17, when
`python mcp/server/heron_tools.py --sizes` was built and `tests/test_tool_sizes.py` held the six
together, and every tool alone, to a budget of characters of description ([04 §8.8](../04-heron-mcp.md)).
Whether going over that budget should only be reported, or should stop a pull request from merging, is
a question about how Heron is developed, and it was the owner's to answer - the same question D-100
answered for the routing score.

### The question, as it was put

> *"Should a tool description over budget only be reported, or should it stop a pull request from
> merging? As written it stops it (exit 1). I recommend keeping it a gate."*

It was put beside D-100's own picture - Revit's warnings against its errors: a warning shows in Review
Warnings and work carries on; an error stops the command. He answered: *"keep it a gate"*.

### Decision

**A tool description over its budget fails `tests/test_tool_sizes.py`, and so stops a pull request.**
The budgets are the two constants at the top of that file - ALWAYS_LOADED's descriptions together, and
any one tool's - and raising either is a decision whose reason is written beside it, as
`tests/test_instructions.py` does for `host.chat`'s word budget.

### Alternatives considered

**Report only** - print the tools over budget and exit 0, as D-100 chose for the routing score. It lost
because two of D-100's three reasons do not hold for a size:

- **A size is exact.** D-100's score is *"a sample of one store"*, and a gate on a sample fails pull
  requests on noise. A description's length is the same on every machine and every Python since the
  change that built `--sizes` ([row 5b-489](../fragment-issues/section-5b-rows-401-425.md)).
- **It is fast.** D-100's run takes about three minutes; this suite about a second, and it needs no SDK,
  so CI runs it.

**D-100's first reason does hold**: a gate teaches people to cut words to buy the number back. So the
same suite refuses the trims that would be the wrong trade - a description that stops naming an argument
the tool takes, and `revit_change` or `revit_read` losing a sentence its safety stands on (`MUST_KEEP`).

### Consequences

- **Easy:** the cost every chat pays cannot creep back up unseen; a pull request that grows a description
  past its budget is red and says which tool and by how much.
- **Hard:** a new tool, or a longer description, has to fit - or the budget is raised in the same pull
  request with its reason. What does not fit belongs in the answer the tool gives at the moment it is
  needed, or in a comment no host is served.
- **Locks in:** `tests/test_tool_sizes.py` exits 1 over budget. Making it a report needs a new decision
  that supersedes this one.
