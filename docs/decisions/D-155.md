### Context

D-55 built the preview into the add-in on 2026-09-08: a fragment sent **without** `apply` runs for real
inside one `TransactionGroup`, reports what Revit counted, and is rolled back. Every proof since was taken
that way. But the chat had no way to ask for it: `revit_change` has always sent `"apply": "true"`, and the
only run-and-roll-back doors were the command line's `fragment --write` and `tools/batch-prove.py`.

So a chat that wanted to know *how many* elements a change would touch, and which would be skipped, had to
make the change and let the modeller Discard it - a box in Revit for a question the chat could have
answered alone.

### Decision

1. **`revit_change` takes `dry_run`, false by default.** True sends the same request with **no `apply`
   field at all** - the word the add-in already reads as run-and-roll-back. Never `"apply": "false"`: an
   absent field cannot be misread by an add-in of any age.
2. **A dry run can only keep less.** Every refusal stands for it unchanged: the Changes switch (read in the
   add-in), the PROVEN rule (D-117), the pinned model. Nothing in the flag raises what a chat may do, which
   is why Golden Rule 19 does not stop it.
3. **A Publish or Admin capability is refused as a dry run, before anything is read or sent.** A rollback
   takes back what Revit's transactions hold and nothing else: an export, a save or a sync done inside the
   run is done. A "dry run" that left a file on a server would be the opposite of its name.
4. **The reply opens `DRY RUN: <capability> was tried in <model> and rolled back.`**, keeps the add-in's
   own rollback verdict whole (it is the only side that saw whether the rollback held), and ends by saying
   how to keep it in this tool's words: call again without `dry_run`, only when the user says to, and read
   that run's own counts because the model can have moved.
5. **No after-change table** on the Companion page for a dry run: its values were used on a change Revit
   no longer holds.

### Why this does not reopen D-126's rejected alternative

D-126 rejected *"D-55's preview through the chat"* **as the way a change is approved**: two runs, a model
that can move between them, and the modeller asked in the chat about elements they cannot see. That still
holds, and nothing here replaces the Keep or Discard box - a kept change after a dry run is a second run,
asked in Revit exactly as before. A dry run is a **question the chat asks for itself** ("how many would
this touch?"), not an approval.

### What is not known

- **It has not run in a real Revit.** The add-in's rollback path is D-55's and is exercised by every proof,
  but this door sending it has only been tested against a stand-in. [NEEDS-CHECKING Group NT](../needs-checking/group-nt.md)
  holds the runs.
- **A fragment that writes outside Revit's transactions** - a file, a registry key - is not taken back by
  a rollback whatever its declared risk. Item 3 covers what is declared Publish or Admin; a MODIFY card
  that does more than it declares is a defect in that card, as it already is for a kept run.

### Alternatives considered

- **Leave it to the Keep or Discard box.** It answers *keep this?*, not *how many would this touch?*, and
  costs the modeller a click and a look for a question the chat could answer alone. And with the owner's
  *Ask to Keep* switch OFF - the default since D-138 - there is no box at all: the change is kept at once.
- **A separate tool, `revit_try_change`.** A second door with the same body is how two doors drift
  (D-117 calls its rule rather than copying it for that reason), and every tool added costs every chat
  its description (D-118).
