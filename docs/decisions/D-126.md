### Context

A fragment runs on Revit's own thread inside the dispatcher's `Execute`, and nothing else runs there until
it returns. **One that loops for ever never returns.** The dispatcher stops waiting after
`revit.operationTimeoutSeconds` and can only answer `still_running` - *"It is still working; do not repeat
the request"* - while the loop goes on, Revit stays frozen, and the only way out is ending Revit with the
model unsaved. The stop flag could not help: it was read only before a job starts, and since D-46 nothing
could set it - *"`HeronStop.IsStopped` is false for ever, so both gates are inert"*. Revit gives no way into
its own thread from outside, so whatever stops the loop has to be inside the fragment.

### Decision

1. **The fragment carries the check.** `HeronStackGuard`, which already puts a stack check at the entry of
   every method and lambda of a fragment, puts a call to `HeronRunClock.Check()` beside it, and another at
   the head of every loop body - `for`, `foreach`, a deconstructing `foreach`, `while` and `do`. A loop body
   that is one statement gets braces carrying that statement's own trivia, and the calls go before the
   opening brace's line ending, so no line moves and a `#if` that opens a body still begins its line.
2. **The clock trips on time or on a stop.** Its deadline is the dispatcher's own wait - handed to it by the
   dispatcher, the one reading of the key - less a margin of a sixth, at least two seconds and never more
   than half: 50 s of the default 60. It is counted from `RevitFragment.Run`, before binding and compiling,
   so the rollback and the answer arrive while the caller still waits. It also trips when `HeronStop` was
   asked to stop **during** the job - a count, not the flag, so a read run while stopped is not tripped and
   a second stop still lands.
3. **The trip is sticky and asked after the script.** Many fragments catch `Exception`. Once tripped, every
   later check in the job throws again, and `RevitFragment` asks the clock after every script whether it
   threw or not. A tripped job is rolled back - its transaction and the group, setup steps included - and
   answered `ran_too_long` or `stopped_mid_run`, saying whether Revit **confirmed** the rollback, the
   2026-09-09 rule `RefusedBy` keeps. A read has nothing to roll back and says so.
4. **Only fragment code is timed.** Checks count inside `RunScript` alone. What the add-in reads afterwards -
   a lazy sequence the fragment left, enumerated after the group was kept - stays untimed, because a throw
   there would report a failure for a change already in the model.
5. **A prompt pauses it.** `HeronRunClock.Pause()` holds the deadline while a person is asked something
   from inside a job, and adds the time back. Nothing on the run path shows such a prompt today; the first
   one is a `using` block, not a change to the clock. It does not pause the dispatcher's wait. The Keep or
   Discard box [D-119](D-119.md) shows for a DRAFT's one run is asked after the script has returned,
   outside the timed part, so it cannot trip the clock and needs no pause - and the dispatcher's longer
   wait for it is D-119's own.
6. **The bridge can stop Heron: a `stop` operation.** Declared Read, answered by `RevitDispatcher.Dispatch` on
   the listener thread **before anything is queued** - queued, it would wait behind the job it exists to stop
   - and after the lease, so only the chat holding a Revit can stop it. It calls `HeronStop.Stop()`, says
   whether a job was running, and is recorded in the trail. `tests/test_tool_registry.py` names it as the
   one operation answered before the queue, as row 5b-14 names `ping`, `info` and `release`.
7. **Nothing over the bridge resumes.** A stop that the thing being stopped could lift is advice. A restart of
   Revit clears it, as it always did, and `HeronStop.Message` now names that as the way out - the sentence
   whoever built the trigger was told to own.
8. **Whether a stop should survive a restart was left to the owner** - [Q-67](../open-questions/from-master-specification-part-2.md),
   where 21 §4's requirement 3 and `HeronStop`'s *"IT DOES NOT PERSIST"* were both recorded. A pipe
   operation was chosen over 21 §4's file partly so as not to settle it by accident: a file on disk would
   have survived a restart by construction. **Answered the same day as [D-127](D-127.md): a restart
   clears it**, which is what the code already does.

### What D-46's costs are now

| D-46 said | Now |
|---|---|
| *Nothing can switch the stop on any more.* | The `stop` operation can, from the chat holding the Revit - today through the bridge client's `stop` with that chat's `HERON_CLIENT_ID`. **Nothing in the MCP server sends it yet**, so a chat still cannot stop itself from the chat, and there is still no ribbon button. |
| *`HeronStop.IsStopped` is false for ever, so both gates are inert.* | Both gates are live again after a stop: `RevitOperations.Gate` refuses Modify and above, `RevitWrite.Refuse` refuses the move as well, and reads go on. |
| *There is no stop that leaves the connection up.* | There is: `stop` leaves the pipe up, so the chat can still ask what happened. |
| *Neither control can interrupt work Revit has already started.* | A **fragment** can now be interrupted, at its next check, and is rolled back. A single long Revit API call still cannot, and nor can an operation that is not a fragment. |
| *The file-based kill switch that 21 §4 pairs with the button was never built.* | Still not built, deliberately - see item 8. |
| *`C1`, `C2`, `C4` and `C6` can no longer be run.* | They can be again, through `stop` rather than a button. **Not re-run**, and their wording still names the button. |

### The honest limits

- **An expression-bodied lambda, and so every LINQ query, carries no check** - `HeronStackGuard` leaves them
  alone because rewriting one can change which overload it binds to. A fragment that loops for ever inside a
  LINQ query, or recurses only through `x => expr`, is not stopped. Nor is a loop made with `goto`, which no
  fragment writes today.
- **A single long Revit API call cannot be interrupted** - a Regenerate, a LoadFamily, an export. No check runs
  inside it. It finishes first, and if it outlasts the dispatcher's wait the answer is still `still_running`.
- **A rollback that takes longer than the margin** also arrives after the dispatcher has answered.
- **The compile gate does not compile the rewritten source.** `tools/check-fragments-compile.py` builds each
  fragment as written; D-28 warns that the gate must cover the code that actually runs, and the code that
  runs now carries two injected calls. What stands in for it: `tests/Heron.StackGuard.TestHost` shows, over
  the whole library, that the rewrite adds nothing but its two fully qualified calls and the braces a
  one-statement loop body needs - token for token - and compiles and runs guarded scripts against the linked
  clock. What it does not show is a guarded fragment compiled against each release's Revit assemblies; that
  happens first in Revit. [Row 5b-512](../fragment-issues/section-5b-rows-401-425.md) keeps it open.
- **Only the chat holding the lease can stop a Revit.** A person at a terminal cannot stop another chat's job
  without that chat's client id - the lease refuses first, as it refuses everything else.
- **It is unproven in Revit.** [NEEDS-CHECKING Group ES](../needs-checking/group-es.md): a runaway stopped and
  rolled back within the timeout, Revit coming back, and a stop from a second pipe mid-run.
