### Context

[D-99](../DECISIONS.md#d-99--a-change-asked-for-in-a-chat-is-kept-at-once-with-no-preview-and-article-9-says-so) made
`revit_change` keep what it did at once, with no preview, and wrote that down as Article 9's one exception.
The owner chose it on 2026-09-23 with the preview offered and recommended, because the loop the owner
works in rested on **undo**: try it, and press Ctrl+Z if it did wrong.

Three things in Heron went on saying the opposite while D-99 stood. The Changes window's first promise
read *"You see a preview first, and nothing is kept until you say yes"*; the ribbon padlock's fallback
question says *"It still previews first and still asks before keeping anything"*; and the bridge status
window says *"It previews first"*. None of them was true of a change from a chat.

D-99 also said what going back would cost: *"The preview is one flag away ... Going back is a new
decision and a small change in the server."* That route - run without `apply`, show the rolled-back
counts in the chat, send it again with `apply` - **runs the change twice**, and the model can move between
the two runs. The modeller's eyes are in Revit, not in the chat.

### Decision

1. **Before `revit_change` keeps a change, Revit asks the modeller.** The run happens exactly as before,
   inside one `TransactionGroup` named `Heron: <name>`. Then, with the group still open and no
   transaction in it, the elements Revit reports added and changed are **selected and temporarily
   isolated in the active view** - only when the model run in is the one in front - and a TaskDialog
   asks **Keep** or **Discard**, as two command links. The whole run is one ExternalEvent callback, so
   the group stays open across the dialog and nothing else reaches the model meanwhile.
2. **Only the Keep link keeps.** Discard is the default button; Esc, the close button and any result
   nobody expected are Discard. *One box with D-119:* it is D-119's prompt, `RevitFragment.AskTheModeller`,
   which answers Keep, Discard or Closed and is shown inside `HeronDialogWatch.HeronAsks()` so the job's
   dialog watch never answers it; `HeronKeepQuestion` holds its words for both doors, and a DRAFT's one
   run still says it has never been proved.
3. **Keep** assimilates the group - **one undo entry**, `Heron: <name>` - and leaves the changed elements
   selected, which [D-60](../DECISIONS.md#d-60--a-preview-selects-what-it-would-change-and-what-it-would-skip-up-to-500)
   says is what a modeller wants after a change lands. The reply carries D-119's `asked`, `modellerAnswer`,
   `kept` and the sentence saying who decided.
4. **Discard** rolls the group back and **puts the modeller's own selection back**, saved before it was
   replaced (D-60). *One box with D-119:* the reply is an ok one with D-119's fields - `asked`, and `kept`
   false - and its verdict says *"The modeller chose Discard in Revit, so NOTHING WAS KEPT"* only when the
   rollback held - Revit reported the group rolled back and, since #562's rollback check (Group EO),
   nothing the run added is still standing - otherwise that the model may still hold the change; never the plain
   rollback's *"send it again with apply"*. `revit_change` reports it as refused: **a Discard is never
   retried** ([Article 25](../../HERON_CONSTITUTION.md)), and the chat is told it is the modeller's
   answer, not a fault.
5. **Who decides to ask is the owner's switch, `write.askBeforeKeeping`,** in `heron.config`, **on by
   default**, read fresh inside the add-in by `HeronPermissions.AsksBeforeKeeping`. A value nobody can
   read means ask. It is **never a field in the request** - [Golden Rule 19](../14-golden-rules.md), and
   D-106 item 4's reason: a caller may ask to keep, and only the modeller says yes. Off puts back D-99's
   behaviour exactly, and Article 9 records that as its one exception.
6. **No change, no question.** When Revit reported nothing added, changed or deleted - an `OPEN_VIEW`
   ([D-115](../DECISIONS.md#d-115--a-fragment-that-must-run-with-no-transaction-open-declares-d-112s-switch-too-and-the-first-is-open_view)),
   a rename that matched nothing - Keep and Discard would leave the model the same, so it is kept and the
   verdict says *"the modeller was not asked"*.
7. **What changed is Revit's own report**: `RevitChangedSet`, a `DocumentChanged` collector subscribed
   after `group.Start()`, taken off by a `using` however the group ends, and stopped before anything is
   shown on screen. It keeps the ids and nothing else, so a later short change report can grow from it.
   Deleted elements are only counted. **D-60's cap applies to each set on its own**: above 500 added or
   500 changed elements, that set is not drawn and the question says how many and why.
8. **The isolation is ended inside the group, before Keep or Discard**, with
   `DisableTemporaryViewMode` - D-115 measured that a view change survives a group's rollback, and ending
   it after `Assimilate` would make a second undo entry. A view the modeller has already isolated or
   hidden in is not isolated again, because ending ours would end theirs.
9. **The bridge waits for the modeller.** *One box with D-119:* its wait - a job that has put the box up
   gets `revit.askTimeoutSeconds` (300) after its operation timeout, and a box still open then is answered
   `awaiting_modeller` - RUNNING, WAIT - never *"still running"*. The client's deadline for a run that
   keeps, `fragment_timeout(keeping=True)`, adds the same as D-119's `try_once_timeout`, so the bridge is
   still the side that answers; a read keeps its 180 seconds. And the job's dialog watch is asked again
   after the box, because showing the change commits a transaction of its own.
10. **The activity banner steps aside** while the dialog is up: it is Topmost, and would sit over it.

### What this does NOT change

- **[Article 7](../../HERON_CONSTITUTION.md) stands.** The question comes after the change has run, and it is
  not the yes Article 7 asks for before deleting, purging, a bulk parameter write, a family reload, a
  workset change or anything touching a link. The chat still asks for that first.
- **A publish is asked too, and Discard cannot take it back.** An export, a save or a sync done inside the
  run is done; the question says so in as many words when the request was `run_fragment_publish`. Ctrl+Z
  never undid those either (D-106).
- **`revit_apply_move` keeps its own preview** - a one-use approval re-counted before it writes.
- **Proofs are not asked.** `tools/batch-prove.py` sends `--write` and never `--apply`, so every proof run
  is rolled back as a preview and no question appears. The task that asked for this said batch write
  runs would be prompted; reading the tool says they are not. A command-line `--write --apply` is asked.

### What it accepts

- **While the dialog is up Revit takes nothing else.** A second request is answered *"Revit is busy"*
  after `revit.busyTimeoutSeconds`, as for any open dialog.
- **An answer given after the bridge stopped waiting reaches no chat.** The banner and the audit line
  record it; the chat was told to ask the modeller which they chose.
- **A job slow BEFORE the question opens** - still running when the first operation timeout ends - is
  answered *"still running"* as before; the modeller's answer still decides the model.
- **D-60 calls 500 the default of a setting.** No setting reads it yet; it is a constant in
  `HeronKeepQuestion`, and making it one is a later change.
- **If Revit's report never reaches the collector, nothing is asked** and the verdict says *"Revit
  reported nothing added, changed or deleted"* over a change that plainly happened. That is visible on
  the first run, and NEEDS-CHECKING ET1 is the run that shows it.

### Alternatives considered

- **D-55's preview through the chat** - run, roll back, show the counts, run again with `apply`. Two runs,
  a model that can move between them, and the modeller asked in the chat about elements they cannot see.
- **A request field saying whether to ask.** Golden Rule 19: a caller that can say "keep without asking"
  holds a permission level nobody granted it.
- **Ask in the chat before calling `revit_change`.** The chat cannot show the elements, and Article 9
  wants what will change and how many, which only the run can say.

### Consequences

- [Article 9](../../HERON_CONSTITUTION.md) and its Enforcement row, [Golden Rule 17](../14-golden-rules.md),
  D-106's bullet *"D-99 stands"*, the `revit_change` description and `host.chat` all say this now; every
  chat reads Article 9 with it.
- The Changes window's first promise reads *"You see each change in Revit first, and nothing is kept until
  you choose Keep."* The padlock's fallback and the bridge status window's *"previews first"* are true
  again and were left word for word.
- **The job's dialog watch never answers this question.** Merged beside Group EL's `HeronDialogWatch`,
  which declines every Revit dialog a job meets: the question is shown inside `HeronDialogWatch.HeronAsks()`,
  and the run is kept only after the watch is asked again, because showing the change commits a
  transaction of its own. NEEDS-CHECKING ET12 watches for it.
- **Nothing here has run in Revit.** It compiles for 2020 to 2027 and the Revit-free half is proved by
  `tests/test_keep_question.py`; [NEEDS-CHECKING Group ET](../NEEDS-CHECKING.md) holds the runs that would
  prove the rest, including whether `IsolateElementsTemporary` needs a transaction at all.
