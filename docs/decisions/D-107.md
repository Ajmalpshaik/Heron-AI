### Context

[D-106](../DECISIONS.md#d-106--admin-and-publish-each-get-a-switch-of-their-own-and-only-the-owner-turns-them-on) gave
Publish a switch of its own. Two fragments that write a file out of the model -
`export-model-to-ifc` (IFC) and `export-views-to-dwg` (DWG) - declared `risk: MODIFY`, while every other
export declares `PUBLISH`. So they ran under Changes alone, the Publish switch never saw them, and a
batch walking the library alphabetically could reach both. FRAGMENT-ISSUES section 6 found the mismatch
on 2026-09-19 and said one of the two levels was wrong; [Q-59](../OPEN-QUESTIONS.md) put it to the owner.

### Decision

**Both are `PUBLISH`.** One line in each card. They now travel as `run_fragment_publish`, so Revit runs
them only while the owner's Publish switch is on, with Changes, and no batch, `prove` or setup step
sends them. Both were DRAFT, so no proof moves.

### Consequences

- **Every export in the library is guarded by the Publish switch**, and the owner's rule that a batch
  never reaches `export-*` now holds for all of them. `tests/test_admin_publish.py` no longer names any
  exception: an `export-*` that a batch can reach fails it.
- **Proving either one** needs `validate --allow-publish --write` and the Publish switch on, as every
  other export does. The three job files in `tools/jobs/` that list `export-views-to-dwg` stay as they
  were, as records; run today, each refuses it before anything is sent, because `batch-prove` passes
  `--write` and never `--allow-publish`.
