# D-99 — A change asked for in a chat is kept at once, with no preview, and Article 9 says so

> One record of [the decision log](../DECISIONS.md). It was given its own file on 2026-09-23 so that it
> can be read alone; **its words are unchanged, only its links were re-pointed.** Decisions are
> append-only: to change one, write a new decision that supersedes it.

**Status:** Accepted · **Date:** 2026-09-23 · **Source:** Ajmal PS, 2026-09-23, asked as decision D1 of the earlier-brain plan
**Amends:** [Constitution Article 9](../../HERON_CONSTITUTION.md) · **Breaks, on the record:** [Golden Rule 17](../14-golden-rules.md) · **Keeps:** [D-55](../DECISIONS.md#d-55--a-fragments-preview-is-the-run-itself-rolled-back), [D-19](../DECISIONS.md#d-19--writing-is-off-by-default-until-the-write-path-has-met-a-real-revit)

### Context

`revit_change` sends every fragment to Revit with `"apply": "true"`, so what it does is **kept at once,
with no preview in front of it** ([`heron_mcp_server.py`](../../mcp/server/heron_mcp_server.py)). It was
written that way on 2026-09-15 at the owner's instruction, and ran the same day.

[Article 9](../../HERON_CONSTITUTION.md) said the opposite: *any `MODIFY` operation that does not use a
`PRODUCTION` fragment requires a preview the user has accepted.* No fragment is `PRODUCTION`, and
[Golden Rule 17](../14-golden-rules.md), which Article 9 comes from, says the same. **No decision recorded
the exception**, so for eight days the code and the Constitution disagreed and nothing said which one
was right. The earlier-brain comparison found it on 2026-09-22 (its finding H3).

**The preview was never missing for want of a way to take one.** [D-55](../DECISIONS.md#d-55--a-fragments-preview-is-the-run-itself-rolled-back) made a fragment's preview
*the run itself, rolled back*, and the add-in does exactly that for any run sent without `apply`. This
path simply never sends one.

### The question, as it was put

> *"When you ask Heron to change the model, revit_change keeps the change straight away, with no
> preview. Heron's own rulebook (Constitution Article 9) says: show a preview first - what will change
> and how many - and keep it only after you say yes. Which do you want: (A) add the preview, so every
> change shows its counts first and waits for your yes - I recommend this; or (B) keep changing
> straight away, and write that down as an official exception to Article 9?"*

**He chose B**, with A offered first and recommended.

### Decision

**A change asked for in a chat, through `revit_change`, is kept at once, with no preview.** Article 9
now carries this as its one recorded exception. Golden Rule 17 is broken here **on the record** — which
is what [14](../14-golden-rules.md) asks of a rule that has to be broken — and the rule says so under its
own text.

**The reason is his, and it is older than the question.** Reading [D-19](../DECISIONS.md#d-19--writing-is-off-by-default-until-the-write-path-has-met-a-real-revit) back on 2026-09-06 he
described the loop he works in: *"I need to test — then if that works okay it's proven, next time it
will work. And if not working, or it did wrong, I can undo, then again I can tell what I need
exactly."* That loop rests on **undo**, not on a preview.

### What stands in for the preview — each one read in the code on 2026-09-23

| | Where |
|---|---|
| **The owner's Changes switch.** Off by default, and read inside the add-in, never by the client | `HeronPermissions` — [D-19](../DECISIONS.md#d-19--writing-is-off-by-default-until-the-write-path-has-met-a-real-revit) |
| **Publish and Admin refused** before any code is read or any session is bound — sync with central, save, export, create a workset | `risk_refusal`, called first in `revit_change` since #299 |
| **One named undo entry per call**, and on any failure the whole call rolls back | the `TransactionGroup` in `RevitFragment.Run` — Article 8, [Golden Rule 16](../14-golden-rules.md) |
| **Aimed at the pinned model**, and refused before the transaction group opens when the target is a different one | `document`, `documentPath` and `expectProject` — [D-74](../DECISIONS.md#d-74--a-write-is-aimed-at-the-model-it-was-told-about-not-guarded-against-the-one-in-front), Article 12b |
| **Said afterwards**: what the fragment left, the add-in's own verdict, any value it ignored, and a warning line when the fragment is not `PROVEN` | `revit_change`'s reply |
| **Said to every chat before anything happens**: a change is taken back with Revit's own Undo, never with a second, reversing change — and Articles 7, 8 and 9 as they now read | the MCP server's instructions, assembled from the Constitution by `brain/heron_instructions.py` (`host.chat`) |

### What this does NOT change

- **Article 7 stands, and on this path nothing in code enforces it.** Deleting elements, purging, bulk
  parameter writes, family reloads, workset changes and anything touching a linked model still need
  explicit confirmation for that specific operation. With Changes ON, `revit_change` reaches
  `DELETE_ELEMENTS`, `UNLOAD_LINKS` and `SET_ELEMENT_WORKSET` with the switch as the only gate: the
  add-in asks no question and the server asks none. **The one carrier is the instruction every chat is
  now given.** That gap is older than this decision — [FRAGMENT-ISSUES row 5b-161](../FRAGMENT-ISSUES.md).
- **`revit_apply_move` keeps its preview**, its one-use approval and its re-count before it writes
  (Article 12c).
- **Every other writer is held to Article 9 as it stands.** This exception names one tool. An agent, a
  skill runner or a new tool that changes a model needs a preview, or a decision of its own.
- **The preview is one flag away.** The add-in rolls back any run sent without `apply` ([D-55](../DECISIONS.md#d-55--a-fragments-preview-is-the-run-itself-rolled-back)),
  and the command line proves fragments exactly that way. Going back is a new decision and a small
  change in the server.

### Consequences

- [Article 9](../../HERON_CONSTITUTION.md) and [Golden Rule 17](../14-golden-rules.md) both name this
  decision, and the Constitution's Enforcement table says where each half is actually enforced: the
  move's preview in the add-in, `revit_change` by this exception, and Article 7 on `revit_change` by
  the switch alone.
- Every chat is now told the rules that apply to it, including this one, because the MCP server
  passes the host its instructions — assembled from the Constitution, never copied
  ([`brain/instructions/host.chat.yaml`](../../brain/instructions/host.chat.yaml)).
