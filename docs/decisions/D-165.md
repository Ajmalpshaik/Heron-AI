### Context

Checked first, as asked. Heron's other checks already keep missing data out of their passes: the grounding
check `heron_check` marks a claim whose source is not in the packet UNRESOLVED and prints its denominator
(`brain/heron_ground.py`, `Report.checked`, `Report.lines`); the final gate `heron_qa` refuses a required
check with no result (`brain/heron_qa.py`, `CHECK_MISSING`); the BIM QA agent reports every aspect as
checked, skipped or cannot be checked here, and keeps a parameter's populated, empty and absent apart
(`brain/heron_modelqa.py`, `check`, `parameters`).

The QA checklist did not. A check that ran and got back no value - the output absent, `(null)`, or text -
was **NOT RUN**, the same word as a check that was never sent. It was never a pass, but the modeller could
not tell *Heron could not ask* from *the model has no data*, and the run said nothing of how much it had
decided. Worse, a check's rule is on one output, so `failures == 0` **passed** while the same fragment
reported 37 of 43 elements it could not read: the field's 100%-with-86%-missing, in Heron.

### Decision

1. **A fourth answer, NO DATA - *could not decide, data missing*.** A check that was read but whose rule's
   output came back absent, empty or not a number is NO DATA, never NOT RUN. It is never counted as a pass
   and never as a fail. NOT RUN keeps its meaning: nothing was read. Its colour is the brand's Warning.
2. **Two optional coverage outputs on a check**, each named by the chat from the card and checked when
   saved - an output the card declares that reads as a number: `missing`, the count of elements the check
   could not read the value of, and `applicable`, the count it looked at. **A rule that holds is NO DATA**
   while `missing` is above nought, while `applicable` is nought, or while either does not come back as a
   number. **A FAIL stays a FAIL**, because a failure found is real. The row says *checked 6 of 43
   element(s), 37 with no data*.
3. **A coverage line beside every pass count**, in the chat, on the Companion page and in the CSV:
   *"Coverage: 2 of 4 check(s) decided, 1 with no data, 1 not run."* - checked, applicable, missing.
4. **NO DATA is never a change.** Against the last run it is NOT COMPARED, never FIXED or NEW; so is any
   state other than PASS and FAIL.

### What is not known

Nothing of it has run in Revit. It runs without Revit in `tests/test_checklist_no_data.py` - all data, some
missing, all missing - whose checks were seen to fail on the code before the change, and in
`tests/test_checklists.py` and `tests/test_checklist_tool.py`.
[NEEDS-CHECKING Group NV](../needs-checking/group-nv.md) NV18 to NV20 hold the runs. Which card's output
counts what it could not read is the chat's to read off the card, one check at a time; no card is changed.

### Alternatives considered

- **Keep NO DATA inside NOT RUN.** It was never a pass, but two causes fixed in two different places read
  as one.
- **Let Heron find a card's coverage outputs by their names.** The cards name them `notChecked`,
  `unreadable`, `withoutParameter`, `scanned`, `elementsRead` and more; a guess at which means what is the
  guess D-01 forbids.
- **A percentage beside the count.** *100%* is the figure that hid the missing data; a count of what was
  decided, of how many, cannot be read as a grade.
