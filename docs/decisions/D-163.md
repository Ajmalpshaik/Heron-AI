### Context

What Heron changed in a model could be read back in the chat (`heron_run_record`) or on the Companion page,
never in Revit itself - where the modeller is looking. The comparison D-155 came from had an activity pane
listing each AI change with Select, Zoom and Undo.

### Decision

1. **A dockable pane, *Heron Activity*,** opened from the Heron menu's new **Activity** row - never a ribbon
   button (D-150). Registered in `OnStartup` in a `try` of its own: its fault costs the pane, never the
   add-in.
2. **It lists the newest 15 run records** - the record the dispatcher already keeps for every change a chat
   makes - each with its fragment, model, time, outcome in words (*Kept*, *Tried, nothing kept*, *Discarded
   by you*, *Nothing changed* ...) and its counts. Re-read every four seconds while it is shown. No second
   list: the record is the source. A record from before this says *Outcome not recorded*.
3. **Select and Zoom** send a new operation, **`show_elements`** - EXECUTE, fixed code, no transaction - with
   the change's added and changed element ids (never a deleted one, at most 500). It selects them, and zooms
   to them when asked, **only in the model the change was made in**; elements gone since are skipped and
   counted, and only when none remain is it refused.
4. **Undo** is on the newest change alone, and only when it was kept. It sends D-157's `undo_last`, so Revit's
   own Undo is posted only while that change is still the top of the undo list - and it needs Changes on.
5. **The pane never calls the Revit API.** Every button hands its request to the add-in's **one dispatcher**
   (`HeronApplication.DispatchFromPane`, D-09) from a background thread - the same queue, `ExternalEvent`,
   gate, model hold and audit trail a chat's request meets - and the answer comes back to the pane's status
   line in the add-in's own words. Each request carries `"claim": "no"`: it looks at the model hold and
   never takes a model from a chat (D-141).
6. **Each run record now carries its outcome at the top** (`kind`), where the pane's reader can read it.

### What is not known

None of it has run in Revit. It compiles for 2020 to 2027, every Revit member it calls exists in every
release, its colours are the brand's, and what it lists runs without Revit in
`tests/Heron.Activity.TestHost`; `tests/test_activity_pane.py` reads the wiring and fails on the code before
the change. **Whether the pane draws and docks, whether a request from it stays responsive while Revit is
busy, and whether the selection lands** are [NEEDS-CHECKING Group NW](../needs-checking/group-nw.md)'s.

### Alternatives considered

- **Call the Revit API from the pane's click.** Outside the API context - the crash the skill names.
- **A second `ExternalEvent` for the pane.** D-09: one event, one queue, one handler.
- **A list of its own, written as changes happen.** A second account of the same work, which could
  disagree with the run records.
