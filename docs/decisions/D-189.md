# D-189 — A development session never pulls into the main Heron folder

> One record of [the decision log](../DECISIONS.md). Decisions are append-only: to change one, write a new
> decision that supersedes it.

**Status:** Accepted · **Date:** 2026-11-20 · **Accepted:** Ajmal PS, 2026-11-20, in conversation, on pull request [#1107](https://github.com/Ajmalpshaik/Heron-AI/pull/1107): *"no to B1"*
**Settles:** item B1 of the field report [#1058](https://github.com/Ajmalpshaik/Heron-AI/issues/1058)
**Keeps:** [Group EU](../needs-checking/group-eu.md)'s guard - a chat whose Heron code changed under it stops and asks to be reopened
**Affects:** [`AGENTS.md`](../../AGENTS.md) "How to work" - no code

### Context

On 2026-11-19 a development session ran `git pull --ff-only origin main` twice in the owner's main Heron folder
while a modeller chat opened from that folder was mid-job on a real Revit 2020 model. Group EU's guard then refused
the chat's next change - *"Heron's code changed since this chat started ... Close and reopen the chat."* The guard
did what it is for; the modeller's job stopped half-way.

### Decision

1. **A development session never pulls, checks out, merges or rebuilds in the main Heron folder** - the folder a
   modeller's chat is opened from. It works in its own worktree or its own clone.
2. **Bringing the main folder up to date is the owner's own step**, done when no modeller chat is open from it.

### Alternatives considered

- **Pull only after checking that no Heron server runs from that folder.** Not taken: a check can miss a chat about
  to start, and the cost of a miss is a modeller's job stopped half-way.
- **Name the changed commit in the guard's refusal.** Not taken here: with rule 1 kept, the code under a chat changes
  only by the owner's own step.

### Consequences

- AGENTS.md says it under "How to work".
- No code changed; Group EU's guard stays as it is.
