### Context

Until 2026-11-20 an AI that found a mistake in Heron, or a check owed on a real Revit, wrote it into a register -
a FRAGMENT-ISSUES row, a NEEDS-CHECKING check, an open question - and only later did a session turn it into a
GitHub issue. On 2026-11-16 the owner had every open row moved into small issues of one kind each, because he
works through GitHub issues one at a time, closing each when it is done. Rows written after that started `OPEN`
again and waited for someone to move them; on 2026-11-20 several written that day were still waiting.

The registers cannot be replaced by issues: `next-id.py` takes ids from them, `open-defects.py` and the owner's
queue count them, `archive-fragment-issues.py` moves finished rows out of them, and the gates check their links.

### Decision

1. **Every new finding becomes a GitHub issue at once** - a FRAGMENT-ISSUES row, a NEEDS-CHECKING check or
   group, an open question.
2. **The register stays the permanent record.** The entry is written there AND its issue opened - or the entry
   added to an open issue of the same subject and kind - **in the same change**. Its line names the issue from
   the day it is written: a row's state begins `MOVED TO ISSUE #N <date>`, its old state after `Was:`; a group
   or a question carries *Tracked as GitHub issue #N since <date>* under its heading.
3. **The issue is written in the plain-words shape the owner's issues already use**: what happened, what is
   expected, the kind line, a checkbox linking the entry, a ready prompt, and *Close this issue when* - with the
   label that fits: `bug`, `needs-revit-run`, `question` or `documentation`.
4. **It is automatic.** [`tools/open-issue.py`](../../tools/open-issue.py) prints the issue for an id, opens it
   or extends one with `--create`, and writes the number back; it is a dry run unless told, and sends only the
   entry's text and the words given - never model data or anything private. The
   [`heron-issue-recorder`](../../.claude/agents/heron-issue-recorder.md) agent takes the id from `next-id.py`,
   writes the entry, looks for an open issue on the same subject, and opens or extends it with the tool.
5. **Where GitHub cannot be reached** - some cloud containers - nothing is half-written: the entry stays `OPEN`,
   the pull request lists the issue under **Issues to open**, and the coordinating session opens it and writes
   the number back with `open-issue.py <id> --record N`.
6. **Every place that tells an AI to record a finding now says: the entry AND its issue, through
   `heron-issue-recorder`.**

### Alternatives considered

- **Issues only, no register entry.** Not taken: the tools and gates that read the registers would lose sight
  of what is owed, and the archive would have nothing to keep.
- **Append each new row to the tables of `fragment-issues/ISSUES.md` as well.** Not taken: one table every
  branch appends to is one merge conflict in every merge - the reason a new 5b row is a file of its own
  ([row 5b-1585](../fragment-issues/row-5b-1585.md)). Those tables map what was moved before this decision; since
  then an entry's own line is its link.
- **`gh issue create`.** Not taken: it asks GitHub's GraphQL, which a Claude Code cloud session refuses; the
  tool uses `gh api`'s REST routes, as `next-id.py` does for pull requests.

### Consequences

- A pull request that adds a register entry carries the issue's number in it, or lists the issue under
  **Issues to open** - never neither.
- `open-defects.py` counts a row moved the day it is written as moved, not open, as it counts the rows moved
  on 2026-11-16.
- Nothing in Heron's runtime changed: no fragment, no C#, no Revit behaviour.
