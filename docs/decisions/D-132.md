# D-132 — Off Windows the Heron server serves its library alone, and no Revit tool

**Status:** Accepted · **Date:** 2026-10-17 · **Accepted:** Ajmal PS, 2026-10-17, in conversation: *"yes"*, to Q-67 put to him in plain words · **Answers:** [Q-67](../open-questions/tier-2.md)
**Keeps:** [D-02](../DECISIONS.md#d-02--mcp--add-in-transport-named-pipes) - the bridge is a Windows named pipe, and nothing here reaches it · [D-01](../DECISIONS.md#d-01--execution-host-claude-code-plugin) · every tool on Windows, exactly as before
**Affects:** [`heron_mcp_server.py`](../../mcp/server/heron_mcp_server.py), [`heron_tools.py`](../../mcp/server/heron_tools.py) (`LIBRARY`), [`AGENTS.md`](../../AGENTS.md), [38 §4](../38-the-cloud-environment.md), the [`heron-session`](../../.claude/skills/heron-session/SKILL.md) start-up line, [`tests/test_mcp_stdio.py`](../../tests/test_mcp_stdio.py), [`tests/test_tool_registry.py`](../../tests/test_tool_registry.py)

### Context

The server's `__main__` exited **2** on any system but Windows - *"Heron's bridge uses Windows named pipes.
Revit is Windows-only."* - before it served a tool. So a cloud session listed no `heron` tool at all: not the
Revit tools, which cannot work there, and not the library tools, which never touch Revit. The
`heron-fragment-author` agent is given `heron_lookup`, `heron_resolve` and `heron_capabilities`, and is told to
search the library before it writes a tool; in a cloud session it could not. [Row 5b-162](../fragment-issues/section-5b-rows-151-175.md)
left it as *"a design question nobody has asked"*, and nothing in this log, the open questions or the
Constitution decided it. It was asked as Q-67, with a recommendation.

The one thing a yes must not break is [`AGENTS.md`](../../AGENTS.md)'s test: *"If no `heron` tools are listed,
Heron is not connected."* A library that answers where no Revit can be would read as connected.

### Decision

1. **Off Windows the server starts and registers only `heron_tools.LIBRARY`**: `heron_capabilities`,
   `heron_lookup`, `heron_method`, `heron_resolve`, `heron_standards` - the five the owner said yes to.
   Every other tool is **not registered**, so it is never listed: never listed and then refused, never a hang.
   A Revit tool asked for anyway is refused by the SDK at once as unknown.
2. **The host's own list says there is no Revit here**: no `revit_` tool appears. The server's instructions
   open with *"No Revit on this machine (it is not Windows)"*, and a lookup's version line says the same
   instead of *"No Revit is connected"*, without looking for one.
3. **On Windows nothing changes.** Every tool is served, the Companion keeper starts, and the code path is the
   one it was. Off Windows the Companion keeper does not start: it serves a button in Revit.
4. **Only when run as the server.** A test or tool that imports the module is served every tool on any system,
   as before - `test_mcp_serves` and `heron_tools --sizes` depend on it.
5. **A tool joins `LIBRARY` only by a decision**, declared READ with no operation - a tool with an operation
   reaches the add-in, and there is none. `tests/test_tool_registry.py` holds that, and that every Heron tool
   the fragment-author agent is given is on the list.
6. **AGENTS.md's test becomes the one that still holds**: no `revit_` tool listed means no Revit here. The
   `heron-session` start-up line off Windows says the library is there and Revit is not.

### Alternatives considered

- **Leave it.** Every cloud session, and the fragment-author agent in it, searches the library with `grep`
  instead of the ranked lookup a modeller's chat gets, so the two can disagree on what exists - which is how a
  second tool for the same job gets written.
- **List every tool and have each Revit tool refuse.** Honest per call, but a list that says Revit is here
  when it is not - the trap AGENTS.md's sentence exists to catch.
- **Serve every tool that sends nothing to Revit.** More could qualify, but the owner was asked about five; a
  wider list is a wider claim, made one decision at a time.

### Consequences

- A cloud session can search, resolve and read a method the way a modeller's chat does. Nothing that needs a
  model becomes possible there: proving, loading the add-in and every `revit_` tool stay on the owner's PC.
- `tests/test_mcp_stdio.py` starts the real server over stdio off Windows and fails if it does not start,
  if the list is not exactly `LIBRARY`, if a `revit_` tool appears, if a search does not answer inside the
  deadline or does not say there is no Revit here, or if a Revit tool is not refused at once. It runs where
  the MCP SDK is installed; CI's hosted runner has none, so there it exits 3, as before.
- **Seen in a real cloud session's host list, 2026-10-17.** The session that built it was restarted on this
  branch (`f82be5da`), and its host listed `heron` with exactly the five `LIBRARY` tools and no `revit_` tool;
  the server's instructions opened *"No Revit on this machine (it is not Windows)"*; and `heron_lookup` asked
  *"select all the ducts"* answered `SET_SELECTION` and *"No Revit on this machine (it is not Windows), so the
  version filter did not run."* Nothing on Windows was run.
