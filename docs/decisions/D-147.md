### Context

The Companion's Model Dashboard reads the model once, when asked, and its Refresh reads it again only when
the modeller presses it - README rule 3, so the page never queues work on Revit's thread by itself. That
leaves the modeller with no way to tell whether what the page shows is still the model: a duct drawn or
deleted after the read changes nothing on the page. The plan for the dashboard asked the owner whether the
add-in may watch for changes; [D-09](../DECISIONS.md#d-09--revit-thread-marshalling-externalevent) says
`Idling` is used only for a liveness heartbeat, and [D-108](../DECISIONS.md#d-108--the-modeller-can-see-and-edit-herons-work-in-a-local-companion-page-and-the-chat-stays-the-only-place-to-talk-to-heron)
amended that for the selection watch alone, so a change watch needed the owner's word.

### Decision

1. **The add-in subscribes to `DocumentChanged`** at startup and unsubscribes at shutdown, on every release
   2020 to 2027 - one path, no version branch.
2. **The event only counts.** Per model - keyed by its title and path - a number goes up by one per
   committed change. No element is read, no id list is taken, no file is written in the event, and nothing
   is held that D-09 forbids holding (no `Document`, no `Element`).
3. **The count reaches the page through the live file, on the existing throttled `Idling` check.** The
   count for the model in front is part of that check's fingerprint, so the file is written at most once a
   second while the count moves, as `"changes": N` - `null` with no model.
4. **The page compares; Revit is asked nothing.** The dashboard keeps the count at its read; on the state
   poll it already makes, the page shows *the model has changed in Revit since this read - press Refresh*
   once the live count is higher for the same model. **It never refreshes by itself.**
5. **Heron's own changes count too** - a colour applied from the page, a change from the chat - because the
   page then shows the model as it was before them.

### Consequences

- An add-in redeploy is needed before the note appears; until then the live file carries no `changes`,
  `live_changes` reads None, and the page shows nothing - never a wrong note.
- A change committed in the moment between the read and the count being taken can be missed; the next
  change shows the note. A change just before the read can show the note once when nothing moved after.
  Either errs towards *press Refresh*, never towards a stale page called current.
- **Not run in Revit** - NEEDS-CHECKING group JT row JT28.
