# D-108 — The modeller can see and edit Heron's work in a local Companion page, and the chat stays the only place to talk to Heron

### Context

The owner asked on 2026-09-29 for a window beside Revit that shows the live selection, lists every
Heron call the chat makes, and gives the modeller a table the chat opens in one call - edited and applied by
the modeller, with no chat involved and no tokens spent. The design is [40](../40-heron-companion.md).

[D-105](../DECISIONS.md#d-105--talk-is-removed-and-the-modeller-works-with-heron-in-the-chat-only)
had closed that door two days earlier: after Talk lost a message, *"the modeller works with Heron in
the Claude chat, as D-01 chose"*. [40 §2](../40-heron-companion.md) listed that as the first conflict
and put it to the owner before any code. The owner answered yes.

### Decision

1. **Each chat's MCP server may serve a Companion page**, on request, on `127.0.0.1` only, on a port
   Windows picks, protected by a per-session secret, a `Host` check, an `Origin` check and a custom
   header, and never framed ([40 §11](../40-heron-companion.md)).
2. **The page never sends anything to Claude or any AI**, never reads a Claude login, token or API
   key, and loads nothing from the internet. The chat stays the only place the modeller talks to
   Heron.
3. **Revit still opens no socket** ([D-02](../DECISIONS.md#d-02--mcp--add-in-transport-named-pipes)
   stands). For the live view the add-in writes a small read-only state file - model, view,
   selection counts - and the page reads that file. **Nothing polls Revit through the pipe for the
   page.**
4. **The selection is watched by a check on `Idling`, on every release, at most every 200 ms,
   writing only on a change.** That is the amendment to D-09; `Idling` is used for nothing else.

   **Revised the same day, before this decision reached `main`.** As first written, this point used
   Revit's `SelectionChanged` event on 2023 and later and `Idling` only on 2020-2022, because the event
   is in the 2023-2027 reference assemblies and absent from 2020-2022 (measured,
   [40 §2 C3](../40-heron-companion.md)). Building it that way needed a version branch, and
   `tools/check-api-surface.py` - which reads the one 2024 build against every release - reported the
   event missing on the three older ones. The house rule is a member every release has over a branch
   that hides one that does not ([revit-version-support](../../.claude/skills/revit-version-support/SKILL.md)),
   and `Idling` is on all eight. The cost is a cheap check five times a second while Revit is idle
   instead of an event; NEEDS-CHECKING group BK measures it.
5. **A change from the page takes exactly the path `revit_change` takes**: the same operation
   (`run_fragment_write`), the add-in's gate, the Changes, Admin and Publish switches, the pinned
   model, one `TransactionGroup` and one entry in Revit's undo list. No second write path, no new
   add-in operation, `write.enabled` still off by default.
6. **The table is the preview [Article 9](../../HERON_CONSTITUTION.md) requires**: each row shows its
   current and new value, the Apply button carries the count, and pressing Apply is the acceptance.
   [Article 12c](../../HERON_CONSTITUTION.md) applies **as it stands** - whether a stale row refuses
   the whole Apply or is skipped is [40 §18](../40-heron-companion.md) question 2, and this decision
   does not answer it.
7. **Taking a change back is Revit's own Ctrl+Z.** No button makes a second, reversing change.

### Why this is not Talk, and what D-105 point 4 asked

D-105 said a second attempt at Talk must first answer why its listener stopped with a message waiting.
**This is not a second attempt at Talk**: the Companion carries no words anywhere, so there is no
message to take and lose. Its failures are a page that stops updating or an Apply that is refused,
and both are visible on the page. Talking to Heron from Revit stays removed.

### What it accepts

- **The page lives as long as the chat that opened it.** Claude Code closing ends it; an unapplied
  table is lost, and nothing half-applied, because nothing is sent before Apply.
- **Claude is not told about the modeller's edits** unless it asks - that is what saves the tokens -
  so it must re-read before acting ([Golden Rule 21](../14-golden-rules.md)), as it already must.
- **The Apply button is a person's action by design, not proof of a person.** A program or agent
  running as the same Windows user could press it, as it could press the Changes switch. The Changes
  switch inside Revit is the gate either way.
- **Two of the owner's chats share one client id**, so an Apply while another chat is mid-request can
  lose its answer. The page then says to check the model and never retries.

### Alternatives considered

- **One long-lived Companion process that owns the pipe for everybody.** Rejected: every existing
  Revit tool would change transport, a new always-running program would need installing, and D-22's
  refusal of a second chat would stop working ([40 §4.1](../40-heron-companion.md)).
- **The page asks Revit through the pipe.** Rejected: the READING banner would flicker, Revit's own
  thread would be kept busy, and a second client displaces the chat's pipe - the reason D-104 already
  rejected polling ([40 §4.2](../40-heron-companion.md)).
- **Keep D-105 as it was.** Not the owner's choice.

### Consequences

- **Easy:** small edits without a message to Claude, and a view of what Heron is doing.
- **Hard:** a local web server inside the MCP process, which must never print to stdout; an add-in
  change and a Revit restart for the live file; two new fragments, starting `DRAFT`.
- **Still open, one question at a time:** [40 §18](../40-heron-companion.md) questions 2 to 7.
- **Owed:** a NEEDS-CHECKING group when Phase 1 is built, every row NOT_VERIFIED until run on a named
  model.
