### Context

Two orders were being read as one. *Value to one user* runs project → company → regional → international,
because the AI knows least about the first. **The owner corrected the second on 2026-09-11:** what Heron
should know *out of the box* is a question about the product, not about one person, and it runs the other
way. A company standard helps one company; ISO 19650 helps every user of the product and is stable across
projects.

And *first priority to load* had started to read as *ships in the box*. ISO sells ISO 19650 the way NFPA sells
NFPA; a standard bought per seat that rode in Heron's download would reach everyone who downloads it.

R-87 - no knowledge store is ever committed or shipped - was held only by the file layout: stores live in
Heron's home, outside the checkout ([D-135](../decisions/D-135.md)), so it could not happen today. The release
builder zips what is on the disk rather than what git tracks, so a store a session made inside the checkout
would have ridden in the download, and nothing said so.

### Decision

1. **The out-of-box order is BIM and ISO standards first, regional next, company last.** Wherever Heron tells
   a new installation what knowledge to load, it says it in that order. Nothing does that yet; this is the
   order it will use. It is not a ranking rule: inside a question, a project standard still outranks the company
   default ([20 §2](../20-knowledge-trust-and-conflict.md)), and a company BIM standard is what a modeller uses
   daily ([R-93](../work-notes/plans/rag/01-requirements.md)).
2. **No standard is ever bundled with Heron.** Priority means *load it first on your own PC*, never *ships in
   the box*. A standard reaches Heron by its owner putting in the copy they hold.
3. **No knowledge store is ever committed to the repository or shipped with Heron** - a rule now, not an
   accident of where files live. The download refuses, by name, any file shaped like a store or a source
   document, and a suite fails if git tracks one.

### Consequences

- `tools/build-release-assets.py` stops the release on a `.db`, `.sqlite`, `.sqlite3`, `.heron-db` or
  `-documents.jsonl` file, and on a `.pdf`, `.docx`, `.doc`, `.xlsx`, `.xls`, `.pptx` or `.ppt`, anywhere in
  what it packs - the same document shapes `.gitignore` already blocks from the repository.
- `tests/test_knowledge_rules.py` fails if git tracks a file shaped like a store.
- Nothing ranks differently: clause 1 orders what is asked for, not what is answered.
