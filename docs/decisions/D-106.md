# D-106 — Admin and Publish each get a switch of their own, and only the owner turns them on

> One record of [the decision log](../DECISIONS.md). It was given its own file on 2026-09-28 so that it
> can be read alone; **its words are unchanged, only its links were re-pointed.** Decisions are
> append-only: to change one, write a new decision that supersedes it.

**Status:** Accepted · **Date:** 2026-09-28 · **Source:** Ajmal PS, 2026-09-28, after Heron refused ADD_PROJECT_PARAMETER when he asked for two project parameters
**Supersedes:** the rule that Publish and Admin are *"not reachable in Phase 0 or Phase 1 at all"* - it lived in `HeronPermissions.Allows()` and the client's `risk_refusal`, never in a decision - and so the row *"Publish and Admin refused"* in [D-99](../DECISIONS.md#d-99--a-change-asked-for-in-a-chat-is-kept-at-once-with-no-preview-and-article-9-says-so)'s table, which now reads *refused unless the owner's switch for that level is on* · **Keeps:** [D-19](../DECISIONS.md#d-19--writing-is-off-by-default-until-the-write-path-has-met-a-real-revit), [D-99](../DECISIONS.md#d-99--a-change-asked-for-in-a-chat-is-kept-at-once-with-no-preview-and-article-9-says-so), [Constitution Articles 7 and 10](../../HERON_CONSTITUTION.md), [Golden Rule 19](../14-golden-rules.md)

### Context

On 2026-09-28 the owner asked Heron for two project parameters. `ADD_PROJECT_PARAMETER`
(`FRG-PAR-010`) is declared `risk: ADMIN`, and the answer was a refusal:

> *"add-project-parameter is declared risk: ADMIN, and Heron does not run those yet - HeronPermissions
> puts Publish and Admin out of reach for Phase 0 and Phase 1. Nothing was sent to Revit."*

**The rule had never been decided; it was code.** `HeronPermissions.Allows()` returned false for any
level above Modify, under a comment saying Publish and Admin *"are not reachable in Phase 0 or Phase 1
at all"*. The add-in's gate reads an operation's risk from the tool registry by name, and the only
operation that ran a changing fragment was `run_fragment_write`, declared Modify - so an `ADMIN` or
`PUBLISH` fragment could only ever have travelled under the Modify gate. That is why the client refused
to send one at all ([FRAGMENT-ISSUES](../FRAGMENT-ISSUES.md) rows 9 and 5b-155), and why
[D-99](../DECISIONS.md#d-99--a-change-asked-for-in-a-chat-is-kept-at-once-with-no-preview-and-article-9-says-so) could
list *"Publish and Admin refused"* among the things standing in for a preview.

**The owner decided:** Admin and Publish become reachable, but **only through switches that he alone
turns on in Revit - exactly like the Changes switch.** He asked for both at once: Publish is built the
same way as Admin.

### Decision

1. **Two switches, beside Changes on the ribbon**, each a setting in `heron.config`:

   | Switch | Setting | Lets through | Which fragments that is |
   |---|---|---|---|
   | **Admin** | `admin.enabled` | the operation `run_fragment_admin`, declared **ADMIN** | every card declaring `risk: ADMIN` - changes to how the project is set up: a project or global parameter, a workset, a new family document. Derive them: `grep -l '^risk: ADMIN' brain/fragments/*/fragment.yaml` |
   | **Publish** | `publish.enabled` | the operation `run_fragment_publish`, declared **PUBLISH** | every card declaring `risk: PUBLISH` - what sends something out of the model or saves it: an export, a print, a save, a sync with central. Derive them: `grep -l '^risk: PUBLISH' brain/fragments/*/fragment.yaml` |

2. **Both are OFF by default** and are read fresh on every call, as `write.enabled` is. A settings
   file that does not mention them means off.
3. **Each also needs Changes (`write.enabled`).** Admin or Publish on with Changes off is refused, and
   the refusal says Changes is what is off. The two are **independent of each other**: Admin on says
   nothing about Publish.
4. **The operation carries the risk; the request never does** ([Golden Rule 19](../14-golden-rules.md)).
   The add-in declares one operation per level. The client picks it from the fragment's **own card, on
   its own disk**, and the add-in's gate reads that operation's level from its registry by name. Nothing
   on the wire says how dangerous a request is.
5. **Only the owner turns them on, at the ribbon.** Each button is a padlock whose picture is the
   state, read from `heron.config` when Revit starts; it asks for confirmation on the way on and never
   on the way off; either way of changing it takes effect at once. Nothing automatic sets them, and no
   agent does.
6. **The guard against accidents stays.** `prove`, a plain `fragment`, `validate` without
   `--allow-publish --write`, every setup step and every job `tools/generate-jobs.py` writes send
   nothing declared `PUBLISH` or `ADMIN`, so a batch walking the library alphabetically never sends an
   `export-*` declared `PUBLISH`. Three paths send one, each asking for that one fragment by name:
   `revit_change` from a chat, `fragment --write`, and `validate --allow-publish --write`. The read path
   no longer carries one at all - it used to, with `--allow-publish`, and an export needs no transaction.

### What does NOT change

- **[Article 7](../../HERON_CONSTITUTION.md) stands.** Deleting elements, purging, bulk parameter writes,
  family reloads, **workset changes** and **anything touching a linked model** still need the owner's
  explicit yes in the chat for that specific change. No switch says yes on his behalf. As D-99 recorded
  for Changes, nothing in code asks for it; the carrier is the instruction every chat is given
  (Articles 7 and 10 are *every chat* in the Constitution's Enforcement table). `CREATE_WORKSET` is
  `ADMIN` and a workset change: with Admin on the gate lets it through, and the chat must still ask
  first.
- **[Article 10](../../HERON_CONSTITUTION.md) stands.** Heron never saves, syncs or exports on its own
  initiative. Publish makes a publish *possible when asked*, never automatic.
- **[D-19](../DECISIONS.md#d-19--writing-is-off-by-default-until-the-write-path-has-met-a-real-revit) stands.** Changes
  is off by default, and it is the floor under both new switches.
- **[D-99](../DECISIONS.md#d-99--a-change-asked-for-in-a-chat-is-kept-at-once-with-no-preview-and-article-9-says-so)
  stands.** `revit_change` keeps what it does, with no preview, whichever of the three operations it is
  sent as.

### What it accepts

- **Ctrl+Z undoes only what happened inside the model.** An exported file stays written, a save is
  kept, a sync reaches everybody on the project, and a parameter written into the shared parameter file
  stays in that file. Each confirmation says so before the switch goes on.
- **The add-in never sees a fragment's own risk**, so a caller that skips Heron's client could still
  send an `ADMIN` fragment as `run_fragment_write`, under Changes alone. That is row 9's limit and it
  stands: the client refuses the mistake, and refusing the deliberate one in the add-in would mean
  sending the risk over the wire.
- **Two fragments that write files declare `MODIFY`** - `export-model-to-ifc` and `export-views-to-dwg`
  - so the Publish switch does not guard them. Found in FRAGMENT-ISSUES section 6 on 2026-09-19, left
  for the owner, and put to him now as [Q-59](../OPEN-QUESTIONS.md). Not changed here.
- **[docs/12 §1](../12-security-and-permissions.md)'s proposed mapping** asks for *"explicit, per action"*
  confirmation at `PUBLISH` and `ADMIN`. A switch is a standing permission, the same shape as Changes;
  per-action confirmation remains where Article 7 names it. That is the owner's choice, recorded here
  rather than smoothed over.

### Alternatives considered

- **Keep both refused.** Rejected by the owner: a modeller could not add a project parameter through
  Heron at all.
- **One switch for both.** Not what he asked for: one each, like Changes.
- **Send the fragment's risk with the request and let the add-in judge it.** Rejected - Golden Rule 19:
  the caller would be deciding how dangerous its own request is.

### Consequences

- **Easy:** with Changes and Admin on, *"add these two project parameters"* runs in the chat, as one
  entry in Revit's undo list.
- **Hard:** three switches to explain, so every refusal names the one that is off and where it is.
- **Locks in:** one operation per risk level for a fragment. A level above Admin, if one is ever added,
  is refused until somebody decides which switch opens it.
- **Owed:** NEEDS-CHECKING [group BF](../NEEDS-CHECKING.md) - the refusal with Admin off, the
  confirmation, binding `ID_Room_Name` and `ID_Room_Number` in *heron ai bulding* and reading them back,
  and the refusal again with Admin off. Recorded as [FRAGMENT-ISSUES row 5b-254](../FRAGMENT-ISSUES.md).
