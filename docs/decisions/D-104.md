### Context

Heron works in one direction: the modeller types into a Claude Code terminal **outside** Revit, and the
work reaches Revit through the MCP server and the pipe. [D-01](../DECISIONS.md#d-01--execution-host-claude-code-plugin)
chose that on 2026-08-27, called an in-Revit panel the better long-term experience, and kept the door
open. On 2026-09-06 the owner was asked again and stayed with Claude Code alone, so nothing was built.
The idea came back on 2026-09-20 in the plugin-extension brainstorm
([03 §3](../work-notes/plans/plugin-extension/03-open-questions.md)).

On 2026-09-27 the owner asked for the other direction: *"from Revit I can say something, it will go
to Claude, it will work from there and it will come back to Revit."* Asked which Claude, the answer
was *"Claude is not background, it will be on"* — the session already open, as if the words had
been typed there — and **Revit must not wait for the reply**. Then what should travel with the
words: press and hold a button to talk, release to send; the selection goes with them; and *"Heron
have a short memory for this selection — how much elements is selected and what was that element
with element id — so message will be not big and we can select lot of elements, … if need to
check the selection Claude can check again … without interrupt me."*

### Decision

1. **A Talk button in Revit sends the modeller's words, with what is selected, into the Claude Code
   session that is already open.** It uses Claude Code's *channels*: Heron's MCP server declares the
   `claude/channel` capability and pushes each message into the session, where Claude reads it exactly
   as if it had been typed there. **Claude Code stays the host and decides what the words mean**
   ([D-01](../DECISIONS.md#d-01--execution-host-claude-code-plugin), [D-34](../DECISIONS.md#d-34--herons-own-wording-is-english-understanding-the-user-is-not-herons-job)).
   Heron carries text and interprets none of it.
2. **Revit never waits for the reply.** The button saves the message and returns. The work reaches Revit
   the way it does today — Heron's tools, the pipe, the `ExternalEvent` — so Revit being free is what
   lets it arrive.
3. **The selection is saved, not sent.** When the modeller sends, the add-in saves what is selected: the
   model, the view, the count, and each element's id, `UniqueId`, category and name. The message carries
   only the count, the categories and the selection's number, so it stays small however much is
   selected. Claude reads the list with `heron_selection` when it needs it, and **reading it touches
   neither the model nor the pipe**, so it can never interrupt the modeller. It is the selection *when
   the modeller spoke*, not the live one, and it is deleted when that Revit closes.
4. **Revit and the chat meet through files, not a second pipe.** The add-in writes each message into
   Heron's derived folder (`talk` beside `bridges`); the MCP server claims it by renaming it, so exactly
   one chat takes each message. The bridge hands its pipe to the newest connection
   ([docs/25](../25-multi-session-and-binding.md)), so anything polling the pipe would cut off the chat's
   own requests — and `batch-prove`'s — mid-reply.
5. **Talk is off unless the chat was started for it.** [`mcp/heron-talk.cmd`](../../mcp/heron-talk.cmd) sets
   `HERON_TALK=on`, starts Claude Code with the development-channel flag naming Heron's server, and
   pre-allows Heron's own tools for that session, so a request from Revit does not stop at a terminal
   prompt nobody is looking at. A chat started any other way never claims a message, because Claude Code
   would drop it without a word.
6. **Built in steps, each proved before the next.** Step 1: the button opens a small window to type in —
   Windows voice typing (Win+H) already works there — and sends. Step 2: press and hold to talk, with a
   speech engine that runs outside Revit. Step 3: a hold key on the keyboard.

### What it accepts, said now so it is not a surprise later

- **Channels are a research preview.** Heron's channel is not on Anthropic's approved list, so Claude
  Code starts with `--dangerously-load-development-channels server:heron` and shows a warning screen
  every time. Anthropic says the flag and the protocol may change.
- **Claude Code must be open.** A message is only delivered while it runs; the button says so when no
  chat is listening, and sends nothing.
- **In a Talk session Heron's tools do not ask in the terminal.** What is given up is Claude Code's own
  prompt, not Heron's gate: every change still needs **Changes ON**
  ([D-19](../DECISIONS.md#d-19--writing-is-off-by-default-until-the-write-path-has-met-a-real-revit)) and keeps
  [D-99](../DECISIONS.md#d-99--a-change-asked-for-in-a-chat-is-kept-at-once-with-no-preview-and-article-9-says-so)'s rails.
  `write.enabled` is untouched and still off by default.
- **A process running as the same Windows user could write a message file.** The folder is the user's
  own, which is the same trust the bridge's discovery file already rests on.
- **Two Talk chats on one PC both listen**, and whichever claims first takes the message. Run one.
- **A company Claude plan** (Team or Enterprise) needs an admin to switch channels on.

### Alternatives considered

- **A second Claude run hidden in the background for each message** (`claude -p`). Rejected by the
  owner: it is not the conversation already open. Anthropic has also said `-p` will change to a mode that
  skips the subscription login and the project's MCP servers.
- **Polling the bridge's pipe for messages.** Rejected: the newest connection takes the pipe, so a poll
  would chop the chat's own requests mid-reply; and an answer outside the gate is a fourth exception
  that FRAGMENT-ISSUES row 5b-14 made a conversation rather than an accident.
- **A pipe that the MCP server listens on.** More code inside Revit — a pipe client and its discovery —
  for nothing files do not already give.
- **A docked chat that calls a model itself.** Rejected by D-01: it rebuilds the host, and it would put
  the network inside Revit, which [03 §1a](../03-heron-revit.md) forbids by construction.
- **Typing into the terminal window by simulated keystrokes.** Fragile, and it steals focus.

### Consequences

- **Easy:** the modeller stays in Revit and Revit stays free, so the wait that would have made every
  tool answer *Revit is busy* never happens.
- **Hard:** a preview feature and its warning screen; a chat not started with the launcher ignores Talk;
  the owner's PC is the only place any of it can be proved.
- **Locks in:** the talk folder's file format (format 1, written by `HeronTalkMailbox.cs` and read by
  `heron_talk.py`, held together by `tests/test_talk.py`); the `claude/channel` capability whenever
  `HERON_TALK` is on; and `heron_selection` as a READ tool that sends nothing to Revit.
