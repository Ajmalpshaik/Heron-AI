### Context

[D-132](../DECISIONS.md#d-132--off-windows-the-heron-server-serves-its-library-alone-and-no-revit-tool) made the server start
off Windows with its library tools, so that a cloud session can search, resolve and read a method.
[D-135](../DECISIONS.md#d-135--herons-python-side-keeps-its-data-in-userprofileheron-and-the-companions-notes-in-the-temporary-folder-where-a-store-claudes-copy-cannot-reach-them)
point 1 gives Heron's Python side no home off Windows, so the knowledge store has a folder there only when
`HERON_KNOWLEDGE` or `HERON_DATA` names one. [38 §1](../38-the-cloud-environment.md) sets `HERON_KNOWLEDGE` in the
cloud environment called *Heron* and calls it *"the one that is not optional"*.

A cloud chat that does not run in that environment - one opened from a phone is the case - has neither.
**Found live on 2026-11-11:** there `heron_lookup` and `heron_method` answered only *"Heron has nowhere to
keep what it knows ... Set HERON_KNOWLEDGE to a folder and ask again"*, and so did `heron_capabilities` and
`heron_resolve` when the real server was started over stdio with nothing named
([row 5b-1508](../fragment-issues/section-5b-rows-401-425.md)). A modeller in a chat cannot set a variable for a
server the host has already started. So D-132's first consequence held only where somebody had configured the
machine - and `tests/test_mcp_stdio.py` names a store for the server it starts, which is the one thing such a
session has not got, so no suite could see it.

### Decision

1. **A server run off Windows in D-132's library-only mode, with no knowledge folder named, names one for
   itself** before anything opens the store: `<machine-local>/Heron/index/<checkout>`. *Machine-local* is what
   `heron_bridge_client.local_app_data()` answers - `$XDG_DATA_HOME` when it is an absolute path, else
   `~/.local/share`, the folder .NET names there and where the development hooks' diary already is.
   `<checkout>` is the checkout folder's name and a digest of its whole path.
2. **It is that process's own `HERON_KNOWLEDGE`.** Every reader already asks that variable first, so the store
   is a private one by the rule already in `heron_scope.rebuild_refusal()` and `builds_from()`: built from that
   checkout's cards, on any branch, and warmed at start-up - exactly as one a person names.
3. **It is DERIVED, and it is not a home.** Such a server serves READ tools alone (D-132 point 5), so all it
   writes there is the index of the cards beside it, which a rebuild makes again; `index` is one of docs/06
   s2's derived folders. `heron_paths.data_home()`, `heron_scope.shared_dir()` and the brain's audit folder
   answer off Windows as they did: none.
4. **One folder per checkout.** A store two servers write follows whichever cards asked last (rows 136 and
   5b-233), and two chats in two worktrees are two servers.
5. **A folder somebody named is used as it is**, and **nothing else is given one**: on Windows the function
   does nothing, and a suite, a tool or `heron_scope.py --rebuild` with nothing named is refused by name, as
   before. If the folder cannot be made, if its name is not a whole path - `~` left unexpanded, or a
   relative `HOME` - or if it would land inside the checkout, nothing is named and the lookup says what to
   set, as before. The folder is made without looking for it first, so two servers started together both
   get it.
6. **The server says where on stderr**, once, at start.

### Alternatives considered

- **A home off Windows** - `~/.heron`, answered by `data_home()`, the one place that answers on Windows. It
  reverses D-135 point 1, and it would not have fixed this: a home's knowledge folder is the SHARED store,
  which is built only from a main checkout on branch `main`, and a cloud session is a clone on a branch of its
  own - so the first lookup would be refused for that reason instead. It would also give every suite and tool
  on Linux a store and a brain audit under the developer's home, where today they are refused
  (`tests/test_brain_reachable.py` section 7 and `tests/test_check_routing.py` section 10 hold that refusal).
- **`HERON_KNOWLEDGE` in `.mcp.json`.** One file starts the server on both systems, so it would take the
  owner's PC off its home.
- **The session-start hook sets it.** A hook can say a line to the chat; it cannot give a variable to the MCP
  server the host starts, and a session with no hooks would still have no store.
- **The temporary folder.** As derived, and gone sooner; Heron's other machine-local derived state is already
  under the folder chosen.
- **One folder for every checkout.** Point 4.
- **Leave it, and document the variable harder.** docs/38 already says it is not optional; the chat that met
  this could not act on the sentence.

### Consequences

- A cloud chat with nothing configured can search, list jobs and methods and resolve a capability. Its first
  lookup pays for building the index: measured here on 2026-11-11, about 20 s, then under a second.
- The *Heron* cloud environment's `HERON_KNOWLEDGE` still wins and is still what `tools/cloud-setup.sh` builds
  ahead of the first question; it is no longer what decides whether the server answers. **The tools and the
  suites still need it** - `check-routing`, `check-intrusion` and the rest exit 2 without a store, unchanged.
- **A document put in from a shell does not reach it.** `heron_standards` opens the company scope in the
  same folder and says, rightly, that nothing is indexed; `python brain/heron_ingest.py` run beside it has no
  folder named and stops on *"nowhere to keep knowledge"*, as before. Whoever wants company documents in a cloud session names
  `HERON_KNOWLEDGE` for both, as docs/38 does.
- **Two servers on one checkout share its folder.** Review of the first commit, 2026-11-11: a cold first
  lookup of 18 to 22 s became 34 to 36 s with three servers started at once, and one answered *"database is
  locked"* once before recovering ([row 5b-1520](../fragment-issues/section-5b-rows-401-425.md)).
- **The folder's path is joined in `heron_brain.py`, not asked of a path seam** - the precedent is the
  Companion's `live` folder ([row 5b-1519](../fragment-issues/section-5b-rows-401-425.md)).
- **Nothing prunes these folders.** A checkout that is removed leaves its index behind; it is derived, and
  deleting `Heron/index` under the machine-local folder is always safe.
- **Seen from a test host, not yet from a real cloud chat.** `tests/test_mcp_stdio.py` starts the real server
  over stdio with nothing named and holds a search, the method list, the job list and where the store went;
  it was seen to fail on the code as it stood and to pass on this. `tests/test_data_home.py` section 7 holds
  the name, what is left alone and who calls it, and runs where there is no MCP SDK. A phone chat on a branch
  carrying this has not been watched.
- **Nothing was run on Windows.** The call is under `LIBRARY_ONLY`, which is false there, and the function
  returns at once on Windows as well.
