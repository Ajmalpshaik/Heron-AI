# D-100 — A drop in the score of the owner's own questions is reported, never a gate

> One record of [the decision log](../DECISIONS.md). It was given its own file on 2026-09-23 so that it
> can be read alone; **its words are unchanged, only its links were re-pointed.** Decisions are
> append-only: to change one, write a new decision that supersedes it.

**Status:** Accepted · **Date:** 2026-09-23 · **Source:** Ajmal PS, 2026-09-23, asked as decision D3 of the earlier-brain plan
**Affects:** [`tools/score-routing.py`](../../tools/score-routing.py), [`tests/test_score_routing.py`](../../tests/test_score_routing.py), [`.github/workflows/gates.yml`](../../.github/workflows/gates.yml), which does not run it

### Context

`tools/score-routing.py` scores Heron's search on the 79 questions the owner asked on real work, against
the answers he confirmed on 2026-09-23 ([`tests/data/owner-questions.yaml`](../../tests/data/owner-questions.yaml)),
and names every question that fell since the last comparable run. Whether a fall should only be reported,
or should stop a pull request from merging, is a question about how Heron is developed, and it was the
owner's to answer. The plan that built the scorer called it D3.

### The question, as it was put

> *"Should a drop in this score only be reported, or should it stop a pull request from merging? Heron's
> other routing checks only report today - I recommend report-only to start."*

He asked what D3 was. It was explained as Revit's warnings against its errors: a warning shows in Review
Warnings and work carries on; an error stops the command. He answered: *"report only"*.

### Decision

**A drop in the score of the owner's own questions is reported and never stops a pull request.**
`tools/score-routing.py` exits 0 whatever it finds, and exit 2 only when it could not score at all. It is
not one of the gates CI runs.

### Alternatives considered

**Stop the pull request** — a drop fails the check and blocks the merge. It lost for three reasons.

- **Every routing check here already reports rather than gates, and says why.** `check-routing.py`,
  `check-intrusion.py`, `check-risk-crossings.py`, `check-skill-routing.py` and
  `check-declared-questions.py` all exit 0 whatever they find: a gate on a routing number teaches people
  to reword a sentence or weaken an utterance to buy the number back — [FRAGMENT-ISSUES row
  113](../FRAGMENT-ISSUES.md)'s forbidden move, and [D-34](../DECISIONS.md#d-34--herons-own-wording-is-english-understanding-the-user-is-not-herons-job)'s. On
  this score that move would be rewriting the owner's own questions or answers.
- **One run is a sample of one store**, not a measurement ([row 116](../FRAGMENT-ISSUES.md)), and a gate on a
  sample fails pull requests on noise.
- **A run takes about three minutes**, every lookup opening and checking the store.

### Consequences

- **Easy:** the score can be taken on any branch and read without blocking unrelated work.
- **Hard:** a real drop can merge if nobody reads it. The scorer names every question that fell and
  `--record` keeps the rows in [`brain/retrieval-history.md`](../../brain/retrieval-history.md); reading
  them stays a person's job.
- **Locks in:** `exit_code()` in the scorer returns 0 on a drop and names this decision, and
  `tests/test_score_routing.py` holds it there. Making a drop stop a pull request needs a new decision
  that supersedes this one — the recommendation said *"to start"*, and a later one may make it a gate once
  the score has been read on the owner's trained backend and is stable.
