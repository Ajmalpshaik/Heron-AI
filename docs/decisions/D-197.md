### Context

On 2026-11-23 another session was proving three DRAFT family tools on a scratch family, `fp-scratch`, in Revit 2020
(session 35764). A box came up in Revit and broke his concentration. Heron's add-in log and run records for that
morning show what it was:

- **Only one Heron box came up that morning.** It was the Keep or Discard box, *"Heron - keep this change?"*, for the
  `try-once` of `create-family-forms`. Run `wf-20261123-074520-0007-598f` started at 07:45:20 UTC, he pressed Keep, and
  it ended at 07:46:24 UTC (`asked: true`, `modellerAnswer: keep`, `elementsDeleted: 0`). His PC is on UTC+3, so that
  was about 10:45 his time. The brief that started this work gave 07:45 to 07:55 as local time; it was the log's UTC.
- **No Delete box came up.** No run that day counted a deletion. The log has no `Delete box:` line, the line D-142's
  gate writes (seen on 2026-11-09, for example). The four rolled-back runs after it had no warnings.
- **Ask to Keep was off** in that Revit the whole time. A DRAFT's one run is asked whatever Ask to Keep says
  (D-119, D-138 item 5), and so is a delete (D-142). Turning Ask to Keep off had stopped neither.

Asked which box he meant, he said both.

### Decision

1. **One more switch, *Ask to Delete*, in Heron's Settings beside Ask to Keep.** It is the sixth row there. It is
   held in Revit's memory (`HeronPermissions.AsksInRevit`) like D-166's three, and like them each Revit holds its own.
   Unlike them, it is **ON whenever Revit starts**: that was the owner's answer. No file holds it: `HeronConfig`
   declares no key for it, so a program writing `heron.config` cannot turn the Delete box off. No request sets it
   (Golden Rule 19).
2. **Safe on, like Ask to Keep.** Turning it off asks once, in Heron's switch window: *"Stop Revit's Delete box?"*,
   with *Keep asking* as the default. Turning it on asks nothing.
3. **On, nothing changes.** D-142's Delete box and D-119's Keep or Discard work exactly as before.
4. **Off, Revit shows neither box.** The executor reads the switch once per request, so D-142's second run is never
   decided by a different answer than its first.
   - **A kept change that Revit counts deletions in** is kept as it ran. There is no box, no rollback and no second
     run. Revit's own count is still taken. The log says `Delete box: off (Ask to Delete) - ... deletes N element(s)`.
     The reply carries `deleteAsked: false`, `deletedUnasked: N` and `deleteSkipped: "askToDeleteOff"`, plus a
     `deleteAsking` sentence the chat prints first: *"Revit did not ask before deleting: Ask to Delete is off ..."*.
     D-142's three refusals (`delete_in_publish`, `delete_not_shown`, `delete_not_measured`) existed only to show
     the box. With no box, they do not apply.
   - **A DRAFT's one run (`try-once`, `apply: "ask"`)** is kept with no box. The reply carries `asked: false` and
     `askSkipped: "askToDeleteOff"`, plus an `asking` sentence saying nobody has looked at it in Revit. The banner
     says *"Kept without asking - Ask to Delete off"*. The try-once record says `"asked": false`, and its positive
     phase says in words that nobody looked. It is never read as a modeller's Keep. Whether such a run counts as
     the positive case of the tool's proof is the signer's call.
   - **Ask to Keep is not read here.** With Ask to Keep on and Ask to Delete off, a chat's change that deletes still
     gets D-126's Keep or Discard box, which is Ask to Keep's own.
5. **The chat asks in words first.** Constitution Article 7 already wants the chat's explicit yes before the call
   for any delete, and `revit_change`'s description says so. With Ask to Delete off, that yes is the only one.
   `info` gains an `askToDelete` field. When it says off, `revit_health` and `heron_diagnose` print one line under
   that Revit, beside Ask to Keep's. The line tells the chat to ask the modeller in words and wait for a yes before
   any change that deletes, and to say, before trying an unproven tool, that it will be kept with no box. On, older
   or unread, no line is printed: Revit asks as it always has.

### What this does NOT change

- **Article 7's other cases**: purging, bulk parameter writes, family reloads, workset changes and anything that
  touches a link are still the chat's to ask about first.
- **Previews.** A run that rolls back deletes nothing and keeps nothing, whatever the switch says. Every proof is
  one, and so are `validate --write` and `tools/batch-prove.py`.
- **Changes, Admin, Publish and Ask to Keep** each decide what they decided. `write.enabled` stays off by default.
- **D-121's conditions on a DRAFT's one run.** The model must be in front, saved, and the run must be no export.
  The add-in still refuses everything else before the run.

### What it accepts

- **With Ask to Delete off, nothing in code stands between a chat and a delete except Changes.** The chat's yes in
  words is a rule a model can be argued out of. D-142 was written because that was once the only guard, and the
  owner chose this knowing it. The switch is on again at every Revit start, and the health line says when it is off.
- **An unproven tool's first run is kept without a look.** That is safe on a scratch family and riskier on a real
  model. Ctrl+Z takes it back as one step, and the reply and the banner both say nobody looked.
- **Not run in Revit.** Compiled and tested for 2020 to 2027. [Group PR](../needs-checking/group-pr.md) holds the
  checks owed.

### Alternatives considered

- **Two switches, one per box.** Offered to the owner, who chose one.
- **One switch, off at every start.** Offered to the owner, who chose on.
- **Widening Ask to Keep so that off also stops these boxes.** No new switch would be needed, but it would change,
  for every modeller, what an existing switch has meant since D-138. He asked for *"one more switch"*.
- **Keeping the switch in `heron.config`, like Ask to Keep.** Its risky side is off, so any program that writes
  that file could turn the Delete box off. D-166 moved the risky switches out of the file for that reason.
