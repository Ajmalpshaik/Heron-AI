# D-162 — The pipe to Revit refuses another computer, the chat checks who serves it, and the token's file is this user's alone

### Context

The bridge's pipe allowed only the current Windows user, and every request had to carry a token minted
for the session. The comparison D-155 came from found three gaps:

- **Another computer.** The same user's account, logged on over the network, carries the user's SID - and a
  named pipe is reachable over SMB while the Server service runs.
- **Another process.** The pipe's name is known to every process of the user. One that created it first
  would be handed the requests meant for Revit, and the token with them. The client never asked who served
  the pipe it opened.
- **The token's file.** It sat in `%LOCALAPPDATA%\Heron\bridges`, relying on the profile folder's rules.

### Decision

1. **The pipe denies `NT AUTHORITY\NETWORK`**, on both .NET branches - Microsoft's own guidance for a pipe
   used locally only. A deny rule is read before any allow, and no local logon carries that SID.
2. **The chat asks Windows which process serves the pipe** (`GetNamedPipeServerProcessId`) as soon as it
   opens it, and **refuses one that is not the Revit the discovery file named** - closing it with nothing
   written, the token included - answered `wrong_server`, a refusal. A pid that cannot be read on either
   side is not a mismatch: it refuses on evidence only, so a Windows that will not say changes nothing.
3. **The discovery file holding the token is set to this user alone**, its folder's rules no longer
   inherited. Best effort, Windows only: a file whose rules could not be set is still a working bridge.

### What is not known

None of it has run on Windows. It compiles for 2020 to 2027, the bridge round trip still passes on Linux
with the new code (`tests/test_bridge_roundtrip.py`), and `tests/test_pipe_hardening.py` runs the client's
rule on a stand-in pipe and reads the C#, failing on the code before the change. **Whether
`GetNamedPipeServerProcessId` answers on a client's handle** - Microsoft's page names the server's - decides
whether rule 2 ever fires; if it does not, the check reads nothing and refuses nothing.
[NEEDS-CHECKING Group NW](../needs-checking/group-nw.md).

### Alternatives considered

- **`PIPE_REJECT_REMOTE_CLIENTS`** - the same effect as rule 1, but .NET does not expose it on .NET
  Framework, which Revit 2020 to 2024 run.
- **`FirstPipeInstance`** - refuses to create a pipe another process made first. Not in .NET Framework's
  `PipeOptions` either; rule 2 catches the same squatting from the side that would be harmed.
