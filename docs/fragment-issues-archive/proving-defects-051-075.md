### Row 75

*Moved from the register on 2026-11-17.*

**Defect.** **THE CHAIN CANNOT CARRY A LINKED ELEMENT, AND WHEN AN ID COLLIDES IT BINDS THE WRONG ONE SILENTLY.** `select-from-link` is PROVEN and reaches into a link happily - on `Snowdon-scratch` it returns **142 Doors, 54 Rooms, 1128 Walls, 106 Windows** from `Snowdon Towers Sample Architectural.rvt`. **Nothing downstream can consume any of it.** `RevitFragment.Shape()` revives a carried value by walking its ElementIds through **`doc.GetElement(id)` on the HOST document**, and a linked element's id belongs to the LINK's document. **MOSTLY THAT FAILS SAFE AND SAYS SO:** 142 linked doors carried over produced *"'elements (IList<Element>) - nothing usable survived'"*, and so did 54 rooms. The message is honest and the run stops. **BUT 1128 LINKED WALLS PRODUCED `elements from select-from-link (2)`.** Two ids out of 1128 happen to name real elements in the HOST document, so two unrelated host elements were bound in place of linked ones, with a binding note that reads exactly like a successful narrowing. `report-door-room-links` then reported `doorsChecked 0` - it rejected them as non-doors and saved itself - **but a fragment that accepts any element would have acted on two things nobody chose.** **WHAT WAS AND WAS NOT ESTABLISHED:** the counts are measured (142->0, 54->0, 1128->2) and the mechanism is read from `Shape()`. The two surviving elements were NOT identified, so "they are unrelated host elements" follows from the ids belonging to another document rather than from inspecting them. **The safe behaviour and the dangerous one differ only by whether an id number happens to be in use twice.**

**State.** **MOVED TO ISSUE [#933](https://github.com/Ajmalpshaik/Heron-AI/issues/933) 2026-11-16** - still open, tracked there; this row is kept whole. Was: **OPEN - THE LOSS IS VISIBLE NOW AND THE WRONG BINDING IS NOT FIXED, 2026-09-20.** The state still says OPEN because the repair this row names - a carried value that says which DOCUMENT it came from - is not built, and two unrelated host elements are still bound. **WHAT CHANGED IS THAT IT NO LONGER READS LIKE SUCCESS.** `RevitFragment.Size` takes the carried value beside the shaped one and reports **`(2 of 1128)`** where it used to report `(2)`, which was indistinguishable from a deliberate narrowing to two. **THE MECHANISM WAS CONFIRMED FROM THE SOURCE RATHER THAN RE-RUN**, which this container can do and a Revit is not needed for: `Shape()` walks each carried `ElementId` through `doc.GetElement(id)` on the HOST document, swallows the miss (`try { ... } catch { }`), keeps only what resolved, and returns `live.Count == 0 ? null : live`. **The zero case was thought about and the partial case was not** - the comment on that very line reads *"Held ids, resolved none - not the same as having been empty"*. **NO THRESHOLD, DELIBERATELY**: *refuse below some percentage* needs a floor, and R-60 says a floor is derived from a measurement or it is not set at all. Reporting both numbers needs neither, and it is [row 71](../FRAGMENT-ISSUES.md#)'s rule again - naming is the half that cannot break a caller relying on today's behaviour. **AND THE FORMATTER IS NOW RUN, NOT ONLY COMPILED - WHICH A REVIEW FINDING ASKED FOR AND ITS AUTHOR HAD NOT.** The first version of this repair shipped with **no test**: `Size` had become the only thing distinguishing `(2 of 1128)` from the misleading `(2)`, and a compiler cannot catch a regression in its wording or in the ORDER of its two arguments, both of which are `object`. Codex raised it as P1 on the pull request and was right. **The rule moved into `revit/Heron.Revit.Addin/HeronBindingNote.cs`**, which touches no Autodesk type, so `tests/Heron.BindingNote.TestHost` links it **BY SOURCE** - the pattern `Heron.StackGuard.TestHost` and `Heron.Banner.TestHost` already use, for the reason their own project files give: a project reference would drag in `RevitAPI.dll` and make the one testable piece untestable anywhere without Revit. Linking the source keeps exactly **one** copy of the rule, which is [row 96](../FRAGMENT-ISSUES.md#)'s lesson. `tests/test_binding_note.py` builds and runs it, and **exits 3 where there is no .NET - which is not a pass**, the fourth state `check-gaps.py` and `change-evidence.py` both read. **IT WAS MEASURED AGAINST THE PREVIOUS IMPLEMENTATION, WHICH IS WHAT MAKES IT A TEST RATHER THAN A DESCRIPTION**: built against a copy of `Size` as it stood before the fix, **3 of the 7 checks fail and the host exits 1**, and the four that still pass are exactly the ones that must not move - equal counts, no carried value, and a scalar. **AND THE TEST NOW CROSSES THE CALL, WHICH A SECOND REVIEW SAID IT DID NOT.** Codex was right twice on this repair: the host links the FORMATTER, so its argument-order check only verified the order the host itself supplied. Swap the production call and every check in the host still passes while a modeller reads **"1128 of 2"** - the loss reported backwards, which is worse than the `(2)` this row started with, and no compiler catches it because both arguments are `object`. The call site now **names** them, `Size(shaped: shaped, before: value)`, and `tests/test_binding_note.py` reads that one line and fails when it changes - crude, and the only thing here that can fail when it does. **Measured by doing it:** swapped to `Size(shaped: value, before: shaped)`, the host still prints *"PASSED - 7 checks"* and **the suite exits 1**, naming what it found instead. **WHAT IS STILL NOT ESTABLISHED:** the sentence has never been seen in a real binding note. No Revit here and no linked model, so *"2 of 1128"* is the formatter proved on the two counts it is handed, not read off a screen after a real `select-from-link`.
