### Row 5b-83

*Moved from the register on 2026-11-17.*

**Defect.** **NINETY OF THE 145 MODULES IN `brain/` ARE IMPORTED BY NOTHING BUT THEIR OWN TEST - AND THAT IS THE EXACT SHAPE `mcp/README.md` SAYS WAS FIXED ON 2026-08-29, WHEN IT WAS EIGHT.** Measured 2026-09-21 with an AST walk over every `.py` in `brain`, `mcp`, `tools`, `tests` and `.claude`, resolving each import to the module it names. **145 modules in `brain/`: 53 reachable from `mcp/` or from another brain module, 2 reached only by a tool, 90 imported only by their own test, and 0 imported by nothing at all.** **THE COMPARISON IS THE REASON THIS IS A ROW.** `mcp/README.md` describes the state before `heron_brain.py` existed in its own words: the transport-only rule *“was being kept by **having no route at all**: eight brain modules, seven fragments and ten skills, imported by nothing but their own tests, and therefore **unreachable from any conversation**”*. One named seam was built so the rule could hold without that. The seam works - [row 5b-82](../FRAGMENT-ISSUES.md#) measured ten MCP tools standing on it. **The number it was built to fix has gone from eight to ninety.** **AND NOTHING DISPATCHES DYNAMICALLY, SO THE COUNT IS NOT AN ARTEFACT OF THE METHOD.** Three `importlib` uses exist in non-test code and all three load one named file - `heron_agent_count`, a backup tool, a spec probe. There is no registry that resolves an arbitrary brain module by name, so an import really is the only route in. **WHAT THE NINETY LOOK LIKE.** Every one carries a `Heron-Agent:` header, so each is the Kernel half of an agent in [28](../28-agent-registry.md) - and some of them are operationally serious rather than incidental: `heron_safemode`, `heron_rollback`, `heron_healing`, `heron_deployment` (which [row 5b-75](../FRAGMENT-ISSUES.md#) found promoting fragments through a lifecycle nothing calls), `heron_shadow`, `heron_regression`, `heron_observability`. **WHAT IS DELIBERATELY NOT CLAIMED HERE: THAT ANY OF IT IS WRONG.** An agent may be a vocabulary for who owns what rather than a runtime actor, and a library waiting for its caller is not the same thing as dead code. Answering that needs [18 - the Agent Operating System](../18-agent-operating-system.md) and [28](../28-agent-registry.md) read properly, and **neither has been read by this sweep**. [Row 5b-75](../FRAGMENT-ISSUES.md#) is what it costs to settle a question like this on half the sources - four modules were changed to match a document whose own header said it was a proposal, and all four had to be reverted

**State.** **MOVED TO ISSUE [#913](https://github.com/Ajmalpshaik/Heron-AI/issues/913) 2026-11-16** - still open, tracked there; this row is kept whole. Was: **OPEN — needs a sitting. NOTHING WAS CHANGED AND NO MODULE WAS WIRED TO ANYTHING.** **The measurement is the deliverable**; the judgement is not mine to make from here. **So it ships as a command rather than as a number in a cell** - `python tools/module-reach.py`, `--list` to name every module in each bucket. ### Row 5b-95

*Moved from the register on 2026-11-17.*

**Defect.** **SIX REFUSALS THE CODE PRODUCES AND NO CONTRACT DECLARES - A CALLER HANDLING EVERY DECLARED FAILURE STILL MEETS AN UNHANDLED ONE.** Found 2026-09-21. **`tools/generate-contract-reference.py` ALREADY REPORTS THESE ON EVERY RUN** and nothing records them, so they are re-discovered and never closed - which is why this row exists at all. The tool's own words for this direction: *“the code refuses with a word the contract does not list. A caller handling every declared failure still meets an unhandled one, and **that is the direction that breaks at run time**”*. **THE SIX, ACROSS FOUR AGENTS**: `HERON-FRG-UPD-008` produces `STALE_APPROVAL` (`brain/heron_apply.py`); `HERON-INS-HLT-009` produces `NOT_CHECKED_BY_A_CHECK` (`mcp/server/heron_install_health.py`); `HERON-NAM-VAL-002` produces `MISSING_PART`, `BAD_VERSION` and `GENERATED_A_BAD_NAME` (`brain/heron_naming.py`); `HERON-SKL-UPD-003` produces `REVISION_INCOMPLETE` (`brain/heron_revision.py`). **EVERY ONE WAS READ AND EVERY ONE IS A CORRECT, WELL-ARGUED REFUSAL** - the three in `heron_naming` are all from `generate()`, whose eight declared failures are all from the `check()` side, so the generate half was added and the contract never followed. **This is the session's own shape a fifth time** - [rows 5b-81, 5b-82, 5b-85, 5b-87](../FRAGMENT-ISSUES.md#) - *a document that was true when it was written and the code moved past it*. **AND THE OTHER DIRECTION READS ZERO**, so the tool is not noisy: nothing declares a refusal its code cannot produce

**State.** **MOVED TO ISSUE [#913](https://github.com/Ajmalpshaik/Heron-AI/issues/913) 2026-11-16** - still open, tracked there; this row is kept whole. Was: **OPEN — needs a sitting, and the question is one sentence long: what does a contract's `version` mean when the contract was wrong from birth?** `heron_contract.compare()` calls **an added failure state BREAKING**, which is MAJOR - so declaring these six would take four contracts from `1.0.0` to `2.0.0` **for a documentation correction, with no agent behaving any differently afterwards**. **`compare()` cannot tell *the promise changed* from *the promise was written down wrong*, and all six sit in that gap.** **NOTHING WAS CHANGED.** The alternative - making the code return an already-declared refusal instead - was checked and is wrong for all six: no declared code fits, and `AGENTS.md` says a rule is never edited to match code that broke it, so the direction has to be chosen rather than assumed. **IT IS NOT URGENT AND THE ROW SAYS SO**: `compare()` is exercised by its own suite and by nothing else, and no gate compares a contract against its previous version, so the consequence today is a rule rather than a red build. **THE MEASUREMENT IS THE DELIVERABLE** - `python tools/generate-contract-reference.py`, which prints the six and writes the page carrying both directions. **AND MY OWN SWEEP OF THE SAME QUESTION WAS WRONG 28 TIMES OUT OF 28.** A hand-rolled scan said 26 contracts declare a refusal the code never names; the tool says **0**, and the tool is right - those codes are named as the prefix of an exception message, like `raise LookupError("NO_SUCH_HANDLE: ...")`, and two more of my hits were a per-item annotation inside a list mistaken for the agent's own refusal. **The tool recognises a refusal BY POSITION, which is what its suite's first line says it does.** Third time in one day a crude scan was wrong about nearly everything it flagged - [5b-86](../FRAGMENT-ISSUES.md#) at 15 of 16, [5b-92](../FRAGMENT-ISSUES.md#) at 6 of 6 - and the standing instruction in `AGENTS.md` is the one that would have saved all three: **check whether a tool already owns the answer**
