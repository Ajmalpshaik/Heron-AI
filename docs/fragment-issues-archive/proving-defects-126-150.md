**State.** **FIXED 2026-09-19, AND THE RULE IS READ OUT OF THE C# RATHER THAN TYPED**, which is the half that keeps it true. `id_need_names()` parses `OneIdNamed`'s own `name == "..."` branches out of `RevitFragment.cs` - **22 names, derived on every call** - the same discipline `risk_ladder()` already uses for the HeronRisk enum, so the day somebody adds a rule to the add-in this tool follows without being edited. `receivable()` now refuses any need whose type carries `ElementId` and whose name the add-in has no rule for, with a reason that says WHY and names the two ways out: give the name a rule there, or change the contract to ask for the THING rather than its id. **AN UNREADABLE ADD-IN RETURNS AN EMPTY SET AND IS TREATED AS 'CANNOT TELL'** rather than as 'nothing resolves' - a missing checkout must not silently mark every id need blocked any more than it should mark them all arrangeable. **MEASURED: 7 EMITTED BECAME 4**, and the three that left are honest - `create-roof` because it is now PROVEN ([row 138](../FRAGMENT-ISSUES.md#)), `create-view-filter` and `copy-from-link` because they cannot run as written. **PROVED IN `tests/test_generate_jobs.py`, SEVEN CHECKS, AND THE LAST IS THE ONE THAT MATTERS**: no fragment in the library is offered with an id need the add-in has no rule for - which is the defect stated as a property of the whole library rather than as one fragment's story. **State.** **FIXED AND PROVED 2026-09-19, ON ALL THREE RELEASES INSTALLED ON THE OWNER'S PC, AND WRITTEN UP IN [docs/07 section 10](../07-installation-and-update.md).** Built into `tools/deploy-addin.ps1`: every deploy now copies the install it is about to replace into `%LOCALAPPDATA%\Heron\install-backup\<release>\` with a `replaced.json` recording the release, the UTC time, the assembly version, its SHA-256 and the file count; `-Rollback` puts it back and **verifies what was WRITTEN rather than what was intended**, the same discipline the deploy path already used; `-Remove` backs up first, because an uninstall is what somebody reaches for when things are already going wrong. The copy is taken at the LAST moment before overwriting, after every other check has passed, so a run that throws on the wrong build flavour does not spend the rollback point on a no-op. **THE PROOF IS A ROUND TRIP WITH A GENUINELY DIFFERENT BUILD, NOT A FILE COPY CHECKED BY EYE.** For each release a second build was made with `-p:Version=0.1.1`, deployed OVER the good one to stand in for an update that turns out badly, then rolled back, then every file in the folder hashed and compared: **2020** `2B3FA216` -> `C119604C` -> `2B3FA216`, **22 files restored, 0 differing**; **2024** `8A3922C3` -> `6E712353` -> `8A3922C3`, **22 restored, 0 differing**; **2027** `5B5935C8` -> `D34B37DF` -> `5B5935C8`, **15 restored, 0 differing**.
