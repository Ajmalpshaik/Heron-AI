# External Repository Adoption Plan

> **Type:** Operational work note. **Not specification.**
>
> This note answers one practical question: **from each external repository, exactly what should Heron take, what should it add, and what should improve because of it?**

Related plan: [`project-perfection-and-continuous-upgrade-plan.md`](project-perfection-and-continuous-upgrade-plan.md)

---

# 1. OpenDesign

Reference: `https://github.com/nexu-io/open-design`

## What I would take

### 1. One authority behind multiple interfaces

Take the principle that UI, CLI, agent, automation, and other surfaces should call the same underlying business logic rather than each owning their own implementation.

### What it adds to Heron

A stronger **Capability Authority** model:

- one Revit operation implementation;
- one capability/fragment contract;
- UI requests it;
- MCP requests it;
- agent requests it;
- future automation requests it;
- tests exercise the same core logic where possible.

### What it improves

- fewer duplicate implementations;
- fewer inconsistent results;
- easier debugging;
- easier testing;
- easier version compatibility;
- safer refactoring.

### Heron implementation direction

Audit current Heron features for duplicated logic across UI, MCP, Brain, and Revit bridge. Where duplication exists, move authority to one Heron-native layer and make other surfaces adapters.

---

## 2. Strong ownership boundaries

### What I would take

Clear separation between interface, orchestration, runtime adapters, persistence, registries, and execution.

### What it adds to Heron

A formal **Layer Ownership Check** for every change:

- UI owns interaction and display;
- Brain owns interpretation/planning/context;
- orchestration owns workflow;
- Revit bridge owns controlled Revit execution;
- registries own identities/contracts/status;
- persistence owns durable state;
- updater owns install/update lifecycle.

### What it improves

- prevents fixes being placed in the wrong layer;
- reduces architectural drift;
- makes future AI coding safer;
- makes repo easier for a new agent or developer to understand.

---

## 3. Runtime and capability discovery

### What I would take

Explicit discovery instead of assumptions.

### What it adds to Heron

A **Runtime Capability Snapshot** available to agents before planning:

- active Revit version;
- document state;
- write availability;
- available bridge/runtime;
- supported capability set;
- optional tools/providers;
- trust mode;
- whether something is unavailable or simply not detected.

### What it improves

- fewer hallucinated capabilities;
- fewer wrong-version calls;
- better fallback behaviour;
- clearer error reporting.

---

## 4. Managed artifact lifecycle

### What I would take

Artifacts are treated as managed project objects with origin, status, and lifecycle rather than random generated files.

### What it adds to Heron

An **Artifact Evidence Record** for important outputs:

- generated by;
- task/intent;
- source/context;
- version;
- status;
- verification state;
- replacement/superseded state.

Use Heron's existing metadata standard rather than creating a second metadata system.

### What it improves

- traceability;
- handover;
- debugging;
- safe cleanup;
- ability to know what is draft vs. proven.

---

## 5. Critique/lint before completion

### What I would take

A final quality review that is separate from ordinary unit tests.

### What it adds to Heron

A **Pre-Completion Critic Gate** checking:

- scope creep;
- wrong-layer changes;
- unsupported assumptions;
- missing negative tests;
- version compatibility;
- trust/security impact;
- stale docs;
- package/provenance impact.

### What it improves

It catches the kind of mistake that compiles and passes a small test but still makes the project worse.

---

## What I would NOT take from OpenDesign

- its frontend/backend technology stack;
- its product shape;
- its design-template terminology;
- its plugin marketplace architecture unless Heron later has a real requirement;
- its folder structure wholesale.

**OpenDesign contribution to Heron:** stronger architecture discipline and artifact/runtime management.

---

# 2. Awesome LLM Apps

Reference: `https://github.com/Shubhamsaboo/awesome-llm-apps`

## 1. Evaluation-gated self-improvement

### What I would take

The strongest pattern in this repository:

**baseline → execute → diagnose → one mutation → re-evaluate → keep/revert**.

### What it adds to Heron

A reusable **Improvement Loop** for low-risk intelligence assets:

- prompts;
- agent instructions;
- fragment descriptions;
- routing hints;
- evaluation cases;
- documentation;
- low-risk deterministic rules.

### What it improves

- stops random prompt tweaking;
- creates measurable improvement;
- allows rollback;
- builds evidence over time;
- makes Heron learn from failures without uncontrolled self-rewriting.

### Important restriction

Do not automatically mutate core architecture, Revit transactions, trust rules, installers, or production model-write code.

---

## 2. Scope-creep detector

### What I would take

Compare one-line intent against the final Git diff.

### What it adds to Heron

A **Change Scope Report** that marks files/changes as:

- required;
- supporting;
- tests/evidence;
- documentation;
- dependency/build/config change;
- suspicious/unrelated.

### What it improves

- prevents a small fix becoming a broad rewrite;
- improves PR review;
- makes AI-generated changes easier to trust;
- makes rollback simpler.

This should become one of the first things built.

---

## 3. Evaluation cases beside capabilities

### What I would take

Skills include trigger cases, expected outputs, and executable evals.

### What it adds to Heron

For important Heron agents/fragments/capabilities, progressively add:

- should-trigger cases;
- should-not-trigger cases;
- expected results;
- edge cases;
- negative cases;
- executable deterministic tests where possible.

### What it improves

- routing accuracy;
- lifecycle confidence;
- regression protection;
- easier promotion from DRAFT toward proven status.

---

## 4. Commit archaeology before cleanup

### What I would take

Before deleting ugly or old-looking code, inspect why it was introduced and which failures it protects against.

### What it adds to Heron

A **Legacy Change Safety Check** for compatibility and cleanup work:

- introducing commit;
- related fixes;
- related tests;
- affected Revit versions;
- reason for workaround;
- safe-removal evidence.

### What it improves

Especially valuable for Revit 2020–2027 compatibility, where apparently strange code may be deliberate.

---

## 5. Dependency doctor concept

### What I would take

Systematic dependency health review.

### What it adds to Heron

A lightweight dependency gate checking:

- unused dependency;
- duplicate package;
- version conflict;
- obsolete package;
- unnecessary framework addition;
- licence/provenance change.

### What it improves

- smaller install;
- fewer conflicts;
- safer upgrades;
- less technical debt.

---

## What I would NOT take from Awesome LLM Apps

- generic agent frameworks because examples use them;
- unrelated AI applications;
- demo UIs;
- broad autonomous self-evolution;
- provider-specific architecture unless Heron has a direct need.

**Awesome LLM Apps contribution to Heron:** measured improvement, scope control, eval discipline, and safer cleanup.

---

# 3. OpenHands / Agent Canvas

Historical reference: `https://github.com/OpenHands/agent-canvas`
Current reference: `https://github.com/OpenHands/OpenHands`

## 1. UI separated from execution

### What I would take

The UI does not directly own agent execution or workspace security.

### What it adds to Heron

A harder rule:

**Heron UI never owns Revit business logic.**

UI only:

- captures intent;
- shows progress;
- presents results/evidence;
- requests approved actions.

Execution stays behind the controlled Revit bridge/capability layer.

### What it improves

- safety;
- testability;
- maintainability;
- easier UI replacement later;
- fewer transaction/threading mistakes.

---

## 2. Mock/test mode

### What I would take

A first-class development mode that can simulate enough runtime behaviour to test UI/workflows without the real execution environment.

### What it adds to Heron

A **Heron Offline Test Harness** for everything that can truthfully be tested without Revit:

- routing;
- planning;
- fragment selection;
- schema validation;
- parameter/type contract validation;
- result/error contracts;
- lifecycle state;
- UI state;
- installer/update logic;
- report generation.

### What it improves

This can greatly reduce manual Revit testing time while keeping real Revit proof mandatory where required.

This is one of the highest-value long-term improvements.

---

## 3. Explicit runtime/service context

### What I would take

Backend tells the frontend/agent what services and environment are actually available.

### What it adds to Heron

A **Heron Environment Context Contract** passed into planning/execution rather than inferred.

### What it improves

- fewer guesses;
- better agent planning;
- better error messages;
- safer automation.

---

## 4. Packaging as part of QA

### What I would take

Build/package verification is part of normal quality gates.

### What it adds to Heron

A **Release Verification Gate** covering:

- clean build;
- expected files;
- installer/package contents;
- per-user/no-admin install promise;
- Revit version discovery;
- upgrade path;
- rollback/recovery;
- update compatibility.

### What it improves

Prevents the common problem where code works locally but the delivered Heron install is broken.

---

## 5. Workspace/security boundary

### What I would take

Treat local workspace access and automated actions as privileged.

### What it adds to Heron

Stronger explicit trust levels around:

- live Revit model writes;
- external file writes;
- external process launch;
- unattended automation;
- package/update changes;
- credentials/tokens.

### What it improves

- production safety;
- clearer user confirmation;
- safer future automation.

---

## What I would NOT take from OpenHands

- terminal/browser coding-agent UI as Heron's main interface;
- general coding sandbox architecture for Revit execution;
- unrestricted host filesystem access;
- its backend technology stack wholesale.

**OpenHands contribution to Heron:** execution separation, offline testing, environment awareness, packaging QA, and stronger trust boundaries.

---

# 4. My combined Heron plan

The three repositories should not become three new subsystems. Their best ideas should be merged into **one Heron-native improvement system**.

## New Heron mechanism: Improvement Gate

### Input

- one-line change intent;
- target subsystem;
- risk level;
- acceptance criteria;
- baseline commit/state;
- relevant tests;
- optional external references.

### Process

1. Capture baseline.
2. Discover environment/capability state.
3. Identify blast radius.
4. Revisit external research only when useful.
5. Create smallest Heron-native plan.
6. Implement bounded change.
7. Run focused tests.
8. Run negative/regression tests.
9. Compare intent against diff.
10. Check layer ownership.
11. Check Revit/version compatibility.
12. Check trust/security impact.
13. Check dependency/provenance changes.
14. Check packaging if affected.
15. Run independent critique.
16. Accept, revise, split, or revert.
17. Store evidence.

### Status result

- `PASS`
- `REVISE`
- `SPLIT`
- `REVERT`
- `NEEDS_REAL_REVIT_PROOF`

# 5. Recommended implementation order

## Priority 1 — Change Intent + Scope Gate

Build first because it protects every later AI-generated change.

## Priority 2 — Baseline/Evidence Record

Every fix or upgrade should have a before/after evidence package.

## Priority 3 — Offline Test Harness Expansion

Move everything safely testable outside Revit into fast automated verification.

## Priority 4 — Evaluation-Gated Improvement Loop

Apply first to prompts, agents, routing, fragment text, docs, tests and low-risk rules.

## Priority 5 — Architecture Ownership Gate

Detect wrong-layer changes and duplicated business logic.

## Priority 6 — Runtime/Capability Snapshot

Give the agent explicit environment truth before planning.

## Priority 7 — Packaging/Update Gate

Make delivery quality part of normal verification.

## Priority 8 — Unified Improvement Gate

Combine all previous mechanisms into one reusable workflow for:

- new features;
- bug fixes;
- refactors;
- upgrades;
- repo cleanup;
- agent improvement;
- release preparation.

---

# 6. Expected improvement to Heron

If implemented correctly, these ideas should make Heron:

- safer to change;
- harder to regress;
- easier for AI agents to understand;
- easier to debug;
- easier to test without Revit;
- more deterministic;
- more traceable;
- more controlled during self-improvement;
- cleaner during upgrades;
- safer across Revit 2020–2027;
- easier to package and release;
- less likely to accumulate duplicate logic or random framework dependencies.

The goal is **not to add more agents**.

The goal is to make every future Heron change **smaller, more evidence-based, easier to review, and safer to ship**.
